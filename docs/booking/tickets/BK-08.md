# BK-08 — Manual entry, status/stage edits, blackout dates

**Status:** plan-reviewed 2026-08-10 — 2 blockers, 4 should-fixes, 4 nits, all
accepted and folded in below. The blockers were both real code-level
contradictions: the draft claimed the BK-05 send seam could deliver "customer
message only" (it can't — `sendBookingNotifications` delivers the internal
message unconditionally, so the admin route would have mailed the office), and
claimed BK-07's warning flag would surface a failed admin-entry send (it
won't — `notificationFlags` deliberately never flags `source='admin'` rows).
Both now have named mechanisms: scope item 2 (`sendCustomerConfirmation`)
and the flash + neutral-stamp spec in items 3 and 7.
**Phase:** P4 · **Tier:** Reviewed · **Depends on:** BK-07 (detail page hosts
the edit forms; auth fix), BK-05 (confirmation send path) · **Blocks:** BK-06
partially (reminders read `sms_consent_at`, which manual entries must set
correctly)

Reviewed because it adds the first *authenticated write path* over
appointments and blackouts, touches the slot-uniqueness concurrency story,
sends email, and records CASL consent. Risk areas, in the order a reviewer
should weight them:

1. **Slot uniqueness under concurrency.** Manual entry races the public form
   for the same slot; the only real guard is the partial unique index and
   `insertBooking`'s CTE (null on conflict). Reuse it — a second insert path
   that checks-then-inserts reintroduces the race BK-02 closed. The subtler
   case is **un-cancelling**: a cancelled row's slot may have been rebooked,
   so flipping status back can violate the index mid-`UPDATE`; that must
   surface as a friendly "slot is taken" message, never a 500.
2. **Write whitelisting.** Every mutable field arrives from a form. Status
   and stage must be validated against their closed sets, ids must be
   integers, and nothing outside the whitelist (never `slot_start`, never
   insurance fields on edit) is updatable. `duration_minutes` is untouched —
   the CHECK is locked.
3. **CASL.** `sms_consent_at` is set only when the office explicitly checks
   the consent box (oral consent relayed), never by default, and never
   retroactively edited. Absence of the timestamp *is* absence of consent
   (locked rule).
4. **Email from the admin path.** A manual entry may send the BK-05 customer
   confirmation; it must never send the internal notification (the office is
   the one typing), a send failure must never fail the entry (BK-05's
   never-throws adapter and budget apply), and the locked PII copy rule
   holds by construction because the message builder is reused, not rebuilt.
5. **Grid math.** The form's date + time become a UTC instant via
   `zonedTimeToUtc` and are gated by `isSlotOnGrid` — both existing,
   red-verified, DST-aware helpers. Hand-building the instant is the
   wrong-day bug waiting to happen.

## Goal

The office can read bookings (BK-07) but cannot act: a phone-in emergency or
follow-up has nowhere to go, a cancellation frees no slot, a completed visit
stays "booked" forever, and closing a day for holidays requires SQL. This
ticket makes the admin surface operable: enter, edit status/stage/notes,
manage blackout days, and (re)send a confirmation.

## Decisions taken by the user (2026-08-10)

Asked rather than assumed; both client-facing.

1. **Manual entries send the customer confirmation via a checkbox, default
   on** when an email is entered. Office unticks it for after-the-fact
   record entries. The internal notification is never sent from admin.
2. **Admin bypasses all four public windows** — 4 h notice, 14-day horizon,
   closed Fridays, blackout days — and may enter past dates for
   record-keeping. Grid snap and the no-double-booking guard always hold
   (locked). This is the ROADMAP's "emergencies and follow-ups are phone-in
   and entered manually" made concrete.

## Scope

1. **`src/lib/booking-admin-entry.ts`** — pure parsers, no env, no DB,
   `tsx`-importable:
   - `parseAdminEntry(record)` → `{ ok: true; payload: BookingPayload;
     sendConfirmation: boolean } | { ok: false; errors }`. Contact fields
     reuse `isPlausiblePhone` / `isPlausibleEmail` and the service key
     validates against `SERVICE_LABELS`. The slot is built with
     `zonedTimeToUtc(dateKey, time)` from a date input plus a select of the
     five grid times, then checked with `isSlotOnGrid`; **no window checks**
     (decision 2). Payment route and insurance fields validate with the
     same rules as the public payload (insurer required on the insurance
     route). `smsConsent` true only when the checkbox value is present.
   - `parseAppointmentUpdate(record)` → whitelisted
     `{ id, status?, pipeline_stage?, admin_notes? }`, statuses and stages
     validated against the closed sets, id an integer. Nothing else passes.
   - `parseBlackoutInput(record)` → `{ day: DateKey, reason: string | null }`
     via `isValidDateKey`; and the delete form's day the same way.
2. **`src/lib/booking-notify.ts` gains a customer-only entry point**
   (plan-review blocker 1: the existing seam cannot express this —
   `sendBookingNotifications` delivers `plan.internal` unconditionally and
   `resendSender`/`deliver` are unexported, so "just don't send the
   internal one" was not buildable as drafted). New export
   `sendCustomerConfirmation(plan, bookingId, deps?) → 'sent' | 'skipped' |
   'failed'`, sharing `resendSender`, `deliver`, the deadline, and the
   `BOOKING_NOTIFY_DISABLED` check with the existing function — same
   never-throws contract, same injectable `deps.send` seam. It touches the
   customer message only; by construction it cannot deliver the internal
   one, and the verify script pins that (see Verification).
   `sendBookingNotifications` itself is unchanged — the public path keeps
   its exact shape.
3. **`POST /api/admin/appointments/create/`** — parse; on failure redirect
   back with **field-error codes only, never typed values** (plan-review
   should-fix 4: repopulating via query string puts names, addresses, and
   insurance identifiers into request URLs and platform logs; the office
   retypes — the form is short and theirs). On success call
   `insertBooking(sql, payload, null, now, 'admin')`; a `null` result means
   the slot was taken — redirect back with that message. Then, when
   `sendConfirmation` and an email was given: build the BK-05 plan, send
   via `sendCustomerConfirmation`, stamp `confirmation_sent_at` via
   `stampNotifications` (customer side only — its per-column CASE already
   supports that), all inside the BK-05 budget and swallow. The redirect to
   the new detail page carries the outcome as a flash param
   (`?email=sent|failed|off`), because BK-07's warning flags deliberately
   never fire for `source='admin'` rows (plan-review blocker 2) — the flash
   is the immediate surfacing, and the detail page (item 7) renders the
   admin-row stamp honestly thereafter. A NULL stamp on an admin row stays
   ambiguous between "unticked" and "failed" after the flash is gone; the
   resend button is the recovery either way, and the ticket accepts that
   ambiguity rather than adding a column for it.
   `internal_notified_at` stays NULL, which `notificationFlags` already
   treats as fine for `source = 'admin'`.
4. **`POST /api/admin/appointments/update/`** — parse; single `UPDATE` of
   the whitelisted fields plus `updated_at`. Status transitions:
   - entering `cancelled` sets `cancelled_at = now()`; leaving it clears
     `cancelled_at`.
   - leaving `cancelled` can violate the partial unique index (slot
     rebooked since): catch that specific failure and redirect with "that
     slot has since been rebooked" — the row stays cancelled.
   - no transition is otherwise restricted: the office may correct
     mistakes freely (completed → booked etc.).
   - a 23505 rolls back the whole statement, so a same-submit stage/notes
     edit is discarded along with the status flip; the redirect message
     says nothing was saved.
5. **`POST /api/admin/appointments/resend/`** — the detail page's
   "send confirmation email" action, offered and accepted **only for
   `status = 'booked'` appointments with an email** (plan-review should-fix
   5: a cancelled or no-show row must not receive a fresh "You're booked"
   for a slot that may since belong to someone else): same
   plan/`sendCustomerConfirmation`/stamp path as item 3, updates
   `confirmation_sent_at` on success, outcome flashed on the redirect.
   (BK-05 deferred "resending from admin" to the admin tickets; this is
   it.)
6. **`/admin/appointments/new/`** — the entry form, server-rendered, zero
   client JS: date input, grid-time select (the five starts), contact
   fields, service select, address block, payment route radio with both
   insurance fields rendered (no JS toggle — server validates per route,
   and the parser **drops** insurance values on the private route rather
   than storing stale ones), description, SMS-consent checkbox (unchecked),
   send-confirmation checkbox (checked), notes. Validation failures
   redirect back with field-error codes only — typed values are not round-
   tripped (see item 3's rationale).
7. **`/admin/appointments/[id].astro`** — gains the write forms: one form
   for status/stage/notes posting to update; the resend button (item 5's
   visibility rule) where the notification section already renders; a
   "cancel this appointment" path is just the status select. Renders the
   `?email=` flash. One rendering change from BK-07: an **admin-source row
   with an email** shows the customer stamp as a neutral "none sent" rather
   than "Not applicable" (which is now false — admin rows can have
   confirmations), keeping actual *warnings* web-only; the BK-07 matrix in
   `verify-booking-admin.ts` is updated to match (changed assertions, red
   runs owed).
8. **`/admin/blackouts/`** — list of blackout days (day, reason), an add
   form, per-row delete forms, posting to
   **`POST /api/admin/blackouts/add/`** and **`.../delete/`**
   (`INSERT … ON CONFLICT (day) DO UPDATE SET reason` and `DELETE`).
   Third link in the admin nav. Adding a blackout does **not** touch
   existing appointments on that day (see Assumptions).
9. **`/admin/appointments/index.astro`** — an "Add appointment" link to the
   new form. No other change.
10. **`scripts/verify-booking-admin-entry.ts`** + `npm run
    verify:booking:admin:entry` — the pure parsers, exhaustively (see
    Verification).
11. **`scripts/verify-booking-admin-db.ts`** + `npm run
    verify:booking:admin:db` — the write paths against the **Neon dev
    branch**, following BK-02's full four-step protocol, restated because
    this script imports routes: refuse when `DATABASE_URL_DEV` is unset
    (never fall back); assert the target host is not the production host;
    **swap `DATABASE_URL` first, then dynamically import** anything that
    reaches `getDb()` — the guard alone protects nothing; clean up
    fixtures. Asserts: entry insert; duplicate-slot insert returns null;
    cancel frees the slot for a re-insert; un-cancel after a rebook fails
    with the caught 23505, row stays cancelled; blackout add/remove visible
    to the availability query's blackout read **using a day inside the
    14-day window** (the availability blackout read is bounded by
    `blackoutQueryRange`, so an out-of-window day makes the assert inert);
    stamp-column writes. Sends stay muted here (`BOOKING_NOTIFY_DISABLED=1`)
    — send behavior is verified lib-level, not through the routes (see
    Verification).

## Out of scope

- **Reschedule as a first-class edit.** The path is cancel + re-enter,
  which the index handles correctly. A slot-editing UPDATE would need its
  own conflict story for zero operational gain at this volume.
- **File upload from admin.** Manual entries carry no photos; the files
  section stays read-only until BK-09.
- **Deleting appointments.** Records are corrected by status, never
  removed; the test-booking cleanup script remains a deliberate one-off.
- **Any SMS.** BK-06, still Twilio-blocked. This ticket only records
  consent correctly so BK-06 can trust it.
- **The leads pages' unslashed links / bare `toLocale*`** — Known traps,
  owner BK-10.

## Design notes

- **Reuse `insertBooking` wholesale.** It already accepts
  `source: 'admin'`, a null `draftId` degrades the file-claim CTE to a
  no-op, and its conflict contract (null on taken) is exactly the message
  the form needs. The alternative — an admin-shaped INSERT — would need its
  own red pass to prove the same race behavior the CTE already proved.
- **Admin bypasses windows by *not calling* the window checks**, not by
  flags threaded through them. `isSlotBookable` and friends stay untouched;
  the admin parser's slot rule is `isSlotOnGrid` alone. No shared function
  grows an `isAdmin` parameter — that is how the public path accidentally
  inherits the bypass.
- **The confirmation send builds the full BK-05 plan and hands it to the new
  `sendCustomerConfirmation`** rather than teaching `planBookingNotifications`
  an admin mode: the copy module stays single-shaped, and the customer-only
  invariant lives in one exported function that shares the adapter's
  internals. (The draft's claim that the *existing* seam could do this was
  plan-review blocker 1 — `sendBookingNotifications` delivers the internal
  message unconditionally.) The invariant is fixed either way: no internal
  email from admin actions, ever, and the verify script proves the new
  function never passes the internal message to `deps.send`.
- **The un-cancel collision uses the database as the arbiter.** Reading
  "is the slot free" before the UPDATE is the check-then-act race again.
  The UPDATE runs, and the unique-violation error (SQLSTATE 23505) is
  caught and translated. The verify script proves both the catch and that
  the row is unchanged after.
- **Blackout add is idempotent** (`ON CONFLICT (day) DO UPDATE`), because
  the office double-submitting a holiday should not error. The PK column is
  `day` (locked — not `date`).
- **Forms redirect, never render from the POST** (the existing admin
  pattern): every outcome is a 302 back to a GET, so refresh never
  resubmits.

## Acceptance criteria

1. `parseAdminEntry`: accepts a valid entry on any day (Friday, blackout,
   past, tomorrow) at a grid time; rejects off-grid times, malformed dates,
   bad phone/email, unknown service keys, and insurance-route entries with
   no insurer; a **private-route record carrying insurer/policy/claim
   parses with all three `null`** (the always-rendered fields make
   stale-typed-then-switched the likely path); `smsConsent` and
   `sendConfirmation` reflect the checkboxes exactly.
2. `parseAppointmentUpdate`: whitelist only — a record containing
   `slot_start`, `policy_number`, or any unknown key updates nothing beyond
   the whitelist; invalid status/stage values are rejected.
3. Manual entry for an occupied slot reports "slot taken" (from
   `insertBooking` returning null) and inserts nothing.
4. Cancelling sets `cancelled_at` and frees the slot: a subsequent insert
   at the same `slot_start` succeeds. Un-cancelling with the slot since
   rebooked fails with the friendly message and leaves the row cancelled;
   un-cancelling with the slot free succeeds and clears `cancelled_at`.
5. `sendCustomerConfirmation` passes exactly one message — the customer
   one — to its send seam, never the internal one; honors
   `BOOKING_NOTIFY_DISABLED`; maps error/timeout/unset-key to `'failed'`
   without throwing. The admin create route stamps `confirmation_sent_at`
   on `'sent'` only; with the checkbox off (or no email) nothing sends; a
   send failure still creates the appointment and flashes `?email=failed`.
   No admin action ever produces an internal notification.
6. Resend sends the customer message and updates the stamp; it is offered
   and accepted only for booked appointments with an email — absent for
   no-email rows, rejected for cancelled/completed/no-show.
7. `sms_consent_at` is set iff the consent box was checked, at entry time
   only.
8. Blackout add/delete round-trips: an added day appears in the list and
   in the availability query's blackout set; deleting removes it. Adding
   the same day twice updates the reason rather than erroring.
9. All new pages and endpoints sit behind the middleware (prefix-covered;
   no new public path), and every new link/action/Location is slashed.
10. `npm run typecheck` and `npm run build` pass.

## Assumptions log

Settled without the user; each is a reviewer's or the user's to overturn.

- **Reschedule = cancel + re-enter.** Named in Out of scope; the
  confirmation for the new time comes from the re-entry's checkbox.
- **Adding a blackout day does not cancel that day's existing
  appointments.** It only blocks *future public* booking; anything already
  booked stays and the office phones. Auto-cancel would be a silent
  destructive bulk action hiding behind a one-field form.
- **Un-cancelling is allowed** (mistake correction), with the DB-arbitered
  collision guard. Restricting transitions would force SQL for every slip.
- **Oral CASL consent relayed via checkbox is valid consent.** CASL
  recognizes oral express consent; the office attests by checking the box.
  The timestamp records when it was relayed.
- **Manual entries validate contact/insurance fields to the public
  standard.** Garbage in the office's hands is still garbage in BK-06's
  SMS-to number.
- **No new environment variables.**
