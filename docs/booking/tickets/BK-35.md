The office books phone-ins through `/admin/appointments/new/`. Two small gaps
matter more under P9 than they did under P8.

## Why now

**Email.** It is optional on the admin form and always will be — the client's
P7 exemption is explicit ("if we enter ourselves we will ask them to text
pictures/videos"), and `parseAdminEntry` hard-codes `entry: 'admin'` so that no
caller can make the public requirement apply (`booking-admin-entry.ts:214`,
`booking-payload.ts:186`). That structure is correct and this ticket does not
touch it.

What changes is the *consequence*. Under BK-27, no email meant the customer got
no written terms. Under P9 it additionally means **no payment link can ever be
sent** — and if the client answers open question #5 with "payment always
first", an email-less phone booking becomes unbookable rather than merely
undocumented. The office should see that at the moment the field is empty, not
discover it later.

A warning, not a block. Blocking would overturn a client decision.

**Send-confirmation.** Already defaults ON (`new.astro:236`,
`checked(raw.send_confirmation)` at `booking-admin-entry.ts:132`) — the
decision asked for it to stay that way, and it does, so there is nothing to
change there. What is missing is that unticking it is *silent*: "the customer
says they were never told" is currently unanswerable. One audit line fixes it.

## Scope

1. **Inline email warning on `/admin/appointments/new/`.** Rendered whenever the
   field is empty, including on first paint.

   **No JavaScript.** The page's own comment states it has "no client JS on
   this page at all" (`new.astro:167-172`) and the server validates per route —
   adding a listener for a warning would be the first script on the page and
   would put the nudge behind hydration. The CSS `:placeholder-shown` state is
   exactly "this input is empty", so the warning is a sibling revealed by
   Tailwind's `peer-placeholder-shown:` variant. This requires giving the input
   a `placeholder`, which it should have anyway.

   Copy, revised twice on 2026-08-16 — once after the client ruled that payment
   always precedes dispatch, then again in the review-fix pass to separate the
   policy from a mechanism Deploy 1 does not contain: **"Payment comes before
   dispatch — client policy, 2026-08-16 — and the payment link is emailed.
   Without an address there is no way to send them one, and no written terms
   either. Take an email if you can."**

   It warns about a dead end rather than rejecting the entry, because the
   booking still saves today and the office may be mid-call. **If the client
   resolves the exemption collision by making email mandatory** (ROADMAP Known
   trap, owned by BK-23), this stops being a nudge and becomes a `required`
   attribute plus a server-side check.

2. **Audit line when send-confirmation is unticked**, in
   `api/admin/appointments/create.ts`, after the row exists. A `console.warn`
   naming the appointment id, plus an appended line on `admin_notes` so the
   record carries it where the office can actually see it — a platform log is
   not somewhere the office looks.

   Appended, never overwriting: the office's own typed note is the primary
   content of that column.

## Out of scope

- **The emergency flag.** Removed by client decision 2026-08-16, and the second
  ruling that day removed the last reason for it: emergencies are not exempt
  from payment either, so the flag would have keyed an exemption that does not
  exist. What replaces it in BK-32 is a *timing* branch on proximity to the
  slot, which nobody has to remember to tick. Do not reintroduce it.
- **Making admin entries land anywhere other than where they land today.** The
  move to `approved_awaiting_payment` is BK-23's, in the same deploy as the
  machinery that can actually take the payment.
- Making email required for admin entries. Client exemption; not ours.
- Any change to `sms_consent`'s unchecked default — that is CASL, and the
  timestamp *is* the consent.
- Whether admin bookings require payment before dispatch — ~~open client
  question #5~~ **ANSWERED 2026-08-16: payment always first, no exceptions**
  (ROADMAP, P9 decisions). This bullet used to say the ticket "must not encode
  an answer in either direction", which the revised copy correctly no longer
  obeys; leaving it would have told a future reviewer to treat the shipped
  warning as a scope violation. What remains out of scope is the *mechanism* —
  the dispatch gate and the payment link are BK-23/BK-32, in Deploy 2, and the
  warning is careful to read as policy rather than as an enforcement that
  already exists.

## Risk areas for the reviewer

- The warning is copy about money and reachability, on an internal surface. It
  must not overstate: it says the customer cannot be *reached*, not that the
  booking is invalid.
- `admin_notes` is written by the parser and by this append. Check the append
  cannot truncate past `MAX_ADMIN_NOTES` (4000) into a DB error on a row that
  already committed — past the insert, nothing may fail the request.
- The CSS-only warning must not regress the "no client JS" property.

## Acceptance criteria

1. `/admin/appointments/new/` shows the warning on first paint, with the email
   field empty, and hides it once any character is typed — with JavaScript
   disabled.
2. Unticking send-confirmation writes a `console.warn` naming the id, and the
   saved row's `admin_notes` ends with the audit line.
3. Ticking it (the default) writes neither.
4. A row saved with send-confirmation unticked and an email present sends no
   confirmation — unchanged behaviour, asserted so the audit line cannot be
   mistaken for a behaviour change.
5. `admin_notes` at or near the cap does not fail the save **and does not make
   the appointment uneditable afterwards**. The second half was added after
   implementation review: the insert was never the risk (`TEXT` column), but the
   appended line pushed the stored value past `parseAppointmentUpdate`'s cap on
   the way back in, and the detail page submits notes in the same form as
   `status` and `pipeline_stage`. The original wording — "does not fail the
   save" — is exactly what let that through.

## Implementation notes

`UNTICKED_NOTE` and `appendUntickedNote` live in `booking-admin-entry.ts`, not
in the route. That module is the pure, env-free seam the verify harness already
imports; leaving the helper in `create.ts` would have meant importing an API
endpoint into a `tsx` script to assert anything about it.

The note is appended **before** the insert and passed to `insertBooking`, rather
than written by a post-commit UPDATE. Past the insert nothing may fail the
request — a second statement there is a way for a saved appointment to answer
500 — and this way the note is never missing from a row that exists. The
`console.warn` is emitted after, where there is an id to name.

The warning is CSS-only via Tailwind's `peer-placeholder-shown:` variant, so the
page keeps its no-client-JS property. Verified in the built stylesheet: the rule
`.peer-placeholder-shown\:block:is(:where(.peer):placeholder-shown~*)` is
emitted, `AdminLayout` imports `global.css`, and the variant rule sits after
`.hidden` in the cascade (and outranks it on specificity), so the reveal wins.

### Blocker

**B1 — ACs 2 and 3 are unasserted, and the ticket claims otherwise.**
`scripts/verify-booking-admin-entry.ts:824-864` exercises `appendUntickedNote`
in isolation. Nothing binds the route: neither the ternary at
`create.ts:80` nor the `console.warn` at `:109-113`. Demonstrated, not inferred —
the reviewer inverted the ternary to
`sendConfirmation ? appendUntickedNote(adminNotes) : adminNotes` and
`npm run verify:booking:admin:entry` still printed `✓ admin entry checks passed`.
The closing paragraph of this ticket ("The remaining ACs (1, 4)…") asserts by
omission that 2 and 3 are covered. They are not, and none of red rows a/b/c
touches the route.

Failure scenario: a later refactor flips the ternary. Every entry with the box
**ticked** — the default — is stamped "Confirmation email not sent" on a row
where the email did go out, and unticked entries get no note. All gates stay
green, and the audit line becomes misleading evidence in the exact conversation
it was written for.

Fix (the pattern already exists at `:800`): comment-stripped source-text
assertions that `create.ts` contains
`sendConfirmation ? adminNotes : appendUntickedNote(adminNotes)` and an
`if (!sendConfirmation)` guarding a `console.warn` naming `created.id`. Red-observe
each. This is a blocker on *verification*, not on behaviour — the shipped
ternary and warn are correct today.

### Should-fix

- **S1 — the uncapped append can brick the appointment's edit form.**
  `parseAdminEntry` caps the typed note at `MAX_ADMIN_NOTES` (4000)
  (`booking-admin-entry.ts:253`); `appendUntickedNote` then adds `\n\n` + 61
  chars, so a stored value reaches 4063. `parseAppointmentUpdate` re-applies the
  same 4000 cap on the way back **in** (`:332`), and `[id].astro:507-566` renders
  that value into the same `<form>` as `status` and `pipeline_stage`. Above
  **3937** typed characters with the box unticked, every later status or stage
  edit returns `?saved=invalid` → "That edit was not valid. Nothing was saved."
  with no field named, and the appointment cannot move through the pipeline
  until someone hand-deletes text the system wrote. `maxlength` does not catch
  it: per WHATWG HTML, `suffering from being too long` requires the dirty value
  flag and a user edit, so a too-long *initial* value is not blocked client-side.
  AC5's wording ("does not fail the save") is what let this through — the cap is
  a read-back bound as well as an input bound. Fix: reserve headroom at entry
  (`MAX_ADMIN_NOTES - UNTICKED_NOTE.length - 2`), or make the update-path cap
  tolerant of the audit line, or record as a Known trap with an owner.
- **S2 — the "Out of scope" bullet at `BK-35.md:82-83` is stale.** It calls
  payment-before-dispatch "open client question #5" and says this ticket "must
  not encode an answer in either direction"; `ROADMAP.md:955-960` records it
  **ANSWERED 2026-08-16** ("payment always first, no exceptions"). The copy is
  right and the bullet is wrong, but as written it instructs a future reviewer to
  treat the implementation as a scope violation.
- **S3 — the warning copy describes Deploy 2's mechanism in Deploy 1's present
  tense** (`new.astro:180-182`). ROADMAP defines Deploy 1 as "no flow change";
  there is no payment link to send and no dispatch gate until BK-32/BK-23. "we
  cannot send them a payment link" implies that with an email we can (false
  today), and "cannot be confirmed or dispatched until it is paid" describes a
  gate that does not exist. Both clauses are true as *policy*, false as
  *mechanism*. Risk runs the unsafe way: the office believes the system enforces
  the gate and stops chasing payment. Fix: phrase as policy, or hold the sentence
  for the Deploy 2 commit that makes it true.
- **S4 — the "Cascade check" gate row is a proxy that cannot go red.** The
  reviewer deleted `'peer ' + ` from `new.astro:177` — which disables the warning
  permanently, since `:where(.peer)` then matches nothing — rebuilt, and the rule
  `.peer-placeholder-shown\:block:is(:where(.peer):placeholder-shown~*)` was
  **still present** in `dist/`. It is generated from the `<p>`'s class list alone.
  The same holds if the `placeholder` attribute is dropped. Fix: assert in the
  verify script that the email input carries both `peer` and a non-empty
  `placeholder=`, and that `peer-placeholder-shown:block` appears after it.
- **S5 — AC4's stated coverage does not exist.** The existing suite's
  `sendConfirmation` assertions (`verify-booking-admin-entry.ts:333-337, 349-358`)
  test that `parseAdminEntry` *returns the flag*, not that no confirmation is
  sent; the send decision at `create.ts:126-131` is asserted nowhere. Risk is nil
  (the diff does not touch it), but say "unchanged by this diff" rather than
  "covered by the existing suite".

### Nits

- `create.ts:80` — the audit line covers only the unticked path. The commoner
  silent case is **ticked + no email**: nothing sent, no note written, so the
  scenario the new warning exists to flag leaves no trace on the row.
- `verify-booking-admin-entry.ts:860-863` — `/not sent/i.test(UNTICKED_NOTE)` is
  a substring standing in for "names the consequence"; it would pass on useless
  wording and fail on good wording.
- `new.astro:179` — no `aria-describedby` from the input to the warning.
  `display:none` correctly keeps it out of the tree when filled, so adding it is
  safe.
- `new.astro:170` — label moved to "(strongly encouraged)" while the field stays
  optional with no `required`. Consistent with intent; flagged so it is not read
  as a validation change.
- `new.astro:176` — `:placeholder-shown` is now load-bearing on an attribute
  that reads like decoration. The inline comment already says so.

### Verified correct

`admin_notes` is a bare `TEXT` column (`scripts/migrations/002-booking.ts:58`;
no `ALTER` in 003–005), so the uncapped append genuinely cannot fail the insert —
the ticket's premise holds. Nothing after the insert can throw: the added
`console.warn` interpolates a number, and both post-commit sends already carry

Red rows a/b/c each isolate what they claim, for the helper. The `console.warn`
logs an id only, and `BookingPayload` carries no `admin_notes`, so the audit line
cannot reach a customer-facing email.
