# BK-02 — Booking commit endpoint

**Status:** implemented 2026-08-07, all gates green, 16/16 failure modes
observed red — awaiting implementation review
**Phase:** P2 · **Tier:** Heavy · **Depends on:** BK-01

Heavy: a public endpoint that writes, holds insurance identifiers and CASL
consent, is the only real guard against double-booking, and creates rows that
cannot be silently un-created.

## Goal

Turn a completed booking form into an `appointments` row plus its claimed
uploads, rejecting anything the picker should never have offered and losing a
slot race gracefully.

BK-01's verification seeded four rows into production behind an explicit flag.
BK-02's is a **concurrency hammer that creates real bookings in parallel**, and
that must not touch the live table.

Neon branching is copy-on-write, so a dev branch starts as an instant snapshot
of production's schema *and* data at branch time, on its own compute.

1. Authenticate — interactive, once. `neonctl` is not installed and no
   `NEON_API_KEY` is present, so this needs a human:
   `npx neonctl auth`
2. **Discover the project id.** `NEON_PROJECT_ID` *is* in `.env.local` but its
   value is the empty string — Vercel's env pull wrote it blank, as it did for
   `DATABASE_URL_UNPOOLED` and the `POSTGRES_URL*` family. Both `loadEnv`
   implementations skip empty values, so `$NEON_PROJECT_ID` expands to nothing
   and the command below would fail. Get the real id from
   `npx neonctl projects list` (match it by the production host in
   `DATABASE_URL`) and write it into `.env`.
3. `npx neonctl branches create --project-id "$NEON_PROJECT_ID" --name dev`
4. `npx neonctl connection-string dev --project-id "$NEON_PROJECT_ID" --pooled`
5. Put that string in `.env` as **`DATABASE_URL_DEV`** — *not* in `.env.local`,
   which `vercel env pull` overwrites. `.env` is gitignored.
6. Confirm the ledger on the branch:
   `DATABASE_URL="$DATABASE_URL_DEV" npm run migrate -- --status`.
   The env override is required. `migrate.ts` reads only `DATABASE_URL`, loads
   `.env.local` before `.env`, and never overwrites an already-set key — so a
   plain `npm run migrate` reports "Schema up to date" **against production**
   and confirms nothing about the branch. A copy-on-write branch snapshots
   schema and data including `schema_migrations`, so this should show both
   migrations already applied.

**Env split, from here on:**

| Variable | Points at | Used by |
| --- | --- | --- |
| `DATABASE_URL` | production | the app, and prod smoke tests behind `--allow-production` |
| `DATABASE_URL_DEV` | Neon dev branch | every writing verification script, by default |

Writing verification scripts must **refuse to run** when `DATABASE_URL_DEV` is
unset rather than silently falling back to production. Retrofit
`scripts/verify-availability-db.ts` to the same rule as part of this ticket:
default to the dev branch, keep `--allow-production` for deliberate prod smoke
tests only.

**How the branch actually reaches the handler** — this is not implied by the
guard, and getting it wrong means a script that passes every stated rule while
hammering production. `getDb()` reads `process.env.DATABASE_URL` and nothing
else, and the house pattern (see `verify-availability-db.ts`) imports the route
module and calls its handler in-process. So each writing script must, in order:

1. refuse if `DATABASE_URL_DEV` is unset;
2. assert its host differs from the production host in `DATABASE_URL`;
3. `process.env.DATABASE_URL = process.env.DATABASE_URL_DEV`;
4. **only then** dynamically `import()` the route module.

Step 4 must come last — a static import would bind `getDb`'s environment read
before the swap.

## Design notes

- **Revalidate every rule server-side through `isSlotBookable`** (exported by
  BK-01 for exactly this). Do not re-assemble the four exclusion rules by hand —
  that drift is what `booking-config.ts` exists to prevent. Check
  `isSlotOnGrid` *first* and separately: the submitted instant is untrusted and
  may not be a grid time at all, which `isSlotBookable` deliberately assumes.
- **Insert and file-claim must be one statement.** The Neon HTTP driver has no
  interactive transaction, and the claim needs the new `id`, so a two-call
  sequence can leave a booking whose photos are then deleted by the orphan cron
  24 hours later. Use a single CTE:

  ```sql
  WITH new_appt AS (
    INSERT INTO appointments (...) VALUES (...)
    ON CONFLICT (slot_start) WHERE status <> 'cancelled' DO NOTHING
    RETURNING id
  ), claimed AS (
    UPDATE appointment_files SET appointment_id = (SELECT id FROM new_appt)
    WHERE draft_id = ${draftId}::uuid AND appointment_id IS NULL
      AND EXISTS (SELECT 1 FROM new_appt)
    RETURNING id
  )
  SELECT new_appt.id, (SELECT COUNT(*)::int FROM claimed) AS files
  FROM new_appt
  ```

  `ON CONFLICT ... WHERE status <> 'cancelled'` infers the partial unique index
  `appointments_slot_unique` — confirmed against the live schema.

  **The `FROM new_appt` is load-bearing.** The obvious tail —
  `SELECT (SELECT id FROM new_appt) AS id, ...` with no FROM — always returns
  exactly one row, with `id` NULL on conflict. Probed directly:
  `WITH x AS (SELECT 1 AS id WHERE false) SELECT (SELECT id FROM x) AS id`
  returns `[{"id": null}]`, while the `FROM x` form returns `[]`. Checking
  `rows.length === 0` against the first form is never true, so **the loser of a
  race would get 201 with a null id** — the index would hold the line while the
  endpoint told both visitors they had booked. With `FROM new_appt`, zero rows
  genuinely means the slot went to someone else.

  `COUNT(*)::int` likewise matters: the driver hands back bare `COUNT(*)` as the
  *string* `"0"`. Same deserialization trap family BK-01 spent a blocker on.
- **Claim files regardless of `upload_state`.** `onUploadCompleted` never fires
  on localhost, so every dev upload is stuck at `'pending'`; filtering on
  `'uploaded'` would silently drop real photos in dev and any production upload
  whose callback was slow.
- **The claimed `draft_id` is whatever `verifyDraftToken` returned — never a
  client-supplied field.** The payload carries the *token* only; a bare
  `draft_id` key is rejected by the validator as unknown. Verifying a token and
  then binding a separately-submitted id into the CTE would let an attacker
  present their own valid token and claim a victim's `draft_id`, which is
  exactly the attack the check exists to stop. A booking with no draft token is
  valid (zero files); one with a bad or expired token is a 400, not a silent
  no-file booking.
- **Distinguish the conflict from a real failure.** Map *only* a zero-row CTE
  result to 409. Do not treat any thrown error as "slot taken" — a connection
  failure would then read to the visitor as a lost race and to us as normal.
- **Rate limit: 10 bookings per IP per hour**, via `consumeRateLimit`. The
  window is persisted in `rate_limits`, so verification runs must not share a
  bucket: `clientIp` falls back to `'unknown'` for an in-process `Request` with
  no `x-forwarded-for`, which would put the whole hammer plus every rejection
  case in one counter and turn AC2's expected 409s into 429s — and would leak
  across repeated runs within the hour. Each logical test stamps its own random
  `x-forwarded-for`, and the AC9 429 test runs **last**, on a throwaway IP.
- Insurance identifiers are accepted only when `payment_route === 'insurance'`
  and are dropped otherwise, so a private-pay booking cannot carry a claim
  number picked up from a stale form state.
- `sms_consent_at` is set to now **only** when consent was given; absent
  consent it stays null. There is no boolean (CASL).
- `source` is `'web'`; `pipeline_stage` keeps its `'assessment'` default.

## Acceptance criteria

1. A valid payload for a free, in-window grid slot creates exactly one row and
   returns 201 with the appointment id and its formatted slot label.
2. Concurrent submissions for the same slot produce **exactly one** row: one
   201, the rest 409 with a "just taken" message. Verified under real parallel
   load, not reasoned about.
3. A slot that is off-grid, in the past, inside the 4-hour notice window, past
   the 14-day horizon, on a Friday, on a blackout date, or already booked is
   rejected with 409/422 and creates nothing.
4. Files for the submitted draft are attached to the new appointment,
   `upload_state` notwithstanding; files of *other* drafts are untouched.
5. A missing draft token books with zero files; a forged or expired one is a
   400 and creates nothing.
6. Insurance fields persist only for `payment_route = 'insurance'`; they are
   null for `'private'` even when submitted.
7. `sms_consent_at` is null unless consent was given, and a timestamp when it was.
8. Field-level validation errors return 422 with per-field messages and create
   nothing. Oversized or malformed JSON does not 500.
9. Rate limiting applies per IP and returns 429 with `Retry-After`.
10. A DB failure returns 500 and never a false success.
11. Nothing in any response body echoes `policy_number` or `claim_number`.

## Verification

- `npm run typecheck`, `npm run build`.
- `npm run verify:booking:payload` — pure: required fields, phone/email shapes,
  insurance conditionals, consent handling, oversized strings, unknown keys,
  and that no validator output carries insurance identifiers.
- `npm run verify:booking:commit` — **dev branch only**, refuses without
  `DATABASE_URL_DEV`, host-asserted against production:
  - **the raw-CTE conflict test, run first.** Execute the CTE statement itself
    N times in parallel against one slot and assert exactly one execution
    returns a non-null id, none throws, and the losers claim zero files. The
    endpoint-level hammer alone can pass without ever reaching `ON CONFLICT`:
    if the requests happen to serialize, the advisory precheck produces all
    N−1 409s and the conflict path executes zero times, so a broken
    `ON CONFLICT` clause would go unnoticed. This test cannot be dodged that
    way;
  - the endpoint hammer for status-code mapping: N ≥ 10 requests launched with
    a single `Promise.all` and no `await` between launches, asserting one 201,
    N−1 409s, and `COUNT(*) = 1` afterwards;
  - each rejection case from AC3, asserting zero rows created;
  - file claim including a `'pending'` file and a foreign draft left alone;
  - forged and expired draft tokens, and a payload carrying a bare `draft_id`;
  - insurance-field stripping and consent handling read back from the row;
  - **AC10**: a run with `DATABASE_URL` pointed at a non-resolving Neon-shaped
    host, asserting 500 and that no row was created — the trick BK-01 used, and
    it matters more here, where a swallowed insert error reported as 201 is an
    appointment that does not exist;
  - **AC11**: every endpoint response body (201, 409, 422, 429, 500) scanned
    for seeded `policy_number` / `claim_number` values, mirroring BK-01's
    marker-leak check. The pure script only covers validator output, which is
    not what reaches a browser;
  - **AC9** last: a throwaway IP driven past the limit, asserting 429 and a
    `Retry-After` header.
- Re-run `npm run verify:availability` and `verify:slots` for regression.

## Risks

- The partial unique index catches identical `slot_start` only. Everything here
  assumes grid-snapped 30-minute appointments; BK-08's manual entry must snap to
  the same grid or it can create an overlap this endpoint cannot see.
- A visitor double-submitting will hit their own booking's 409 and read it as
  "someone took my slot". See the open question below.
- The CTE claims files even if the client never finished uploading; those rows
  stay `'pending'` forever and the orphan cron ignores them once
  `appointment_id` is set. Acceptable — a stuck row is better than a deleted
  photo — but BK-07's admin view should not promise a file it cannot fetch.

## Assumptions log

- **The service vocabulary is injected, not imported.** `SERVICE_LABELS` lives
  in `db.ts` beside the Neon import, so importing it into the validator would
  pull the driver into every consumer — including BK-03's browser island. The
  endpoint passes `new Set(Object.keys(SERVICE_LABELS))`; the pure script passes
  its own set. Same reasoning as `booking-uploads.ts` avoiding `@vercel/blob`.
- **`insertBooking` is exported** solely so the verification can race the real
  statement rather than a hand-copied one that could drift from it.
- **Rate limit is 30/IP/hour** (`BOOKING_RATE_LIMIT_PER_HOUR`), above the
  12-request hammer so its expected 409s cannot arrive as 429s. Generous against
  five slots a day on purpose: it exists to stop a script, not to ration an
  office behind one NAT.
- **A local `BOOKING_DRAFT_SECRET` now lives in `.env`.** The one in
  `.env.local` is empty — `vercel env pull` writes sensitive vars back as `""` —
  so token signing could not work locally at all. Production keeps its own.

- **201 rather than 200** for a created booking, with the id in the body.
- **422 for validation, 409 for slot conflicts**, so BK-03 can tell "fix your
  input" from "pick another time" without parsing prose.
- **No hold/reservation step.** Availability stays advisory, per BK-01; the
  index is the guard. A hold table would need its own expiry sweep for a race
  that is rare at five slots a day.

## Open questions

**Settled in plan review — 409, not idempotent 200.** My premise that
idempotency was "cheap to add" was wrong: `appointments` has no `draft_id`
column, so finding "the existing booking for this draft" needs either a schema
change or a join through `appointment_files`, which finds nothing for the
majority of bookings that carry no files. It would also turn a 6-hour upload
authorization token into a booking-data read credential. BK-03's disabled
submit button covers the case. Revisit in BK-05, where a retry that *did*
commit could be told "check your confirmation email" instead of the misleading
"just taken".
