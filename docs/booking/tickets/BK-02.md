# BK-02 — Booking commit endpoint

**Status:** draft
**Phase:** P2 · **Tier:** Heavy · **Depends on:** BK-01

Heavy: a public endpoint that writes, holds insurance identifiers and CASL
consent, is the only real guard against double-booking, and creates rows that
cannot be silently un-created.

## Goal

Turn a completed booking form into an `appointments` row plus its claimed
uploads, rejecting anything the picker should never have offered and losing a
slot race gracefully.

## Step zero — Neon dev branch (blocking, do this first)

BK-01's verification seeded four rows into production behind an explicit flag.
BK-02's is a **concurrency hammer that creates real bookings in parallel**, and
that must not touch the live table.

Neon branching is copy-on-write, so a dev branch starts as an instant snapshot
of production's schema *and* data at branch time, on its own compute.

1. Authenticate — interactive, once. `neonctl` is not installed and no
   `NEON_API_KEY` is present, so this needs a human:
   `npx neonctl auth`
2. `npx neonctl branches create --project-id "$NEON_PROJECT_ID" --name dev`
   (`NEON_PROJECT_ID` is already in `.env.local`.)
3. `npx neonctl connection-string dev --project-id "$NEON_PROJECT_ID" --pooled`
4. Put that string in `.env` as **`DATABASE_URL_DEV`** — *not* in `.env.local`,
   which `vercel env pull` overwrites. `.env` is gitignored.
5. `npm run migrate` against the branch to confirm the ledger matches.

**Env split, from here on:**

| Variable | Points at | Used by |
| --- | --- | --- |
| `DATABASE_URL` | production | the app, and prod smoke tests behind `--allow-production` |
| `DATABASE_URL_DEV` | Neon dev branch | every writing verification script, by default |

Writing verification scripts must **refuse to run** when `DATABASE_URL_DEV` is
unset rather than silently falling back to production. Retrofit
`scripts/verify-availability-db.ts` to the same rule as part of this ticket:
default to the dev branch, keep `--allow-production` for deliberate prod smoke
tests only.

## Scope

1. `src/lib/booking-payload.ts` — a **pure** parser/validator: unknown JSON in,
   either a typed `BookingPayload` or a list of field errors out. No DB, no
   clock reads of its own. Verifiable without a database, like BK-01's split.
2. `src/pages/api/booking/create.ts` — `POST`, `prerender = false`,
   rate-limited per IP, plus a `BOOKING_CREATE_ENDPOINT` constant in
   `booking-config.ts` (trailing slash).
3. `scripts/verify-booking-payload.ts` — pure validation checks.
4. `scripts/verify-booking-commit.ts` — the DB-backed checks, including the
   concurrency hammer. Dev branch only.
5. Retrofit `verify-availability-db.ts` to the `DATABASE_URL_DEV` rule.

## Out of scope

- Confirmation email or SMS (BK-05/BK-06). This ticket only writes rows.
- The form UI (BK-03) and the confirmation page (BK-04).
- Admin manual entry (BK-08) — it shares the grid-snapping rule but is its own
  surface with its own auth.
- Rescheduling or cancelling an existing booking.

## Design notes

- **Revalidate every rule server-side through `isSlotBookable`** (exported by
  BK-01 for exactly this). Do not re-assemble the four exclusion rules by hand —
  that drift is what `booking-config.ts` exists to prevent. Check
  `isSlotOnGrid` *first* and separately: the submitted instant is untrusted and
  may not be a grid time at all, which `isSlotBookable` deliberately assumes.
- **Insert and file-claim must be one statement.** The Neon HTTP driver has no
  interactive transaction, and the claim needs the new `id`, so a two-call
  sequence can leave a booking whose photos are then deleted by the orphan cron
  24 hours later. Use a single CTE:

  ```sql
  WITH new_appt AS (
    INSERT INTO appointments (...) VALUES (...)
    ON CONFLICT (slot_start) WHERE status <> 'cancelled' DO NOTHING
    RETURNING id
  ), claimed AS (
    UPDATE appointment_files SET appointment_id = (SELECT id FROM new_appt)
    WHERE draft_id = $draft AND appointment_id IS NULL
      AND EXISTS (SELECT 1 FROM new_appt)
    RETURNING id
  )
  SELECT (SELECT id FROM new_appt) AS id, (SELECT COUNT(*) FROM claimed) AS files
  ```

  `ON CONFLICT ... WHERE status <> 'cancelled'` infers the partial unique index
  `appointments_slot_unique`. No row back means the slot went to someone else.
- **Claim files regardless of `upload_state`.** `onUploadCompleted` never fires
  on localhost, so every dev upload is stuck at `'pending'`; filtering on
  `'uploaded'` would silently drop real photos in dev and any production upload
  whose callback was slow.
- **Verify the draft token before claiming anything.** `draft_id` arriving from
  the client is not proof of ownership — without an HMAC check
  (`verifyDraftToken`) a caller could attach someone else's uploaded photos to
  their own booking. A booking with no draft token is valid; a booking with a
  bad one is a 400, not a silent no-file booking.
- **Distinguish the conflict from a real failure.** Map *only* a zero-row CTE
  result to 409. Do not treat any thrown error as "slot taken" — a connection
  failure would then read to the visitor as a lost race and to us as normal.
- Insurance identifiers are accepted only when `payment_route === 'insurance'`
  and are dropped otherwise, so a private-pay booking cannot carry a claim
  number picked up from a stale form state.
- `sms_consent_at` is set to now **only** when consent was given; absent
  consent it stays null. There is no boolean (CASL).
- `source` is `'web'`; `pipeline_stage` keeps its `'assessment'` default.

## Acceptance criteria

1. A valid payload for a free, in-window grid slot creates exactly one row and
   returns 201 with the appointment id and its formatted slot label.
2. Concurrent submissions for the same slot produce **exactly one** row: one
   201, the rest 409 with a "just taken" message. Verified under real parallel
   load, not reasoned about.
3. A slot that is off-grid, in the past, inside the 4-hour notice window, past
   the 14-day horizon, on a Friday, on a blackout date, or already booked is
   rejected with 409/422 and creates nothing.
4. Files for the submitted draft are attached to the new appointment,
   `upload_state` notwithstanding; files of *other* drafts are untouched.
5. A missing draft token books with zero files; a forged or expired one is a
   400 and creates nothing.
6. Insurance fields persist only for `payment_route = 'insurance'`; they are
   null for `'private'` even when submitted.
7. `sms_consent_at` is null unless consent was given, and a timestamp when it was.
8. Field-level validation errors return 422 with per-field messages and create
   nothing. Oversized or malformed JSON does not 500.
9. Rate limiting applies per IP and returns 429 with `Retry-After`.
10. A DB failure returns 500 and never a false success.
11. Nothing in any response body echoes `policy_number` or `claim_number`.

## Verification

- `npm run typecheck`, `npm run build`.
- `npm run verify:booking:payload` — pure: required fields, phone/email shapes,
  insurance conditionals, consent handling, oversized strings, unknown keys,
  and that no validator output carries insurance identifiers.
- `npm run verify:booking:commit` — **dev branch only**, refuses without
  `DATABASE_URL_DEV`:
  - the concurrency hammer: N ≥ 10 parallel POSTs at one slot, asserting one
    201, N−1 409s, and `SELECT COUNT(*) = 1` afterwards;
  - each rejection case from AC3, asserting zero rows created;
  - file claim including a `'pending'` file and a foreign draft left alone;
  - forged and expired draft tokens;
  - insurance-field stripping and consent handling straight from the row.
- Re-run `npm run verify:availability` and `verify:slots` for regression.

## Risks

- The partial unique index catches identical `slot_start` only. Everything here
  assumes grid-snapped 30-minute appointments; BK-08's manual entry must snap to
  the same grid or it can create an overlap this endpoint cannot see.
- A visitor double-submitting will hit their own booking's 409 and read it as
  "someone took my slot". See the open question below.
- The CTE claims files even if the client never finished uploading; those rows
  stay `'pending'` forever and the orphan cron ignores them once
  `appointment_id` is set. Acceptable — a stuck row is better than a deleted
  photo — but BK-07's admin view should not promise a file it cannot fetch.

## Assumptions log

- **201 rather than 200** for a created booking, with the id in the body.
- **422 for validation, 409 for slot conflicts**, so BK-03 can tell "fix your
  input" from "pick another time" without parsing prose.
- **No hold/reservation step.** Availability stays advisory, per BK-01; the
  index is the guard. A hold table would need its own expiry sweep for a race
  that is rare at five slots a day.

## Open questions

1. **Double-submit idempotency** — should a repeat submission carrying the same
   verified `draft_id` return the existing booking (200) instead of a 409? It
   is friendlier and cheap to add, but it means a draft token can read back a
   booking, so the token becomes a weak retrieval credential. Recommendation:
   **409 for now**, BK-03 disables the button on submit. Not a business
   decision — will settle it in plan review unless it turns out to affect the
   customer-facing message.
