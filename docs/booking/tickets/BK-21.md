# BK-21 — Internal email Reply-To: never point a human at noreply@

**Status:** draft
**Phase:** P6 · **Tier:** Light (email headers + verify assertions — gates
only; tier argument below) · **Depends on:** BK-16 landing first (it has
uncommitted changes in both files this ticket touches — sequencing only, no
functional dependency) · **Blocks:** nothing.

## The incident (2026-08-12)

Booking #25 (Jane Calhoun, phone-in style booking with **no email address**)
produced the internal "New booking" notice to `info@yegrestoration.ca`. Abdul
hit **Reply** on it to send the customer a DocuSeal link. Because the customer
gave no email, the notice carried no `Reply-To`, so the reply went to the
`From:` address — `noreply@yegrestoration.ca` — which is not a real mailbox.
Google bounced it: `550 5.1.1 Address does not exist`. The DocuSeal link went
nowhere, and only the bounce told anyone.

Two distinct holes, one shared root (`noreply@` is undeliverable):

1. **Mail-side (NOT this ticket — user action, records here for the ledger):**
   create `noreply@yegrestoration.ca` in Google Workspace as an alias or a
   routing rule delivering to `info@`. This is the only fix that covers ICS
   RSVPs — a calendar client that "Accepts/Declines" an invite mails the
   `ORGANIZER` address, i.e. `noreply@`, and no code change can redirect that
   (see the locked `ICS_ORGANIZER` note below).
2. **Code-side (this ticket):** no internal message should ever leave without
   a deliverable `Reply-To`. Today two do.

## Where Reply-To stands today (verified against source, 2026-08-12)

| Message | Reply-To | Site |
| --- | --- | --- |
| Customer confirmation | `BOOKING_EMAIL_REPLY_TO` (info@) | `booking-email.ts:278` |
| Customer cancellation/restore | `BOOKING_EMAIL_REPLY_TO` | `booking-admin-notify.ts:346` |
| Contact form | customer's email (required field) | `contact-message.ts:151` |
| Internal "New booking" | customer's email **only if given, else none** | `booking-email.ts:381` |
| Internal calendar notice | none, deliberately | `booking-admin-notify.ts:247` |

The last two are the holes. Both are `From: BOOKING_EMAIL_FROM` (noreply@), so
"none" means "replies bounce".

## Scope

1. `booking-email.ts:381` — internal "New booking" notice: keep the customer's
   email as Reply-To when present; fall back to `BOOKING_EMAIL_REPLY_TO` when
   absent:
   `{ replyTo: input.email ?? BOOKING_EMAIL_REPLY_TO }` (or the spread
   equivalent). A reply then lands in `info@` instead of bouncing — not the
   customer, but the customer is unreachable by email in that case by
   definition, and a visible landing beats a silent one only via the bounce.
2. `booking-admin-notify.ts:247` — internal calendar notice: add
   `replyTo: BOOKING_EMAIL_REPLY_TO` and rewrite the "No replyTo" comment to
   say why the fallback exists (a reply to a notice from `noreply@` bounces;
   pointing it at the office is harmless and self-explanatory).
3. `verify-booking-email.ts` — assert the internal notice's Reply-To both
   ways: customer email when given, `BOOKING_EMAIL_REPLY_TO` when not.
4. The verify script covering `planCalendarInvite` — assert
   `replyTo === BOOKING_EMAIL_REPLY_TO`.
5. Red-first on both new assertions (break the fallback in the production
   target, observe red, restore, log in the gate table).

## Proposed, needs user sign-off at approval

The notice's Email line for a no-email booking currently reads `Email: —`,
which is exactly what Abdul read past. A louder line — e.g.
`Email:       — (none — customer is NOT reachable by email; replies to this
message go to the office)` — would have prevented the incident outright.
Internal-facing copy, but copy nonetheless: **user decides at approval
whether it's in scope.**

## Locked — do not "fix" these while in here

- **`ICS_ORGANIZER` stays `noreply@yegrestoration.ca`.** Gmail matches a
  CANCEL against the organizer of the event it cancels, byte-identical across
  the lifecycle (`booking-config.ts:188-197`). Changing it strands every
  already-sent invite — their CANCELs would silently stop clearing calendars.
  The RSVP-bounce problem it causes is fixed mail-side (item 1 above), not
  here.
- **`BOOKING_EMAIL_FROM` stays as-is.** Resend sends on behalf of the verified
  domain; the From mailbox never needed to exist to *send*. Switching From to
  `info@` would make every automated mail look like a human wrote it.
