# BK-21 — Internal email Reply-To: never point a human at noreply@

**Status:** committed 2026-08-12 — all three `Reply-To` sites, all four copy
sites, five flipped verify assertions. Light tier, so gates only, no

**Phase:** P6 · **Tier:** Light (email headers + verify assertions — gates

## The incident (2026-08-12)

Booking #25 (Jane Calhoun, phone-in style booking with **no email address**)
produced the internal "New booking" notice to `info@yegrestoration.ca`. Abdul
hit **Reply** on it to send the customer a DocuSeal link. Because the customer
gave no email, the notice carried no `Reply-To`, so the reply went to the
`From:` address — `noreply@yegrestoration.ca` — which is not a real mailbox.
Google bounced it: `550 5.1.1 Address does not exist`. The DocuSeal link went
nowhere, and only the bounce told anyone.

Two kinds of hole, one shared root (`noreply@` is undeliverable):

1. **Mail-side (NOT this ticket — user action, records here for the ledger):**
   create `noreply@yegrestoration.ca` in Google Workspace as an alias or a
   routing rule delivering to `info@`. This is the only fix that covers ICS
   RSVPs — a calendar client that "Accepts/Declines" an invite mails the
   `ORGANIZER` address, i.e. `noreply@`, and no code change can redirect that
   (see the locked `ICS_ORGANIZER` note below).
2. **Code-side (this ticket):** no internal message should ever leave without
   a deliverable `Reply-To`. Today three do.

## Where Reply-To stands today (re-verified against source by the reviewer, 2026-08-12)

There are exactly three internal (`to: BOOKING_INTERNAL_TO`) messages in the
codebase — `grep -rn BOOKING_INTERNAL_TO src` — and all three are holes:

## Scope

The rule this ticket installs, stated once: **an internal message's `Reply-To`
is the writer's address when we have one, and `BOOKING_EMAIL_REPLY_TO`
otherwise. Never absent, never `''`.**

1. `booking-email.ts:381` — internal "New booking" notice: keep the customer's
   email as Reply-To when present; fall back to `BOOKING_EMAIL_REPLY_TO` when
   absent: `replyTo: input.email || BOOKING_EMAIL_REPLY_TO`. A reply then lands
   in `info@` instead of bouncing — not the customer, but the customer is
   unreachable by email in that case by definition, and a visible landing beats
   one that surfaces only as a bounce.
   **Use `||`, not `??`.** The typed shape is `string | null`, so `??` type-checks,
   but `''` is a live value elsewhere in this codebase's email plumbing
   (`contact-message.ts:70` admits `z.literal('')` before normalising) and an
   empty `replyTo` is a Resend API error — the exact hazard
   `verify-contact.ts:338` was written to pin. `||` collapses both to the
   office address; `??` would let `''` through.
2. `booking-admin-notify.ts:247` — internal calendar notice: add
   `replyTo: BOOKING_EMAIL_REPLY_TO` and rewrite the "No replyTo" comment
   (currently "There is nobody to reply to…") to say why the fallback exists:
   a reply to a notice from `noreply@` bounces, and pointing it at the office
   is harmless. `BOOKING_EMAIL_REPLY_TO` is already imported in this file
   (used at :347).
3. `contact-message.ts:151` — internal contact-form notice: same one-line fix,
   `replyTo: message.email || BOOKING_EMAIL_REPLY_TO`. Add
   `BOOKING_EMAIL_REPLY_TO` to the existing `./booking-config` import at :41
   (`BOOKING_EMAIL_FROM, BOOKING_INTERNAL_TO` already come from there, and
   `booking-config.ts:166` is where the constant lives — no new module edge,
   so the file stays `tsx`-reachable for its verify script).

Verification — note that **all three of these are existing assertions that
must be flipped, not new blocks bolted alongside.** Leaving the old ones in
place contradicts the new behaviour:

4. `scripts/verify-booking-email.ts:309` — currently
   `check(plan.internal.replyTo === undefined, 'with no reply-to, since there

   message" block. Flip to `=== BOOKING_EMAIL_REPLY_TO` with a message naming
   the fallback. Line 179 (`internal.replyTo === INSURANCE.email`) already
   covers the with-email arm and stays as is — together they are the both-ways
   assertion.
5. `scripts/verify-booking-ics.ts:593` — currently

6. `scripts/verify-contact.ts:337` — currently `anonymous.replyTo ===

7. Red-first. Three production-target failure modes, one row each in the gate

## The loud Email line — APPROVED by the user 2026-08-12, in scope, both notices

The Reply-To fix stops the bounce; it does not tell the office the customer is
unreachable. `Email: —` is what Abdul read past. The dash becomes an explicit
warning wherever an internal notice reports a missing address:

    Email:       — (none — customer is NOT reachable by email; replies to this
                 message go to the office)

Applies to **both** internal notices and to **both** the text and HTML parts of
each — four sites. It is internal-facing copy; no customer ever sees it. Exact
wording is the implementer's to settle within that meaning (line-wrapping in
the text part especially — keep the existing column alignment), but the three
facts must all survive: *no address given*, *customer not reachable by email*,
*replies land at the office*.

8. `booking-email.ts:313` — the `or()` helper returns a bare `dash` for a null
   email. Do **not** change `or()` itself; it feeds Insurer/Policy/Claim rows
   too, where a dash is correct. Special-case the Email row only, at both
   `:320` (HTML, via `row('Email', …)`) and `:359` (text). Escape the HTML
   variant like every other row does.
9. `contact-message.ts:158` (HTML) and `:171` (text) — same treatment for the
   contact notice's `'—'` literals. Say "visitor" rather than "customer" if
   that reads better in that file's voice; the three facts are what matter.
10. Verify, again flipping assertions rather than adding beside them:
    `verify-booking-email.ts:310` (`plan.internal.text.includes('—')`,
    "and the email field reads as absent") and `verify-contact.ts:339`
    (`anonymous.text.includes('Email:   —')`) both currently assert only the
    dash — a substring that survives the new copy unchanged, so they would
    stay green against a half-done change and are worthless as written.
    Replace each with an assertion on the warning itself, in **both** parts,
    and assert the with-email arm does **not** carry it. One further
    red-observed row: (d) the no-email warning line.

## Locked — do not "fix" these while in here

- **`ICS_ORGANIZER` stays `noreply@yegrestoration.ca`.** Gmail matches a
  CANCEL against the organizer of the event it cancels, byte-identical across
  the lifecycle (`booking-config.ts:188-197`). Changing it strands every
  already-sent invite — their CANCELs would silently stop clearing calendars.
  The RSVP-bounce problem it causes is fixed mail-side (item 1 above), not
  here.
- **`BOOKING_EMAIL_FROM` stays as-is.** Resend sends on behalf of the verified
  domain; the From mailbox never needed to exist to *send*. Switching From to
  `info@` would make every automated mail look like a human wrote it.

## Assumptions log

- **Widening to `contact-message.ts` (reviewer, 2026-08-12, settled without
  the user).** Found while verifying the draft's table. It is the same defect,
  the same one-line fix, and the same 550 outcome; the contact form is if
  anything the *likelier* door, since its email field has always been optional
  whereas the booking form's is about to become mandatory (P7 / BK-22). Not
  filed to Known traps as an out-of-scope defect because it is not
  out-of-scope — it is the third instance of precisely the defect this ticket
  exists to close, and closing two of three would leave the ticket's own rule
  false the day it lands.
- **Wording settled (implementer, within the meaning the user approved).** Both
  notices read `— (none given — customer|visitor is NOT reachable by email;
  replies to this message go to the office)`, wrapped in the text parts to the
  existing label gutter (13 columns in `booking-email.ts`, 9 in
  `contact-message.ts` — rendered and eyeballed, alignment holds). It lives as a
  pair of module constants per file (`NO_EMAIL_NOTICE`, `NO_EMAIL_NOTICE_TEXT`)
  rather than four inline literals, so the HTML and text parts cannot drift into
  saying different things. The verify scripts assert on three literal fragments
  — `none given`, `NOT reachable by email`, `replies to this message go to the
  office` — deliberately NOT by importing the constants, which would make the
  assertion tautological and let a reworded line pass while dropping a fact.
  Fragments are chosen to contain no character `escapeHtml` touches, so one
  needle works against both parts.
- **`verify-contact.ts` imports `BOOKING_EMAIL_REPLY_TO` dynamically**
  (implementer). `booking-config.ts` never reaches `getDb`, so a static import
  would be safe today — but that file's stated rule is that every *value* import
  happens after the `DATABASE_URL` swap, and an exception is a thing someone has
  to re-audit later. Noted at the import.
- Bounce cause confirmed from the delivery-failure notice (550 5.1.1 from
  googlemail.com) plus source reading; not reproduced by sending mail.
- Superseded: the draft's "depends on BK-16" sequencing note. BK-16 committed
  as `1162b9d`; the tree is clean and both files are at their post-BK-16 state.
