## The premise this ticket corrected first

The request said *"the homepage booking section currently has no button."* **It
has one, and always has.** `ContactSection.astro` renders a full-width primary
CTA to `/book/`, live on production. Flagged before implementation; **user
decision 2026-08-16: relabel it, and add the teaser as its own ticket.**

So the scope is two things, neither of which is "add a button":

1. **The label.** `Book Your Assessment` → `See available times`. The button
   leads to a page whose first screen is a calendar, so the new label is both
   more accurate and a lower-commitment ask — the visitor is one click from
   looking, not from booking. It sits directly under a box quoting $399/$699/
   $1,199, which is exactly where "Book" is the heavier word.
2. **The teaser.** One line above it: `Next opening: Mon, Aug 17 · 2:30 p.m.`

## Explicitly not built

**The booking wizard does not go on the homepage.** One door per intent is the
BK-10 cutover's whole point and a second copy of the picker would be the second
door. The teaser reads the calendar and links nowhere.

## Assumptions log

1. **`slot.label` is rendered verbatim, so the teaser names the date as well as
   the weekday** — `Next opening: Mon, Aug 17 · 2:30 p.m.`, not the request's
   illustrative `Next opening: Mon, 2:30 p.m.` Two reasons, and the second is
   the real one: the window is 15 days, so a bare weekday is ambiguous between
   two Mondays; and `label` is built server-side by `formatSlot` in
   America/Edmonton. Reformatting it in the browser would read the VISITOR'S
   timezone, so someone in Vancouver would be told 1:30 and shown 2:30 one
   click later. Rendering it verbatim also means the homepage, the picker, the
   confirmation email and the admin panel all print one string built in one
   place.
2. **A failure renders nothing at all** — not an error, not "call us", not a
   retry. The CTA underneath is the page's job and is already there; an error
   message beside a working button only makes the button look broken.
3. **`booking_availability_error` is deliberately NOT fired from here.** It is
   the booking page's funnel diagnostic, and the ROADMAP already records that
   it counts attempts rather than visitors. Firing it from a homepage where
   nobody asked for a calendar would corrupt the one number the client uses to
   ask "did the new filter cost me jobs".
4. **The 60-second cache holds the teaser STRING, never the slot list**, and it
   never feeds the picker. The availability endpoint is `no-store` on purpose,
   because a stale calendar offers slots that are gone. The worst this cache
   can do is name an opening taken a minute ago, after which `/book/` fetches
   fresh and shows the truth. Caching slots would turn that into a booking
   attempt on a dead slot.
5. **`booking-preview.ts` is BK-28's foundation, not a competitor to it.**
   BK-28 owns the fuller preview — several slots, each deep-linked with
   `?slot=`, plus the `applyPrefill` hardening a query parameter feeding the
   public write path needs. That ticket should grow this file rather than start
   another. Recorded here **and** in the module header, because BK-28 is
   drafted and its implementer will not read this ticket.

Both fixture sets are built from the **real** `computeAvailability` rather than
hand-typed payloads — including the fully-booked case, which is generated by
booking out every instant the real computation offers. A typed-out fixture
keeps passing after the endpoint's shape changes underneath it, and shape is
most of what this module reads.

## A note on the live check, and one thing it nearly hid

No `client:visible` island hydrated on the first attempt — including the
pre-existing `VideoReel` and `LocationMap`. A single programmatic
`scrollIntoView()` does not drive `IntersectionObserver` in headless Chromium;
an incremental window scroll does, and all six islands then hydrated together.
**Worth writing down because the first reading was "my island is broken", and
the thing that disproved it was checking the islands that already worked.**

Separately, the first cache check appeared to fail: the sentinel did not
render. The cause was that navigating to `/#contact` from `/` is a same-document
navigation, so no reload happened and the island still held its earlier state.
A real load (`/?reload=1`) showed the sentinel. Both of these are measurement
faults, not defects, and both would have been reported as defects one step
earlier.
