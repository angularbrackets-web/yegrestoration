# BK-37 — Upload link: copy, share, and a real expiry

**Status:** implemented 2026-08-16 — gates green, 2 red rows, six behaviours
driven against the real bundled script in Chromium. Light tier, no reviews by
design.
**Phase:** P10 · **Tier:** Light (admin-only UI; no schema, no new endpoint, no
change to the token format or to what it authorizes) · **Depends on:** BK-34a
(shipped) · **Blocks:** nothing.
**Deploy:** 1.5. **Migration:** none.

**Until the Twilio number clears, the office agent's phone IS the SMS gateway.**
BK-34a made the link; BK-34b will send it automatically; in between, the only
delivery mechanism is an agent getting the link out of the admin page and into
a text message. It was a readonly input with `onfocus="this.select()"` and
nothing else.

## Scope

1. **Copy** button — `navigator.clipboard.writeText`.
2. **Share** button — `navigator.share`, **added by script only when the API is
   really present**, so the OS share sheet (Messages, WhatsApp, mail) is one tap
   on the agent's phone.
3. **WhatsApp** — a plain `wa.me` anchor, in the markup, no JS needed. The
   desktop fallback, alongside Copy.
4. **The link's expiry, stated absolutely** — `issueAppointmentUploadToken` now
   returns `expiresAt`, and the page renders it through `formatAdminTimestamp`.

## The two things this ticket refused to build

Both were in the request as written, and both are false against BK-34a's
shipped design. Flagged to the user before implementation; **decided
2026-08-16: state the absolute expiry, no Regenerate button.**

- **"Expires in 43h" cannot be shown.** `[id].astro` mints a fresh token on
  **every page view** — deliberate, and documented in the frontmatter comment
  BK-34a wrote. The countdown would therefore read 72h every single time and
  tell the office nothing about the link they texted on Tuesday. The absolute
  deadline is the number that is actually useful when pasted into a message.
- **"Regenerate — old link invalidated" is not a thing this system can do.**
  Appointment tokens are stateless HMACs (`draft-token.ts`); there is no
  revocation and no server-side record to revoke against. Opening this page
  does not kill the link already in a customer's messages. A button claiming
  otherwise would leave the office believing a live link was dead — worse than
  no button. Real revocation is possible (a per-appointment token version
  column, checked by the verifier) and was offered; it is a migration plus a
  change to shipped security code, and the user chose not to spend that here.

The page says both of these out loud rather than leaving them to be inferred:
*"A fresh link is made each time you open this page; links you have already
sent keep working until their own 72 hours are up."*

## Assumptions log

1. **Share is added by script, not rendered by the server.** The server cannot
   know whether a phone or a desk machine is asking. A server-rendered Share
   button that does nothing on desktop is worse than no button — the agent taps
   it, nothing happens, and they stop trusting the whole row.
2. **A dismissed share sheet is not an error.** `navigator.share` rejects with
   `AbortError` when the user backs out, which is the single most common
   outcome. Reporting it would put a warning on screen every time the agent
   changes their mind, and a button that cries wolf gets reported as broken.
3. **No clipboard API is a degraded path, not a dead end.** If the office ever
   reaches the panel over plain HTTP on a LAN, `navigator.clipboard` is
   undefined. The button then selects the field and says so, leaving one
   keystroke to go rather than failing silently.
4. **The share message is fixed prose, not personalised.** It names no
   customer, no address, no policy number — the same discipline `/upload/`
   itself follows. The agent can edit it in their own messaging app.

### The behaviour check, and why it is not a hand-written copy

The admin panel's cookie is `Secure`, so the page cannot be logged into over
`http://localhost` and cannot be driven end to end locally. Instead, both
halves of the fixture are **lifted from the build output**:

- the markup is sliced out of `.vercel/output/_functions/chunks/_id_*.mjs` and
  its interpolations resolved, with a hard failure if any `${` survives;
- the script is the **real inlined bundle**, extracted from the manifest in
  `entry.mjs` (Astro inlines this one rather than emitting a file).

Retyping either would have made this a test of the copy — the "source pin
satisfied by the import line" family the ROADMAP already records twice.

| # | Case | Result |
| --- | --- | --- |
| 1 | Copy, happy path | wrote **exactly** the URL, positive status |
| 2 | Copy, `navigator.clipboard` undefined | field focused and selected, warning-toned message |
| 3 | Share sheet dismissed (`AbortError`) | **no message** — correctly silent |
| 4 | Share genuinely failing (`TypeError`) | warning-toned message |
| 5 | Share payload | `{ text, url }`, both present |
| 6 | No Web Share API at page load | **Share button absent**; Copy + WhatsApp remain |

Case 6 loads a second fixture that deletes `Navigator.prototype.share` in a
classic script — which runs before the deferred module — so it is the real
absent-API path rather than a simulation of it.

### Red-observed

| # | Break | Assertion that went red |
| --- | --- | --- |
| k | `expiresAt` computed with a doubled TTL at the mint site | the stated expiry has not yet passed one second before it |
| l | `expiresAt` stamped from `Date.now()` instead of the signed `issuedAt` | the stated expiry has not yet passed one second before it |

Both assertions are written against `verifyAppointmentUploadToken` itself, not
against a recomputation of `APPOINTMENT_UPLOAD_TTL_HOURS`. A recomputation is
the second copy the assertion exists to forbid: it would agree with a drifted
`expiresAt` for exactly the reason the drift was wrong. **This is a deadline the
office reads out to a customer**, so "close to" the verifier is not good enough.

## Follow-up recorded, not fixed

`wa.me` opens WhatsApp Web on a desk machine, which requires the agent to have
WhatsApp Web paired. There is no way to detect that from the page, and the
button is a fallback beside Copy rather than the primary path, so it is
acceptable — noted so the next person does not treat a "WhatsApp did nothing"
report as a bug in this ticket.
