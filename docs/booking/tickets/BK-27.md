# BK-27 — Assessment fee terms: display + required acknowledgment on the public form

**Status:** draft 2026-08-13 — designed in a planning session (user approved the
plan); awaiting plan review by a fresh agent, then approval. Implementation is
assigned to a new session (user decision 2026-08-13).
**Phase:** P8 · **Tier:** Reviewed (public write path: new 422 cause on
`/api/booking/create/`; migration; customer-facing email) · **Depends on:**
nothing — additive over BK-22 (`2adc752`) · **Blocks:** nothing hard, but land
**before BK-23** (see Sequencing) and before BK-28 (shared files, clean diffs
only).

## Why

Client decision, 2026-08-13 (via the user): new conditions for booking an
assessment —

- **Free when the customer proceeds with us.**
- Otherwise: **$699** for a cause-of-loss report and estimate, or **up to
  $1,200** for drafting a sketch/diagram for insurance purposes, including the
  loss report.

User decisions (same day): the terms appear on the **homepage booking section
AND on `/book/`**, with a **required "I understand the assessment terms"
acknowledgment checkbox** before submitting, **recorded in the DB** and
**echoed in the confirmation email**. Admin entry is exempt (same philosophy as
BK-22 — the office books over the phone and explains terms verbally).

Same filtering intent as P7: a visitor who has read "not free if you walk away"
and ticked a box is a better-qualified lead.

## Design decisions

- **Wire/error field name `terms_ack`** (boolean, mirrors `sms_consent`).
  **DB column `terms_acked_at TIMESTAMPTZ`** — the timestamp *is* the
  acknowledgment; no boolean column (consistent with the Locked "no
  `sms_consent` boolean" rule). 422 error field: `terms_ack`. `FIELD_STEPS`
  entry: `terms_ack: 3`.
- **Copy lives in `src/lib/booking-copy.ts`** (the `HAVE_READY_ITEMS` /
  `CANCEL_LINE` home): env-free, importable by the island, `.astro` files, the
  email builder, and `tsx` verify scripts alike. Exports: `FEE_TERMS_HEADING`,
  `FEE_TERMS_INTRO` ("The assessment is free when you proceed with us.
  Otherwise:"), `FEE_TERMS_ITEMS: readonly string[]` (the $699 and
  up-to-$1,200 lines), `FEE_TERMS_ACK_LABEL`. **All wording is placeholder
  pending client sign-off** — this is customer-visible *pricing* language, so
  it goes past the client **before** launch, not after (stricter than the
  standing "client edits later" rule; same carve-out BK-26's checklist has).
- **The checkbox lives on step 3**, directly under a rendered terms box,
  beside the existing SMS-consent checkbox. The acknowledgment must be
  *adjacent* to the terms it acknowledges. Unlike SMS consent, this one
  **blocks** submission.
- `termsAck: boolean` joins `FormValues` (like `smsConsent`), not a new
  `validateStep` parameter — BK-22's `attachmentCount` was a parameter only
  because attachments live outside `FormValues`.
- **Admin exemption rides the existing `entry: 'public' | 'admin'`
  discriminator** in `parseBookingPayload` — the BK-22 seam. `parseAdminEntry`
  needs **no change**. `insertBooking` writes `terms_acked_at` from the shared
  path, so admin rows get NULL with no second statement.

## Changes

1. **`scripts/migrations/005-assessment-terms.ts`** (new) + register in
   `scripts/migrations/index.ts`. Single statement:
   `ALTER TABLE appointments ADD COLUMN IF NOT EXISTS terms_acked_at
   TIMESTAMPTZ`. One statement, `IF NOT EXISTS`, ledger row last — safe under
   the Neon HTTP driver's non-atomicity. *(005 is next-free today; whichever
   of this and BK-23's index migration lands first takes 005 — noted in both
   tickets.)*
2. **`src/lib/booking-copy.ts`** — the four fee-terms exports.
3. **`src/lib/booking-payload.ts`** — `BookingPayload.termsAcked: boolean`;
   reject non-boolean `terms_ack` the way `sms_consent` is rejected; then
   `if (options.entry === 'public' && raw.terms_ack !== true)
   add('terms_ack', 'Please confirm you understand the assessment terms.')`.
4. **`src/lib/booking-commit.ts`** — `insertBooking` adds `terms_acked_at` to
   the column list, `${p.termsAcked ? now.toISOString() : null}` to VALUES —
   byte-parallel to `sms_consent_at`.
5. **`src/lib/booking-form.ts`** — `FormValues.termsAck` + `emptyFormValues()`
   default `false`; step-3 check in `validateStep` (after the `files` check so
   error order matches page order); `FIELD_STEPS.terms_ack = 3` (without it a
   server 422 degrades to the generic form message — the exact trap BK-22's
   `files` comment documents); `assembleBookingPayload` always sends
   `terms_ack: values.termsAck === true`.
6. **`src/components/BookingForm.svelte`** — step 3: terms box (heading +
   intro + the two priced items from `booking-copy.ts`) above a required
   checkbox bound to `values.termsAck`, inline error slot keyed to
   `errors.terms_ack`, beside the SMS-consent label (~line 871).
7. **`src/pages/book.astro`** — the header's "Free assessment … no obligation"
   is now only conditionally true. Reword ("Free when you proceed with us")
   and add a compact terms line/box built from the constants.
8. **`src/sections/ContactSection.astro`** — CTA-card branch
   (`showForm={false}`) **only** (`/contact/` renders the form branch and must
   not gain the block): same rewording + terms block from the constants.
   Never retype the digits — the (780) 244-4747 Known trap is precisely about
   hand-typed facts in copy.
9. **`src/lib/booking-email.ts`** — `customerConfirmation` gains an
   "Assessment terms" section (heading + intro + both items), **HTML and text
   bodies both**, from the constants. `BookingNotificationInput` needs no new
   field — the echo is static copy. Optional (implementer's call): a
   `Terms acknowledged` row in the internal notification.
10. **Should-fix, small:** show `terms_acked_at` on
    `src/pages/admin/appointments/[id].astro` beside the SMS-consent display;

## Sequencing vs BK-23

- **Migration conflict: none.** BK-23 rewrites the `status` CHECK and
  recreates `appointments_slot_unique`; this ticket is a pure additive
  `ADD COLUMN`. Only the migration *number* is contended.
- **`insertBooking`:** this ticket does not touch the `WHERE status <>
  'cancelled'` predicate BK-23 must change; diffs are in different parts of
  the same statement. Land BK-27 first and BK-23 rebases trivially.
- **Confirmation-email collision: real — the reason to land BK-27 first.**
  BK-23 splits "You're booked" into (a) application-received at submission and
  (b) confirmation at approval. The fee-terms echo is an *at-submission*
  artifact — it documents what the customer agreed to when they applied.
  **Handoff to BK-23: when the emails split, move (or duplicate) the fee-terms
  echo into the received-your-info email; keeping it in the approval
  confirmation as well is recommended but is BK-23's call.**
- Like BK-22, this filters immediately while confirmation is still instant.

## Open questions for the client (log answers in Assumptions)

1. **Exact wording** of the terms and the ack label — placeholder until
   client sign-off, required before launch.
2. **GST** — are $699 / $1,200 plus GST? The box should say which; an
   ambiguous price term is worse than none.
3. **Dollar figures inline in the ack label, or in the adjacent box?**
   Recommendation: figures in the box, label references it ("I understand the
   assessment terms above") — the box sits immediately above the checkbox
   regardless.
4. **Is "up to $1,200" inclusive of the $699 item?** The stated wording
   ("including the loss report") suggests yes; the copy must not read as
   $699 + $1,200.
5. **Insurance route** — do the same terms apply when an insurer pays?
   Presumed yes (one message for all); confirm.
6. **Other "free assessment" claims** on the site are now conditionally true.
   In scope here: the two booking surfaces. Out of scope: run a
   `grep -ri "free assessment" src/` inventory and record the rest as a Known
   trap / Light follow-up.
