# BK-43 — Resend idempotency prefix must carry the message type

**Status:** **REVIEWED 2026-08-18** — implementation review returned 1 blocker,
2 should-fix, 1 nit. All fixed. The production fix was found complete and
correct on every path; the blocker was in the assertion protecting it. Gates
green.
**Phase:** P9 · **Tier:** Reviewed (silent customer-facing message loss) ·
**Depends on:** nothing · **Blocks:** BK-31, BK-23, BK-32, BK-36 — every new
email in Deploy 2.
**Deploy:** 2, **first ticket, before BK-31**. **Migration:** none.

Split out of BK-23 on 2026-08-18. It was BK-23's item, but the build order needs
it committed *before* BK-31 while BK-23 lands *after* — one ticket spanning two
commits either side of another ticket is exactly what one-ticket-per-commit
exists to prevent.

## The defect

`booking-notify.ts:186` and `:244` both build the sender with a **fixed
per-booking prefix**:

```ts
send = createResendSender(apiKey, `booking-${plan.bookingId}`);
```

and `createResendSender` sends `Idempotency-Key: ${keyPrefix}:${message.to}`
(`:117`).

Under the flow that exists today this is correct: one booking sends the customer
exactly one message, so a retry collapsing into the first send is the whole
point of the key.

**Under P9 one booking sends the same address up to five messages** —
request-received, payment link, payment reminder, confirmation, and
decline-or-expiry — every one of them carrying the byte-identical key
`booking-<id>:<their@email>`. Resend collapses every message after the first
into a duplicate of the first **and returns success**. The customer receives
"we have your request" four more times, never sees the payment link, never gets
confirmed, and **nothing in any log says so**: the send reports `ok`, the stamp
records `sent`, and the admin panel shows a notified booking.

It is invisible in dev as well as in production — `BOOKING_NOTIFY_DISABLED`
mutes the sender entirely on every local and verify path, so no smoke test
reaches Resend's dedupe at all.

This is the same defect class BK-16 already fixed on the calendar side.
`inviteIdempotencyPrefix(id, kind, now)` (`booking-ics.ts:156`) exists precisely
because a fixed prefix collapsed CANCEL into REQUEST. The notification path
needs the same treatment and did not get it.

## Scope

1. **`BookingMessageType`** — a closed union naming the lifecycle transition a
   plan's messages belong to: `'request' | 'payment-link' | 'payment-reminder' |
   'confirmed' | 'declined' | 'expired'`. Declared in full now, including the
   types BK-23 and BK-32 will be the first to send, so those tickets add a send
   rather than also having to widen a type.

2. **`NotificationPlan` gains `messageType`.** Required, not optional — the
   defect is a thing someone forgets, so the type system has to ask. Every
   existing construction site sets `'confirmed'`, which is what today's single
   customer message is.

3. **`notifyIdempotencyPrefix(bookingId, type)`** → `booking-<id>-<type>`, an
   exported pure function beside `inviteIdempotencyPrefix` in spirit, and the
   *only* place the prefix is spelled. Both send sites call it. **No template
   literal may build a prefix again** — that is what a source-level pin asserts.

4. **The audience is deliberately NOT in the prefix**, matching
   `inviteIdempotencyPrefix`'s documented reasoning: `createResendSender`
   appends `:<to>`, and the customer and office copies of one transition go to
   different addresses. See the nit below for the one case where that is not
   true.

5. **Make the key observable through the existing seam.** `NotifyDeps.send`
   becomes `(message: Message, keyPrefix: string | null) => Promise<SendResult>`
   and `deliver` passes the prefix through. Existing injected fakes take only
   `(m)` and keep typechecking — a function of fewer parameters is assignable —
   so no verify script changes shape, but a new one can now *read the key the
   real sender would have used*. Without this the fix is verifiable only by
   reading the source, which is how the defect survived review the first time.

   The real path is unchanged: `createResendSender` still bakes the prefix into
   its closure and ignores the second argument.

## Out of scope

- Any new message. BK-23 and BK-32 send them; this ticket only makes it
  possible for them to arrive.
- `sendCalendarInvite`, which is already correct.
- `createResendSender`'s signature — `api/contact.ts` and `api/admin/reply.ts`
  pass `null` and must keep working untouched.

## Known nit, recorded not fixed

If a customer's email address is *exactly* `BOOKING_INTERNAL_TO`, the customer
and office copies of one transition collapse into each other, because neither
the prefix nor the `:<to>` suffix distinguishes them. This is pre-existing, it
applies identically to `sendCalendarInvite`, and it requires the business to
book itself. Fixing it means putting the audience in both prefixes and
reversing BK-16's documented decision, which is not this ticket's call to make.

## Risk areas for the reviewer

- A prefix rebuilt as a template literal anywhere is the defect returning.
- `deps.send`'s widened signature must not change what the real sender does.
- The five existing `verify-booking-email.ts` injection sites must stay green
  without being edited to fit.

## Acceptance criteria

1. `notifyIdempotencyPrefix` returns a different string for every member of
   `BookingMessageType`, and the same string for the same `(id, type)`.
2. **Two different message types to the same recipient both deliver.** Driven
   through `sendBookingNotifications` with an injected sender that records
   `(keyPrefix, to)`: two plans differing only in `messageType` produce two
   different keys for one address. *(The user's explicit requirement,
   2026-08-18.)*
3. A retry of the *same* transition still collapses — same `(id, type, to)`
   yields the same key.
4. `src/lib/booking-notify.ts` contains no `` `booking-${ ``-style prefix
   literal; the only prefix source is `notifyIdempotencyPrefix`. Source-level
   pin, the pattern `verify-booking-ics.ts` already uses for the attachment
   whitelist.
5. `createResendSender(apiKey, null)` still passes no header at all, so the
   contact form and lead reply are unaffected.
6. Existing `verify:booking:email` passes unmodified.

## Implementation review — findings and what was done

Reviewer was a fresh agent given only this ticket, the diff for `e476798` and
re-run gate output. It found the **production fix complete and correct** — all
four prefix-constructing senders go through a builder, both `null`-passing call
sites are untouched, `new Resend(` and `.emails.send(` exist nowhere else in
`src/`, the widened `NotifyDeps.send` changes nothing at runtime, and all six
union members match what each route actually sends. The blocker is in the
verification.

### The blocker — the AC4 source pin did not implement AC4

The pin was:

```ts
!/createResendSender\([^)]*`booking-\$\{/.test(notifySrc)
```

which only matches a template literal **inside** the `createResendSender(...)`
argument list, with no intervening `)`. But this ticket restructured every
sender to

```ts
const keyPrefix = notifyIdempotencyPrefix(...);
send = createResendSender(apiKey, keyPrefix);
```

so the natural regression — editing the `const keyPrefix =` line — never appears
between those parens.

**The reviewer restored `sendCustomerConfirmation` (`booking-notify.ts:283`) to
the exact pre-BK-43 defect and `verify:booking:email` printed green**, this
ticket's whole BK-43 block included. Three things had to fail together:

1. the regex did not match the restructured shape;
2. the backup pin counted `notifyIdempotencyPrefix(` occurrences `>= 3`, but
   matched **5** at HEAD — a doc-comment mention and the declaration itself
   among them — so two of the three real call sites could have been deleted with
   it still green;
3. nothing drives `sendCustomerConfirmation` or `sendCustomerMessage` through a
   key-observing fake, so no behavioural check reaches them either.

Real coverage was **one of the four senders**. The identical break at `:222` did
go red, which is what made the red table look convincing — and why red row 4's
claim that it was "the only one that would otherwise pass every behavioural
check" was true of the inline spelling it named and false of the pin's reach.

**This is the "assertion that cannot fail" family with a new spelling.** The six
recorded instances are all about an assertion moving with its target. This one
is narrower and nastier: an assertion that tests a shape the production code no
longer has. **The lesson to add: a source pin written against code you are about
to restructure must be re-read after the restructure**, because it will keep
passing — that is what a pin does — and its passing now means nothing.

Fixed by pinning the **count** rather than a call-site spelling:

- the prefix shape ``` `booking-${` ``` may appear **exactly once** in the file,
  in `notifyIdempotencyPrefix`'s own return. Any second occurrence is a site
  building its own, wherever it sits;
- there are exactly **four** `= createResendSender(` call sites and every one
  passes the `keyPrefix` variable, never an inline expression;
- there are exactly **four** `const keyPrefix =` assignments and every one comes
  from `notifyIdempotencyPrefix` or `inviteIdempotencyPrefix`.

### Reach — recorded, not fixed

The pin reads **only** `src/lib/booking-notify.ts`. A prefix rebuilt in another
file is invisible to it, and `verify-cutover.ts:249` pins `new Resend(` /
`.emails.send(` but not `createResendSender(`, so a BK-32 payment webhook
importing the sender and passing its own literal would pass every gate in the
repo. Not fixed here because BK-32 is the ticket that first creates such a file;
flagged on BK-32 rather than guessed at now.

### Should-fix, both fixed — two comments that stated the opposite of the new invariant

`booking-notify.ts:344` still said `sendBookingNotifications` and
`sendCustomerConfirmation` "both key idempotency on `booking-<id>`, which is
exactly right for a notification" — false, and false in the direction of the
defect: the file's own explanation of why invites carry a transition told the
reader the notification path deliberately does not. `booking-admin-notify.ts:283`
carried the same stale claim.

The second one is attached to a **live hazard BK-43 does not close**: the admin
Resend button builds its plan through `planForAppointment`, whose `messageType`
defaults to `'confirmed'` — byte-identical to the key the payment-time
confirmation will use. Customer says "I never got my confirmation", office
clicks Resend inside the dedupe window, nothing is delivered, flash reads
"sent". Genuinely outside this ticket's scope, so per the out-of-scope-defect
rule it is now in **ROADMAP's Known traps with severity medium and owner
BK-32**, not left in a code comment that had also gone stale.

### Nit — accepted, not changed

AC5's pin is a spelling-exact regex over the ternary, so a benign reformat goes
red with no behaviour change. Low: it is the only affordable check without a
network, and it did go red for the right break.

### The recorded nit (customer email == `BOOKING_INTERNAL_TO`) — reasoning upheld

The reviewer checked whether prepay raises its severity and found it does not:
the collision stays confined to the customer and office copies of one plan, and
the only path P9 adds messages through (`sendCustomerMessage`) sends no office
copy at all. Recording rather than fixing is still right.

## Implementation notes

- `BookingMessageType` and the required `NotificationPlan.messageType` are in
  `booking-email.ts`, beside the plan they belong to; the prefix builder is in
  `booking-notify.ts` beside the sender that consumes it.
- Making `messageType` **required on `BookingNotificationInput`** rather than
  defaulted did the work it was supposed to: `tsc` named all seven construction
  sites, four of them in verify scripts. Every one is `'confirmed'` today, which
  is what the single existing customer message is.
- `planForPayload` / `planForAppointment` take it as an *optional trailing*
  parameter defaulting to `'confirmed'`. They are named builders for one message
  today and BK-23 rewrites them; a required parameter after their existing
  optional `filesAttached` would have been churn for no safety.
- `sendCalendarInvite` was already correct but now computes its prefix before
  the sender and forwards it through `deliver`, so all three senders report the
  key through the same seam rather than two of three.
- **AC6 needs one word of honesty:** `verify:booking:email` passes with a
  one-line change, not unmodified — `INSURANCE` had to name a `messageType`
  because the type now requires it. No injection site changed shape, which is
  what the criterion was protecting.
