## The change

### A · `src/lib/booking-review.ts` — one exported rule for an absent amount

New export, beside `parseAmountCents`, which is where the admin amount rules
already live:

```ts
export function approvalAmountCents(raw: unknown): number | null {
  if (raw === null || raw === undefined || raw === '') return 0;
  return parseAmountCents(raw);
}
```

**Why a lib function rather than an inline `0`.** An inline change would be one
token and would be pinnable only by regexing the source of an API route — the
negative-pin family this project has been bitten by twice. Extracting it makes
the rule **behaviourally testable**: `approvalAmountCents('') === 0` is an
assertion about what the system does, not about how it is spelled. It also
collapses base and travel onto one rule, which they now share — the travel field
already read `travelRaw === null || travelRaw === '' ? 0 : parseAmountCents(…)`.

The docstring must state the inversion explicitly, because the comment it
replaces argued the opposite: **an absent amount is $0, never a guess.**

### B · `review.ts` — both fields through the one rule, and the re-entry point deleted

`:226-228` becomes:

```ts
const baseCents = approvalAmountCents(baseRaw);
const travelCents = approvalAmountCents(travelRaw);
if (baseCents === null) return { error: 'amount' };
```

`:229-230`'s error returns are **unchanged and load-bearing** —
`approvalAmountCents` returns `number | null` and A5/A6 depend on it. *(The first
draft cited `:226-231`, which swallowed them. Corrected.)*

**`suggested` and its `assessmentQuote` call are DELETED.** Plan review's first
blocker: after this change nothing reads `parsed.suggested` — `preview` (`:189`)
and `approve` (`:277`) both destructure only `baseCents`/`travelCents` — so the
naive diff leaves **a live `assessmentQuote({tier, service, slotStart})` call
sitting inside the money function**, still on its return type, invisible to
TypeScript because a returned property is a use. That is this ticket's own
out-of-scope finding #2 (*"a dead constant naming a superseded rule is how a
future edit reintroduces it"*) **recreated inside its own diff, on the money
path.** So:

- `:217-221` — the `assessmentQuote(...)` call: **deleted**
- `:213` — the `suggested` member of the return type: **deleted**
- `:231` — `return { baseCents, travelCents }`
- `:19` — the import narrows to `{ gstFor, isAssessmentTier }`; `assessmentQuote`
  leaves the file entirely
- `:22` — `parseAmountCents` leaves; `approvalAmountCents` enters

### The failed-send fix, and why it is a callback

`markPaid` gained `onCustomerNotify?: (o: 'sent'|'failed'|'none') => void` on its
input; `sendConfirmation` reports the **customer** outcome (not the office
invite's) exactly once on every path out, including its catch. `approveFree` now
branches three ways: `approved-free` / `approved-free-nomail` /
`approved-free-unsent`.

**Not a new `MarkPaidOutcome` member**, deliberately: three money-path callers
switch on that union (`review.ts`, `mark-paid.ts`, `stripe/webhook.ts`), and the
send outcome is not a different *outcome* — the row is confirmed either way — it
is a fact about a side effect. Reported beside the outcome rather than folded in.

**`notified` is the predicate, not `row.email`.** The correctness reviewer found
that `row.email ?` was the only has-email test in the codebase not using the
trimmed form — disagreeing with `booking-payment.ts:1551`, whose own comment warns
that *"a whitespace-only address is falsy here and truthy there."* Reading the
reporter makes the screen state what the sender did, which retires the question.

### Two method findings, both recorded in ROADMAP

1. **A derived pin that over-matches gets loosened by the next person.** The
   flash-map pin's first version grepped every `? 'a' : 'b'` in the file and
   reported `payment-link` — a `messageType` ternary 460 lines from any review
   outcome — as an unmapped review outcome. It now parses the `review:`
   expression and takes only the ternary **arms**, never the condition's own
   literals.
2. **`git checkout --` restores to HEAD, not to working state.** Used to undo a
   break mid-pass, it silently wiped this round's uncommitted production edits to
   two files; the surviving verify scripts then ran green against reverted
   sources. Caught by grepping for a constant that should have existed. **Back up
   the file or commit before breaking.** Third sibling of the crashed-script and
   unlanded-break traps: all three mislead in the reassuring direction.

### A gap that remains, stated rather than papered over

**`approved-free-unsent` has no behavioural arm.** The DB harness has no Resend
key, and a muted send is not a failed one, so `notified` is never `'failed'` here

completeness check fires when the key is deleted (verified, exit 1). What is not:
that the branch is reached on a real failure. **Owner: needs a ticket** — the
honest fix is a `deps`-injectable seam through the route, which
