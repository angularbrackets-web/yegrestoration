# BK-22 — Mandatory email and at least one photo/video on the public form

**Status:** plan-reviewed 2026-08-12 (fresh agent: 4 blockers, 7 should-fixes,
8 nits — all folded in; see Plan review below) — **awaiting user answer on the
`DRAFT_RATE_LIMIT_PER_HOUR` number, then approved**
**Phase:** P7 · **Tier:** Reviewed (public write path; changes what the
booking endpoint accepts) · **Depends on:** nothing — BK-21 landed
(`90c65a9`). *(The draft claimed a dependency on BK-21 because "both touch
`booking-email.ts`". That was false: this ticket touches no email file. Moot
now, corrected for the record.)* · **Blocks:** nothing — BK-23 is independent
and either order would work. This is first because it filters time-wasters
*immediately*, while confirmation is still instant.

## Why

Client decision, 2026-08-12 (ROADMAP P7): "drowning in time-waster bookings",
wants harder requirements to book. Two new requirements on the public form —
**email** and **at least one photo or video** — plus the standing exemption:
"if we enter ourselves we will ask them to text pictures/videos. It won't go
to review process." The 100 MB/file limit stays ("should be fine for now").

This ticket is deliberately the *whole* of the requirement change and none of
the review lifecycle. When it lands, a public booking still confirms
instantly; it just cannot be made without an address to email and something to
look at. BK-23 flips the flow afterwards.

## What the code does today (read, not recalled — verified twice, 2026-08-12)

- `booking-payload.ts:140` — `const email = optional('email', 'Email')`;
  `BookingPayload.email` is `string | null`. The header comment at `:87-91`
  argues the point: "email is optional here anyway — the phone number is how
  this business actually calls people back." That comment is now wrong and is
  part of the diff.
- `booking-form.ts:172-173` — the island's mirror of the same rule:
  format-checked when present, never required.
- `booking-form.ts:205` — "Step 3 collects only optional things: photos and
  consent." Step 3 returns no errors at all.
- `booking-admin-entry.ts:151,197` — `parseAdminEntry` wraps
  `parseBookingPayload` and **forwards its caller's `ParseOptions` verbatim**
  as the second argument. This is the seam the exemption goes through; there
  is no second copy of the validation to keep in step.
- Files: `/api/booking/upload-token/` writes the `appointment_files` row at
  **token-mint time**, before any bytes exist (`upload-token.ts:113`).
  `upload_state` becomes `'uploaded'` only when Vercel's `onUploadCompleted`
  webhook fires — which **never fires on localhost** and "can lag" in
  production (`booking-commit.ts:36-39`). `insertBooking` therefore claims
  files "regardless of `upload_state`".
- `BookingForm.svelte:389` — the payload's `draft_token` is
  `attachments[0]?.draftToken ?? null`, so a form with no attachments sends no
  token and the endpoint never resolves a `draftId`.
- `BookingForm.svelte:396-401` — the island already logs when the server's
  `filesAttached` disagrees with the number of uploads the browser saw
  succeed. The divergence below is known territory, not a new discovery.
- `createDraftSession` (`booking-form.ts:510-537`) does **not** cache a failed
  mint — `current` stays falsy on a `null` result, so the next file selection
  retries. A transient draft failure self-heals today.

## The three design questions this ticket has to answer

### Q1 — What counts as "has a photo", server-side?

The server's only evidence is `appointment_files` rows. Three candidate rules:

| Rule | False-rejects | False-accepts | Dev |
| --- | --- | --- | --- |
| any row for the draft | none | upload minted a token then failed | works |
| row with `upload_state='uploaded'` | webhook lag rejects a real customer | none | **impossible — never fires on localhost** |
| `head()` the blob at commit | Blob outage rejects | none | needs a live store |

**Decided: any row**, i.e. `COUNT(*) FROM appointment_files WHERE
draft_id = $1 AND appointment_id IS NULL`. It behaves identically in dev and
production; the `upload_state` rule is not merely stricter but *unrunnable
locally*, which would make every dev booking impossible and the verify story a
fiction. `head()` adds a network hop inside `POST_COMMIT_BUDGET_MS` to a path
already running four queries. The one false-accept — token minted, PUT failed
— lands on the customer you least want to bounce.

**Corrected from the draft (plan review S2):** the draft claimed this is
"byte-for-byte the same predicate `insertBooking` already claims by, so the
gate can never disagree". It is not. `insertBooking` holds its own copy of the
predicate inside the CTE (`booking-commit.ts:75-82`), plus `AND EXISTS (SELECT
1 FROM new_appt)`, and the two are evaluated at different instants against a
table the cleanup cron writes to. A named `countUnclaimedFiles` beside it is a
**second hand-written copy** — the exact failure mode the ticket cites
`claimedFilePathname` to avoid. The divergence risk is small, but it is not
zero and the ticket must not claim impossibility it does not have. It is
managed by a shared fixture, not by wishing: see Verification.

### Q2 — What happens when photos are *impossible* to attach?

`BookingForm.svelte:232-263` has a deliberate degradation: if minting a draft
fails, the island shows "Photos can't be attached right now. **You can still
book** — or call us", and the booking proceeds. Its JSDoc says the quiet part:
"A failure here **must never block the booking** … an appointment without
photos is still an appointment." Two live causes — `/api/booking/draft/`
answers 429 after `DRAFT_RATE_LIMIT_PER_HOUR = 20` mints per IP per hour, and
a Blob/env misconfiguration.

After this ticket that JSDoc is false, and the branch becomes: photos
impossible ⇒ **booking impossible**. That is a new way to lose a customer.

**Decided:**

1. **Two messages, not one.** `mintDraft` (`BookingForm.svelte:239-263`)
   currently collapses every non-ok status into a single sentence. Split it:
   - **429 — retryable.** "Too many people on this connection right now — wait
     a moment and try again." No phone fallback; `createDraftSession` does not
     cache the failure, so the next tap genuinely works. Telling this visitor
     to abandon the form would be wrong.
   - **anything else — hard failure.** Photos are required and cannot be
     attached, so **call or text `PHONE_DISPLAY`** and the office will book it
     for them. That fallback is real, not a brush-off: the office path is the
     admin entry, which is exempt by the client's own instruction.
2. `DRAFT_RATE_LIMIT_PER_HOUR` — **the user's call, see Open question below.**
3. Do **not** add a "couldn't attach? book anyway" bypass. It reopens exactly
   the hole the client asked to close and is trivially reachable by anyone who
   blocks one request. (Plan review agrees; not to be relitigated.)

### Q3 — What happens when the *only* upload fails or is skipped? (added by plan review B4)

The draft missed this, and it is more common than everything in Q2 combined.
`skipUpload` (`BookingForm.svelte:348-358`) exists for a stated reason:

> "The submit button waits for uploads to finish, so a 100 MB video stalled on
> hotel wifi — **exactly the case this form is built for** — would otherwise
> trap the visitor with no exit but a reload that loses everything they typed.
> A failed upload never blocks; only a hanging one did."

A strict client rule makes that last sentence false. Attach one video on a
flaky connection, watch it stall, hit **Skip** → `status: 'failed'`,
done-count 0, step 3 blocks, no way out. Note the asymmetry: the **server
would accept that booking** — the `appointment_files` row was written at
token-mint time, before the PUT — and only the client refuses.

**Decided: the client counts attachments in `{done, failed}`, not `done`
alone.** A client stricter than the server manufactures a dead end the server
would have allowed. Under this rule the requirement still filters the person
who attaches nothing — the client's actual target — and not the person whose
wifi dropped. `Skip`'s semantics are unchanged, so its JSDoc stays true.

The alternative (Skip becomes "cancel", Retry the only way forward) is
stricter and costs real bookings on bad connections; recorded as the option
not taken, and reversible if the client ever asks for the harder filter.

## Scope

**Validation core**

1. `booking-payload.ts` — `ParseOptions` gains **`entry: 'public' | 'admin'`,
   non-optional**. When `'public'` and email is absent:
   `add('email', 'Email is required.')`. Keep `BookingPayload.email` as
   `string | null` — admin rows genuinely have none, the column stays
   nullable, and **this ticket ships no migration**.
   - A discriminator, not an `isAdmin`/`requireEmail` boolean, for two
     reasons. A boolean's permissive value is `false`, so anything yielding
     `undefined` — a `Partial`, an `as ParseOptions` cast, a spread from a
     stale object — **fails open** and silently exempts the public form. And
     BK-23 needs this exact discriminator anyway (`source='web'` starts
     `pending`, `source='admin'` starts `booked`), so a boolean would be
     replaced one ticket later.
   - **On the rule this appears to break.** `booking-admin-entry.ts:15-24`
     says the admin bypass "is expressed by *not calling* `isSlotBookable`,
     never by a flag threaded through it: an `isAdmin` parameter on a shared
     predicate is how the public path accidentally inherits the bypass." This
     ticket threads a discriminator through a shared parser, so it must argue
     the difference rather than sail past it: the slot bypass is expressible
     structurally because it is a *whole predicate* admin skips, whereas email
     is one field inside a parse both paths need in full. Step 2 is what keeps
     the rule's *intent* — the public path cannot inherit the exemption
     because it cannot name it.
2. `booking-admin-entry.ts` — `parseAdminEntry` takes
   `Omit<ParseOptions, 'entry'>` and **hard-codes `entry: 'admin'` itself** at
   the `parseBookingPayload` call (`:197`), instead of forwarding the caller's
   options verbatim.
   - This is the plan review's B3, and it kills both failure modes: the admin
     route physically cannot supply `entry` (the type forbids it), and no
     caller of `parseAdminEntry` can make it behave like the public form.
     Forwarding instead would leave the admin route's own `ParseOptions`
     carrying a **dead and misleading** field — an `entry: 'public'` there
     would read as meaningful and do nothing.
   - Comment it with the client's exemption so nobody "fixes" the asymmetry.
3. `create.ts:65` — pass `entry: 'public'`.
4. `booking-payload.ts:87-91` — rewrite the `isPlausibleEmail` header comment,
   which currently argues email is optional.
5. **Every `ParseOptions` construction site must be updated — there are six,
   not two** (plan review B3): `src/pages/api/booking/create.ts:65`,
   `src/pages/api/admin/appointments/create.ts:57`,
   `scripts/verify-booking-payload.ts:10`, `scripts/verify-booking-form.ts:187`,
   `scripts/verify-booking-admin-entry.ts:61`, `scripts/verify-booking-ics.ts:448`.
   `astro check` covers `scripts/`, so all six break typecheck — that is the
   mechanism, and it is why `entry` is non-optional.

**The file requirement, server side**

6. `create.ts` — after `verifyDraftToken` resolves `draftId`, count the
   draft's unclaimed files and reject with a 422 field error on `files` when
   the count is 0 — same envelope as a parse error
   (`{ error, fields: [{ field: 'files', message: … }] }`), so the island's
   existing 422 handling routes it without a new branch.
   - `draftToken === null` ⇒ no query, straight to the same error. This is the
     common case, since the island only sends a token when it has an
     attachment.
   - **Fold the COUNT into the existing `Promise.all`** with the
     booked/blackout queries (`create.ts:95`) rather than adding a serial
     round trip. Evaluate the file error *before* `isSlotBookable`, so a
     photo-less booking reads "add a photo" rather than a slot message.
   - Extract the count as a named function in `booking-commit.ts` beside
     `insertBooking` (the `claimedFilePathname` precedent,
     `booking-files.ts:168`) so a verify script drives the *same statement*.

**The file requirement, form side**

7. `booking-form.ts` — `validateStep` gains a fourth parameter carrying the
   count of attachments in `{done, failed}` (per Q3). Non-optional, so every
   call site is typecheck-forced to answer. Step 3 returns
   `add('files', 'Add at least one photo or video.')` when it is 0, and its
   "Step 3 collects only optional things" comment is rewritten.
8. `booking-form.ts:120` — add `files: 3` to `FIELD_STEPS`. Without it,

   `mapCommitResponse` (`:456-463`) falls through to `formError`, and the
   visitor gets "Please check your details and try again" with nothing
   highlighted.
9. `BookingForm.svelte` — **the submit button stays enabled** and
   `validateStep` produces the `files` error, which renders where
   `photoNotice` renders. Do *not* disable submit: every other required field
   on this form (name, phone, address) allows submit and renders a field
   error, and the existing `busy` derived (`:136`) disables only for the
   genuinely transient `uploadsInFlight > 0`. A permanently disabled button
   with no explanation is a dead screen.
   - Specify precedence when both `errors.files` and `photoNotice` are set:
     `photoNotice` is cleared on every new selection (`:269`), and two red
     lines stacked in one box read as two problems.
   - Email label loses `(optional)` (`:630`) and gains the required marking
     the other required fields use.
   - Step 3's "Photos are optional, and they help us arrive with the right
     equipment" (`:758`) becomes a requirement line that still says *why*.
10. `BookingForm.svelte:232-263` — the draft-mint failure path per Q2,

11. `src/sections/ContactSection.astro:263` — "Photos optional, and they help

12. One GA4 funnel event on the Q2 hard-failure branch, matching the
    `booking_availability_error` precedent (`BookingForm.svelte:177,182`) —

    ROADMAP's Known trap, these count **attempts, not visitors**; the event
    name must not read as a visitor count.

**Verify scripts that this change breaks (plan review B1 — the draft missed
this entirely)**

13. `scripts/verify-booking-commit.ts` — its `payload()` helper (`:150-161`)

## Open question for the user (blocks approval)

**`DRAFT_RATE_LIMIT_PER_HOUR` is 20 per IP per hour and now gates the ability
to book at all.** One shared connection — an office, a building, a coffee shop
— burns it, and after this ticket that means nobody behind it can book.

The draft proposed 100. The plan review is right that this is a **cost**
decision and therefore the user's, not the implementer's: each draft
independently permits 10 files / 300 MB (`upload-token.ts:106-111`), so the
worst-case blob burn from a single IP goes from **~6 GB/hour at 20 to ~30
GB/hour at 100**. The review also notes the island mints exactly one draft per
form session (memoised, `booking-form.ts:510`), so 20 already means 20 *booking
sessions* per hour per NAT — the case for 100 is thinner than the draft
implied.

Nothing else in the ticket depends on the answer; it is one constant.

## Acceptance criteria

1. A public POST with no email is rejected 422 with a `field: 'email'` error;
   the same body with an email is accepted.
2. A public POST with no `draft_token` is rejected 422 with a `field: 'files'`
   error.
3. A public POST whose draft has zero unclaimed `appointment_files` rows is
   rejected 422 on `files`; one row is enough to pass, **whatever its
   `upload_state`**; a row already claimed by another appointment does **not**
   count.
4. An admin entry with neither email nor files still commits, and lands
   `source='admin'`.
5. The island shows a `files` error on step 3 when nothing is attached, with
   the submit button **still enabled**; a server `files` error routes the
   visitor back to step 3.
6. An attachment that failed or was skipped satisfies the client-side rule
   (Q3), and a booking made that way commits.
7. When the draft mint fails 429 the visitor is told to retry; on any other
   failure they are told to call.

## Risk areas, for the reviewers to weight

- **Public write path.** The endpoint's accept/reject contract changes.
- **The exemption's polarity.** Get it backwards and either the office cannot
  enter a phone-in booking, or the public form's new requirements evaporate.
  Red rows (f) and (g) exist for exactly this.
- **`verify-booking-commit.ts` is load-bearing and this ticket edits it.** The
  concurrency hammer is the only endpoint-level test of the double-booking
  guard. An edit that makes it pass for the wrong reason is the most expensive
  mistake available here.
- **Availability, not correctness, is the likely failure.** Every branch added
  here is a new way for a real customer to be told no. Q2 and Q3 are where
  that lives.
- No concurrency change: the partial unique index and the CTE are untouched.
- No PII change: no new column, no new field, nothing new in an email.
