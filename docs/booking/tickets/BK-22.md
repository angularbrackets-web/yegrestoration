# BK-22 — Mandatory email and at least one photo/video on the public form

**Status:** draft — awaiting plan review
**Phase:** P7 · **Tier:** Reviewed (public write path; changes what the booking
endpoint accepts) · **Depends on:** BK-21 landing first (both touch
`booking-email.ts`; sequencing only) · **Blocks:** nothing — BK-23 is
independent of this, and either order would work. This one is first because it
filters time-wasters *immediately*, while confirmation is still instant.

## Why

Client decision, 2026-08-12 (ROADMAP P7): "drowning in time-waster bookings",
wants harder requirements to book. Two new requirements on the public form —
**email** and **at least one photo or video** — plus the standing exemption:
"if we enter ourselves we will ask them to text pictures/videos. It won't go
to review process." The 100 MB/file limit stays ("should be fine for now").

This ticket is deliberately the *whole* of the requirement change and none of
the review lifecycle. When it lands, a public booking still confirms
instantly; it just cannot be made without an address to email and something to
look at. BK-23 flips the flow afterwards.

## What the code does today (read, not recalled — 2026-08-12)

- `booking-payload.ts:140` — `const email = optional('email', 'Email')`;
  `BookingPayload.email` is `string | null`. The header comment at :87 even
  argues the point: "email is optional here anyway — the phone number is how
  this business actually calls people back." That comment is now wrong and is
  part of the diff.
- `booking-form.ts:172` — the island's mirror of the same rule: format-checked
  when present, never required.
- `booking-form.ts:205` — "Step 3 collects only optional things: photos and
  consent." Step 3 returns no errors at all.
- `booking-admin-entry.ts:151,180` — `parseAdminEntry` wraps
  `parseBookingPayload` and shares its `ParseOptions`. **This is the seam the
  exemption goes through**; there is no second copy of the validation to keep
  in step.
- Files: `/api/booking/upload-token/` writes the `appointment_files` row at
  **token-mint time**, before any bytes exist (`upload-token.ts:113`).
  `upload_state` becomes `'uploaded'` only when Vercel's `onUploadCompleted`
  webhook fires — which **never fires on localhost** and "can lag" in
  production (`booking-commit.ts:36-39`). `insertBooking` therefore claims
  files "regardless of `upload_state`".
- `BookingForm.svelte:389` — the payload's `draft_token` is
  `attachments[0]?.draftToken ?? null`, so a form with no attachments sends no
  token and the endpoint never resolves a `draftId`.
- `BookingForm.svelte:396-399` — the island already logs when the server's
  `filesAttached` disagrees with the number of uploads the browser saw
  succeed. The divergence below is known territory, not a new discovery.

## The two design questions this ticket has to answer

Both are called out for the plan reviewer to attack; the choices below are
recommendations, not decided.

### Q1 — What counts as "has a photo", server-side?

The server's only evidence is `appointment_files` rows. Three candidate rules:

| Rule | False-rejects | False-accepts | Dev |
| --- | --- | --- | --- |
| any row for the draft | none | upload minted a token then failed | works |
| row with `upload_state='uploaded'` | webhook lag rejects a real customer | none | **impossible — never fires on localhost** |
| `head()` the blob at commit | Blob outage rejects | none | needs a live store |

**Recommended: any row**, i.e. `COUNT(*) FROM appointment_files WHERE
draft_id = $1 AND appointment_id IS NULL`. Reasons: it is byte-for-byte the
same predicate `insertBooking` already claims by, so the gate can never
disagree with the `filesAttached` number in the customer's confirmation; it
behaves identically in dev and production; and its only false-accept is a
customer who *selected a valid file* and whose upload then failed — precisely
the person the client does not want bounced. The requirement exists to stop
people who won't bother, not to defeat a crafted request. The `upload_state`
rule is not merely stricter, it is unrunnable locally, which would make every
dev booking impossible and the verify story a fiction.

The client-side rule is stricter on purpose (below): the browser gates on
`status === 'done'`, so for a real visitor the server rule is a backstop that
essentially never fires.

### Q2 — What happens when photos are *impossible* to attach?

`BookingForm.svelte:233-260` has a deliberate degradation: if minting a draft
fails, the island shows "Photos can't be attached right now. **You can still
book** — or call us" and the booking proceeds. Its comment says the quiet part:
"an appointment without photos is still an appointment." Two live causes —
`/api/booking/draft/` answers 429 after `DRAFT_RATE_LIMIT_PER_HOUR = 20` mints
per IP per hour ("one office behind one NAT", per its own comment), and a
Blob/env misconfiguration.

After this ticket that sentence is false, and the branch becomes: photos
impossible ⇒ **booking impossible**. That is a new way to lose a customer, and
it was previously impossible.

**Recommended:**

1. Rewrite the notice to route the customer instead of stranding them: photos
   can't be attached right now, and they are required, so **call/text
   `PHONE_DISPLAY`** and we'll book it for you. (The office path is the admin
   entry, which is exempt — the fallback is real, not a brush-off.)
2. Raise `DRAFT_RATE_LIMIT_PER_HOUR`. At 20/IP/hour it was throttling an
   optional nicety; it now throttles the ability to book at all, and one
   shared NAT — an office, a building, a coffee shop — burns it. The limit
   still has a job (it gates blob-token minting), so this is a raise, not a
   removal. **Number is the plan reviewer's to argue; 100 is the proposal.**
3. Do **not** add a "couldn't attach? book anyway" bypass. It reopens exactly
   the hole the client asked to close and is trivially reachable by anyone who
   blocks one request.

## Scope

**Validation core**

1. `booking-payload.ts` — add `requireEmail: boolean` to `ParseOptions`, and
   make it **non-optional** so both call sites must state their answer and
   typecheck enforces it (a defaulted `false` lets a future public caller
   inherit the exemption silently). When true and email is absent:
   `add('email', 'Email is required.')`. Keep `BookingPayload.email` as
   `string | null` — admin rows genuinely have none, the column stays
   nullable, and **this ticket ships no migration**.
2. `booking-payload.ts:87-91` — rewrite the `isPlausibleEmail` header comment.
   It currently argues email is optional. Say instead that the public form
   requires it (client decision, P7) while admin entry does not.
3. `create.ts:64` — pass `requireEmail: true`.
4. `booking-admin-entry.ts:180` — pass `requireEmail: false`, with a comment
   naming the client's exemption so nobody "fixes" the inconsistency later.

**The file requirement, server side**

5. `create.ts` — after `verifyDraftToken` resolves `draftId`, count the
   draft's unclaimed files and reject with a 422 field error on `files` when
   the count is 0 — same envelope as a parse error
   (`{ error, fields: [{ field: 'files', message: … }] }`), so the island's
   existing 422 handling routes it without a new branch.
   - `draftToken === null` ⇒ no query, straight to the same error. This is the
     common case for a photo-less submission, since the island only sends a
     token when it has an attachment.
   - **Fold the COUNT into the existing `Promise.all` with the booked/blackout
     queries** (`create.ts:95`) rather than adding a serial round trip — the
     route already runs a rate-limit query, two availability queries and the
     insert inside `POST_COMMIT_BUDGET_MS`. Evaluate the file error *before*
     `isSlotBookable`, so a photo-less booking reads "add a photo" rather than
     a slot message.
   - Extract the count as a named function in `booking-commit.ts` (beside
     `insertBooking`, which owns the matching claim predicate) so a verify
     script can drive the *same statement* against the dev branch — the
     `claimedFilePathname` precedent in `booking-files.ts:168`. A script-side
     copy of the query would stay green for exactly the drift it exists to
     catch.

**The file requirement, form side**

6. `booking-form.ts` — `validateStep` gains a fourth parameter carrying the
   count of attachments the browser has seen finish (`status === 'done'`).
   Non-optional, so every call site is typecheck-forced to answer. Step 3
   returns `add('files', 'Add at least one photo or video.')` when it is 0, and
   its "Step 3 collects only optional things" comment is rewritten.
7. `booking-form.ts:120` — add `files: 3` to `FIELD_STEPS`. Without it
   `stepForErrors` returns `undefined` for the server's new field and a 422
   lands the visitor on no step at all, showing an error next to nothing.
8. `BookingForm.svelte` — email label loses `(optional)` and gains the
   required marking the other required fields use; step 3's "Photos are
   optional, and they help us arrive with the right equipment" becomes a
   requirement line that still says *why* (equipment, accurate quote); the
   submit button stays disabled / the step blocks while no upload has
   finished, consistent with the existing `uploadsInFlight` handling; render
   the `files` error where `photoNotice` renders.
9. `BookingForm.svelte:233-260` — the draft-mint failure copy, per Q2.
10. `booking-config.ts:118` — `DRAFT_RATE_LIMIT_PER_HOUR`, per Q2.

**Copy** — implementer drafts, client edits later (standing rule). It is
customer-visible, so it goes past the client before launch alongside BK-26's
checklist wording.

## Out of scope

- **No migration.** `appointments.email` stays nullable for admin rows. The
  `pending`/`declined` statuses and the index rewrite are BK-23's.
- No change to the confirmation email's `if (!input.email) return null` guard
  (`booking-email.ts:221`) — still correct, still reachable via admin rows.
- BK-21's loud "customer is NOT reachable by email" line stays exactly as it
  is. After this ticket that line can only be produced by an admin row, which
  is the case it was always about.
- The 100 MB/file, 10-file, 300 MB-total limits are untouched (client: "should
  be fine for now").
- The Ads conversion still fires at submission (P7 decision).
- No retroactive treatment of existing email-less rows.

## Acceptance criteria

1. A public POST with no email is rejected 422 with a `field: 'email'` error;
   the same body with an email is accepted.
2. A public POST with no `draft_token` is rejected 422 with a
   `field: 'files'` error, without a database round trip for the count.
3. A public POST whose draft has zero unclaimed `appointment_files` rows is
   rejected 422 on `files`; one row is enough to pass, **whatever its
   `upload_state`**.
4. An admin entry with neither email nor files still commits, and lands
   `source='admin'`.
5. The island blocks step 3 until at least one upload has finished, and a
   server `files` error routes the visitor back to step 3.
6. When the draft mint fails, the visitor is told to call — and is not offered
   a booking that would be rejected.

## Verification

- `verify:booking:payload` — the `requireEmail` both-ways arm (true rejects
  absent, accepts present; false accepts absent).
- `verify:booking:form` — `validateStep` step 3 with 0 and with 1 finished
  attachment; `stepForErrors([{field:'files'}]) === 3`.
- `verify:booking:admin:entry` — the exemption: no email, still ok.
- **A DB-backed arm for the count statement**, against the dev branch, in the
  existing `verify:booking:admin:db` or `verify:booking:smoke` (implementer's
  call, argued in the ticket): a draft with 0 rows, a draft with 1 pending
  row, a draft whose rows are already claimed by another appointment
  (`appointment_id IS NOT NULL` ⇒ does **not** count). The third case is the
  one a script-side copy of the query would get wrong.
- Regressions: `verify:contact`, `verify:booking:smoke`, `verify:cutover`.
- Red-first, one row per failure mode: (a) email requirement, (b) the
  zero-file rejection, (c) the `appointment_id IS NULL` clause in the count,
  (d) the step-3 client gate, (e) the `FIELD_STEPS` routing.

## Risk areas, for the reviewers to weight

- **Public write path.** The endpoint's accept/reject contract changes.
- **The admin exemption is one boolean.** Get it backwards and either the
  office cannot enter a phone-in booking, or the public form's new
  requirements evaporate. It is the single highest-value assertion here.
- **Availability, not correctness, is the likely failure.** Every branch added
  here is a new way for a real customer to be told no. Q2 is where that lives.
- No concurrency change: the partial unique index and the CTE are untouched.
- No PII change: no new column, no new field, nothing new in an email.

## Assumptions log

- Q1 and Q2 answers above are the reviewer-drafter's, settled without the
  user — they are implementation questions beneath the client's decision, not
  restatements of it. **Except** the `DRAFT_RATE_LIMIT_PER_HOUR` raise, which
  changes an abuse control: flagged for the user in the handoff, and the
  ticket ships either way (the number is a constant, not a design).
- "At least one photo **or video**" is one combined requirement, not one of
  each — the client's phrasing throughout is "pictures/videos" as a single
  ask.
- The client's exemption covers admin entry as a whole. Nothing in the admin
  path requires an email or a file after this ticket.
