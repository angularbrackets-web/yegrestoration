**Status:** committed 2026-08-09 as `c223b13`. Implementation review returned
**no blockers**, 5 should-fixes and 4 nits; all nine accepted and fixed, each
fix carrying its own red run. Gates green. **Done** — except the production
migration, which is held for the merge (see Follow-ups).
Plan review: 4 blockers, 8 should-fixes, 5 nits, all accepted and folded in.
**Phase:** P3 · **Tier:** Reviewed · **Depends on:** BK-02, BK-03, BK-04 ·
**Blocks:** BK-06 (reminder reuses the copy module and the send adapter)

Reviewed because it sits on the public write path, puts PII and insurance
identifiers into outbound messages, and adds a network call *inside* the request
that commits a booking. Risk areas, in the order a reviewer should weight them:

1. **A notification failure must never change the booking's outcome.** The
   commit has already happened when this code runs. A throw here lands in
   `create.ts`'s existing `catch` and answers 500 for an appointment that
   exists — the customer books again, and the office gets a phantom. A *hang*
   does the same thing through the platform's function timeout.
2. **The locked PII rule, at the copy level.** `policy_number` and
   `claim_number` may never appear in the customer's confirmation.
3. **Injection.** Customer-typed strings become HTML and email subject lines.
4. **Latency.** Resend is a third-party HTTP call on a path that must answer.
5. **A schema migration** applied to two Neon branches, not one.

## Goal

A booking commits, returns 201, and then nothing happens. The customer has a
confirmation page and no record they can find tomorrow; the office finds out a
crew is expected somewhere only by opening the database. The contact form this
system replaces has emailed the office since day one — booking is a regression
against it.

Send two messages on commit: a confirmation to the customer, and a notification
to the office. Record whether each was sent.

## Decisions taken by the user (2026-08-09)

Asked rather than assumed, because all three are business/client-facing.

1. **Internal notification goes to `info@yegrestoration.ca` only** — the address
   the contact form already uses. No second recipient.
2. **Email stays optional on the booking form.** A customer who gives no email
   gets no confirmation, and the confirmed page says nothing about one. Phone is
   how this business calls back. Making it required was considered and declined;
   it is not deferred work and there is no follow-up ticket.
3. **No `.ics` calendar attachment.** The settled copy list does not include
   one, and a hand-written VCALENDAR needs its own DST and UTC-stamp
   verification. Out of scope, not deferred.

## Design notes

- **Resend never throws — except at the constructor.** Verified against the
  installed source, not recalled: `resend@6.17.1`, `dist/index.mjs`,
  `fetchRequest` wraps the `fetch` in a `try` and returns `{ data: null, error }`
  for a non-2xx *and* for a network failure; `CreateEmailResponse` is a
  `{data, error}` discriminated union. So `await resend.emails.send(...)` inside
  a `try/catch` catches nothing and the error must be read off the returned
  value — the single most likely way to ship this ticket broken and believe it
  works. `new Resend(key)`, however, *does* throw on a falsy key, and before
  that it silently falls back to `process.env.RESEND_API_KEY` — which under
  `astro dev` is empty exactly when `import.meta.env` holds the value. So: read
  the key through `readEnv`, return `'failed'` **before** constructing when it
  is unset, and always pass it explicitly rather than letting the SDK look.
- **Send inline, before the 201.** Vercel functions are not guaranteed to run
  work after the response is returned, and the adapter exposes no `waitUntil`.
  Inline is the only placement where the message is actually sent, and it is
  what lets the response tell the truth about `emailSent`.
- **One deadline over the whole post-commit block, not one per send.**
  `POST_COMMIT_BUDGET_MS = 5000` covers building the plan, both sends, and both
  stamps together; the two sends run concurrently under `Promise.allSettled`,
  so a hanging customer send cannot starve the office notification. Per-send
  timers were the plan's first shape and were wrong: two serial 5-second races
  stack on top of the rate-limit query, two availability queries, the insert,
  and the stamps. Nothing in this repo raises the function limit — `vercel.json`
  has no `functions` block and `astro.config.mjs` sets no adapter
  `maxDuration` — so the platform default applies, and exceeding it returns a
  platform 504 that `mapCommitResponse` shows as "Something went wrong on our
  end. Please call us." That is the ticket's #1 risk caused by the mitigation
  for its #4. The losing side of the race gets `.catch(() => {})` so a late
  rejection cannot surface as an unhandled rejection.
- **The notify step gets its own `try/catch`, inside the existing one.**
  `create.ts`'s outer `catch` returns 500 with "Something went wrong". Reaching
  it after `insertBooking` succeeded would tell a customer their booking failed
  when it did not — the mirror image of the failure that block's comment already
  guards against, and worse, because the appointment now exists and the slot is
  gone. `sendBookingNotifications` is written not to throw *and* is called
  inside a `catch` that swallows, deliberately belt-and-braces: the second guard
  covers the plan-building code too, which does string work on user input.
- **The stamps are awaited and swallowed, not fired and forgotten.** The reason
  for sending inline — post-response work is not guaranteed to run — applies
  identically to an un-awaited `UPDATE`, and a floating rejected promise is an
  unhandled rejection in the function. They are awaited inside the budget and
  before the `Response` is constructed; a failure to write one is logged and
  changes nothing about the response.
- **`emailSent: false` is always safe, `true` is the claim that must be
  earned.** A customer told "check your email" who has nothing is a support
  call; a customer told nothing who receives an email is a pleasant surprise.
  Every default and every failure path resolves to `false`. A message that
  lands after the deadline is therefore reported as unsent, which is wrong in
  the safe direction.
- **Muting the smoke test needs a *positive* signal, and the obvious fix does
  not work.** `verify:booking:smoke` commits a real booking against the Neon dev
  branch on every run. The customer address is `smoke@example.com` (RFC 2606,
  undeliverable by design), but `BOOKING_INTERNAL_TO` is the client's real
  inbox. Today the run is inert by accident: `.env` has no `RESEND_API_KEY` and
  `.env.local` has it as `""`, which both `loadEnv` implementations skip. The
  day someone puts a real key in `.env` — which `.env.example` invites — every
  smoke run mails the client. *Removing* the key from the child's environment
  cannot prevent that: `readEnv` falls back to `import.meta.env`, which Vite
  populates inside the spawned `astro dev` from the dotenv files, and the parent
  process has no reach into that. So the script sets
  `BOOKING_NOTIFY_DISABLED=1` in the child's `process.env` instead, which
  `readEnv` prefers over Vite — the same mechanism the existing `DATABASE_URL`
  swap already proves survives into the daemonized dev server. The flag is
  fail-open: unset means enabled, so no production misconfiguration can silence
  mail by omission.
- **Subjects are whitespace-collapsed.** `parseBookingPayload` trims a name but
  permits interior newlines, and the name reaches a `Subject:` line. Resend
  takes JSON over HTTPS rather than raw SMTP, so this is not a header-injection
  hole, but a subject containing a newline is a malformed subject and there is
  no reason to send one.
- **`html` and `text` are both built, always.** A text/plain alternative is not
  decoration here: it is what a customer's mail client shows in the preview
  line, and it is the copy the client will actually read when editing.

## Acceptance criteria

1. `planBookingNotifications` for a booking with an email address produces a
   customer message addressed to it and an internal message addressed to
   `info@yegrestoration.ca`.
2. A committed booking with **no** email address produces `customer: null`, and
   the 201 reports `emailSent: false`.
3. The customer confirmation contains the slot label, an explicit Edmonton-time
   qualifier, the address, the ~30 minute line, all five have-ready items, and
   the call-or-text phone number.
4. The customer confirmation contains **no** `policy_number` and **no**
   `claim_number`, for an insurance booking where both were supplied — checked
   across the *whole* message object (subject, to, replyTo, html, text), with
   fixture values distinctive enough that "does not contain" means something.
5. The customer confirmation contains no cancel or reschedule URL.
6. The internal notification carries the booking id, the slot label, name,
   phone, email, service label, the customer's description, full address,
   payment route, the attached-file count, and — on the insurance route only —
   insurer, policy, and claim numbers.
7. A private-pay booking's internal notification carries no insurance section.
8. HTML-significant characters (`& < > " '`) in any customer-supplied field are
   escaped in the HTML part and left as typed in the text part.
9. Newlines in a name do not reach a subject line.
10. Each of these still answers **201** with the booking's id and
    `emailSent: false`, with the booking row present and unchanged: a Resend
    error response, a send that exceeds the budget, and an unset
    `RESEND_API_KEY`.
11. `confirmation_sent_at` is set only when the customer message was sent and
    `internal_notified_at` only when the internal one was; a failure to write
    either does not change the response.
12. `/book/confirmed/` mentions email only when `emailSent` is true.
13. `npm run typecheck` and `npm run build` pass.

## Assumptions log

Settled without the user, and each one is a reviewer's to overturn.

- **"The address" in the confirmation is the customer's service address**, not
  the business's. The crew travels to them, and BK-04's confirmed page already
  renders `address, city` on the same reading.
- **From `YEG Restoration <noreply@yegrestoration.ca>`, reply-to
  `info@yegrestoration.ca`** for the customer message — the same sender identity
  the contact form uses, so no new domain verification. People reply to booking
  confirmations, so the reply-to is what makes `noreply` acceptable.
- **The internal message's reply-to is the customer's address** when they gave
  one, matching `api/contact.ts`.
- **Insurance identifiers belong in the internal email.** The `002-booking`
  column comment scopes them to "email and the admin panel only"; the locked
  copy rule constrains the *confirmation* and the SMS, not the office's copy.
- **`BOOKING_NOTIFY_DISABLED` is the one new environment variable**, and it is
  test-only. It is fail-open by design, so production behaviour when it is
  absent — which is always — is unchanged. `RESEND_API_KEY` already exists;
  recipients are code constants.
- **The platform function limit is at least 10 seconds.** No `maxDuration` is
  configured anywhere, so the Vercel default for the account's plan applies and
  the 5-second budget is sized against the lowest documented default rather
  than a measured value. BK-11 should confirm the plan's actual limit as a
  launch check.
- **Migration 003 needs no backfill.** Every existing appointment predates the
  feature, and a NULL that means "we never sent one" is accurate.

## Implementation review — 2026-08-09, no blockers

Nine findings, all accepted and fixed. The five should-fixes, and what each one
actually cost:

1. **The stamp could rewrite the answer.** The `UPDATE` shared the send's return
   path, so a failed stamp reported `emailSent: false` for two emails that had
   gone out — and the first way that happens is deploying before the migration,
   where the columns do not exist and *every* booking under-reports while the
   log blames the notification. Fixed by extracting `notifyAndStamp` into
   `booking-notify.ts` with an injectable `stamp`, so the ordering is asserted
   rather than commented: the send decides the answer, the stamp cannot revise
   it, and its failure is caught where the catch is verified.
2. **The `UPDATE` was executed by no gate.** The email verify injects a sender
   and never touches SQL; the smoke run mutes notifications, so both outcomes
   are `skipped` and the route's own call short-circuits. Nothing anywhere ran
   the statement — including whether Postgres infers `boolean` for the two
   untyped `CASE WHEN ${bool}` parameters the Neon HTTP driver sends. Fixed by
   moving the statement to `stampNotifications` in `booking-commit.ts` and
   calling it from `verify-booking-smoke.ts` against the dev branch, reading
   both columns back. It does infer boolean — now measured, not assumed.
3. **AC9 asserted something that could not fail.** The design note claimed "the
   name reaches a `Subject:` line"; it did not — both subjects were built
   entirely from constants and server-formatted values, so the two
   newline-in-subject assertions were inert whatever `headerSafe` did. Fixed in
   the direction the office benefits from: the internal subject now carries the
   name, which makes it the one customer-typed string in either subject and
   makes `headerSafe` load-bearing. Asserted, then red-observed.
4. **Failure logs named no booking.** The justification for shipping no retry
   queue is that a failure is logged and visible in the columns — but the
   columns are not surfaced until BK-07, so the log is the only signal, and it
   identified no appointment. `bookingId` is threaded into `deliver`.
5. **The disable flag tripped on any value.** `readEnv(FLAG) !== undefined`
   meant `BOOKING_NOTIFY_DISABLED=0` or `=false` — the spelling for "present but
   off" — would silently stop every confirmation in production. Now only `1` and
   `true` disable, the suppression logs at `error`, and all seven values are
   asserted.

The four nits, all fixed: `row()` escapes its value by default with `rawRow` as
the explicit opt-out (the asymmetry was a footgun for the next field added, and
no assertion would have caught it); the `Promise.all`-described-as-`allSettled`
comment now says why `all` is correct; the stamp uses a fresh clock rather than
the request's; and the unreachable `SERVICE_LABELS` fallback says that it is
unreachable, since it read as though raw user input could reach a subject.

**Second red pass** — the fixes' own failure modes, same protocol, 7/7 red:

| Broken target | Observed |
| --- | --- |
| `notifyAndStamp` lets a stamp failure propagate | red — a failed stamp turned a sent confirmation into an unsent one |
| `notifyAndStamp` stamps `sent` regardless of outcome | red — `and nothing is stamped as sent` |
| the disable flag trips on any value again | red — `BOOKING_NOTIFY_DISABLED="0" must not mute` |
| the internal subject drops the name | red — `the internal subject carries the name, so headerSafe is load-bearing` |
| `row()` stops escaping its value | red — `the internal html has no injected tag` |
| `confirmation_sent_at`'s `ELSE` arm → `NULL` | red — `stamping the internal side preserves the customer stamp`, against the live dev branch |
| `internal_notified_at`'s `ELSE` arm → `NULL` | red — `stamping the customer side preserves the internal stamp` |

The last two are worth a note. Breaking the `internal_notified_at` arm was
**green on the first attempt**: the smoke script asserted one direction of the
CASE and not the other, so half the statement was uncovered. The symmetric
assertion was added and the break then went red. This is the red-first rule
paying for itself on the same day it was applied — the coverage gap was
invisible from reading the script.
