Client-requested 2026-08-11 ("can we connect the booking directly to Google
Calendar?"), scoped in conversation with the user to **level 1** of the three
levels offered: bookings *appear* on the office calendar as standard email
invites, cancellations clear them. Level 2 (Google Calendar API,
self-maintaining events) is the recorded upgrade path; level 3 (the calendar
*blocking* availability) is declined — blackout dates are the manual version
and fit one crew.

Reviewed because it adds mail to two write paths (one of which sends nothing
today), extends the `Message` contract every notification flows through, and
amends a deliberately-tested invariant (admin actions never mail the office).
Risk areas, in the order a reviewer should weight them:

1. **The whitelist no-op.** `createResendSender` maps `Message` fields to the
   SDK by an explicit object literal (`booking-notify.ts:100-110`) — adding
   `attachments` to the `Message` type without editing that literal ships a
   silently attachment-less email, and every verify script would stay green
   because their injected fake senders *do* see the field. The real mapping
   is behind the SDK boundary, so it gets a source-level pin (the BK-09
   precedent for behaviour that cannot be driven without a live call),
   stated honestly as such.
2. **PII in a calendar artifact.** The internal notification email carries
   insurer/policy/claim by design; the ICS must **never** — a calendar event
   syncs to phones, shared calendars, and third-party apps, so it gets the
   SMS-grade rule (`policy_number`/`claim_number` never in ICS output, any
   audience), not the internal-email one. This restates the locked PII rule
   for a new artifact class before the artifact exists.
3. **The amended invariant.** Admin actions currently never mail the office
   (`booking-admin-notify.ts:9-11`, asserted at
   `verify-booking-admin-entry.ts:474-486` — "the office doesn't need to be
   told what it just did"). A phone-in booking typed into admin is exactly
   the case where the office *does* want a machine artifact of what it just
   did — that is the feature. The invariant narrows to "no admin action
   sends a *notification* email to the office"; the calendar invite is a
   calendar artifact, deliberately tiny, and the assertion is rewritten to
   pin the narrowed rule (exactly one office mail per admin create, and it
   is the invite; zero on every other admin action except cancel/un-cancel).
4. **Lifecycle correctness.** Cancel must send `METHOD:CANCEL` with the
   *same UID* and a *higher SEQUENCE* or Google ignores it; un-cancel must
   re-issue `METHOD:REQUEST`, same UID, higher still. Nothing stores a
   sequence — see Mechanism for the stateless answer.

## Goal

Every booking — public `/book/` commit or admin phone-in entry — arrives at
`info@yegrestoration.ca` as a standard iCalendar invite that lands on the
office Google Calendar in one click (or automatically, per Gmail settings).
Cancelling in admin clears the calendar event; un-cancelling restores it.
No new credentials, no Google API: RFC 5545 over the Resend pipeline that
already exists and is already muted, seamed, and verified.

## Mechanism — pinned against installed source and the RFC, not recall

**Resend 6.17.1** (`dist/index.d.mts`, read by this ticket's recon):
`CreateEmailBaseOptions.attachments?: Attachment[]` (:526), max 40 MB/email;
`Attachment` takes `content?: string | Buffer`, `filename?`, `contentType?`
(:602-616). `invalid_attachment` is an existing error code and flows through
the current resolved-`{error}` mapping unchanged. The batch API excludes
attachments; not used here.

**RFC 5545 facts the builder must honour** (the verify script asserts each):

- CRLF line endings; lines folded at 75 octets with a leading space on
  continuations; text values escape `\` `;` `,` and newlines.
- `METHOD:REQUEST` in VCALENDAR for create/restore, `METHOD:CANCEL` +
  `STATUS:CANCELLED` for cancel. Same `UID` across the lifecycle:
  `booking-<id>@yegrestoration.ca` (the SERIAL id is the only reference
  that exists — recon confirmed no human-facing reference column).
- **`SEQUENCE` is stateless by design**: seconds-since-epoch of the send
  instant. RFC 5545 requires only that it increases per revision; deriving
  it from the injected `now` means cancel > create and re-book > cancel
  with **no new column and no migration** — the alternative (a
  `calendar_sequence` column bumped per transition) buys nothing but a
  migration and a race. Two bounds, documented rather than defended
  (plan review): 1-second granularity means a cancel→un-cancel inside the
  same second yields an equal SEQUENCE and the restoring REQUEST reads as
  stale — implausible through two form submits and redirects, accepted;
  and iCalendar INTEGER is int32 (RFC 5545 §3.3.8), which
  seconds-since-epoch crosses on 2038-01-19 — a dated, documented horizon,
  not a defect this ticket pays to avoid.
- **Idempotency keys must not collapse the lifecycle** (the plan-review
  blocker). `createResendSender`'s key is `<prefix>:<to>`; a fixed
  per-booking prefix makes create, cancel, and un-cancel byte-identical
  keys, and Resend's dedupe would swallow every transition after the
  first. Invite sends therefore use a **per-transition prefix embedding
  the SEQUENCE** — `booking-<id>-<kind>-<seq>` — which keeps retry
  dedupe within a transition and never across transitions.
- **ORGANIZER is a bare address and identical across the lifecycle**
  (plan review): `ORGANIZER:mailto:` takes the plain address, not the
  friendly-name `BOOKING_EMAIL_FROM` form, and Gmail distrusts a CANCEL
  whose organizer doesn't match the event's — so `ICS_ORGANIZER` is its
  own booking-config constant, aligned with the sending identity and
  asserted equal across REQUEST and CANCEL.
- Required VEVENT/VCALENDAR properties include `VERSION:2.0` and
  `DTSTAMP` (from the injected `now`) — both on the verify list, not
  assumed.
- `DTSTART`/`DTEND` as UTC instants (`...Z` form) — no VTIMEZONE block
  needed, and Google renders in the viewer's zone. `DTEND = slot_start +
  SLOT_MINUTES` (no `slot_end` column exists; the CHECK pins 30).
- `ORGANIZER:mailto:` the noreply identity; `ATTENDEE:mailto:` the office.
  `SUMMARY: Assessment — {name} ({serviceLabel})`, `LOCATION` from the
  row's address/city/postal (the `address` column exists and is NOT NULL),
  `DESCRIPTION`: phone, service, and the visit-length line — **and never
  policy/claim** (risk area 2).

**Attachment shape**: `{ filename: 'assessment-<id>.ics', content: <ics
text>, contentType: 'text/calendar; charset=utf-8; method=REQUEST' }` (or
`method=CANCEL`) — the `method=` parameter is the conventional signal for
invite rendering; Gmail's actual behaviour is heuristic and undocumented,
which is why AC5's post-deploy render check is the honest pin, not this
sentence. (`Attachment` type at `index.d.mts:602-616`; `attachments` on
`CreateEmailBaseOptions` at `:526`. The draft's `:520`/`:602-620` were
off by a few lines — corrected at implementation review, nit 2.)

## Design notes

- **One mechanism per path, no double mail.** Public bookings: the ICS rides
  the internal notification that already fires. Admin creates and
  cancel/un-cancel: the tiny invite-only email, because nothing else fires
  there and a full lead-notification to the office about its own typing is
  exactly what the old invariant rightly forbade.
- **Best-effort everywhere.** No booking, entry, or status edit ever fails
  or blocks on an invite; a missed invite is an office inconvenience
  recoverable by hand, and the failure is in the function log. This is the
  public path's existing posture extended to the new sends.
- **Stateless SEQUENCE** — Mechanism; the reviewer should challenge the
  derivation, not the absence of a column.
- **The ICS never carries policy/claim for any audience**, even though
  today's only audience is the office that already receives them in the
  same email's body. The rule is about where calendar artifacts travel,
  and it must hold before a customer variant ever exists.

## Acceptance criteria

1. A public booking's internal notification carries exactly one `.ics`
   attachment: METHOD:REQUEST, UID `booking-<id>@yegrestoration.ca`,
   DTSTART/DTEND spanning the slot's 30 minutes in UTC `Z` form, LOCATION
   from the row's address, SUMMARY with name and service — and no policy or
   claim number anywhere in the ICS, for a fully-insured booking. The
   customer confirmation carries no attachment.
2. An admin manual entry sends exactly one office email — the calendar
   invite — regardless of the customer-confirmation checkbox; every other
   admin action except a cancelled-boundary status edit sends the office
   nothing (the narrowed invariant, asserted in both directions).
3. A status edit into `cancelled` sends METHOD:CANCEL + STATUS:CANCELLED
   with the same UID and a SEQUENCE strictly greater than the create's;
   un-cancelling sends a fresh REQUEST, same UID, greater still. Re-submits
   and completed/no_show edits send nothing; the 23505 conflict arm sends
   nothing.
4. All invite sends are best-effort: with the send failing or the key
   unset, booking commit, admin entry, and status edits all succeed exactly
   as today, with the failure logged.
5. The builder's output is RFC-honest: CRLF, 75-octet folding, escaped
   text, and it survives a real Gmail render (post-deploy check).
6. `createResendSender` forwards `attachments` to the SDK (source-pinned),
   and `BOOKING_NOTIFY_DISABLED` mutes every new send.
7. `npm run typecheck` and `npm run build` pass; existing notification
   verify scripts pass unmodified in behaviour (extended, not weakened).

## Assumptions log

Settled without the user; each is a reviewer's or the user's to overturn.

- **The admin-mail invariant narrows rather than holds.** Risk area 3; the
  feature is impossible without it, and the narrowed form is asserted more
  precisely than the old one was.
- **Office-only this ticket; customer ICS deferred** — Out of scope.
- **SEQUENCE from the clock, no column** — Mechanism.
- **Cancel/un-cancel invites are best-effort with no UI flash.** The
  office is the audience and is standing in admin performing the action;
  a failed CANCEL is visible in the log and recoverable by deleting the
  event by hand. A flash would add a UI state for a self-correcting case.
- **`now` is injected as a `Date`** everywhere (the BK-09 precedent), so
  DTSTAMP and SEQUENCE come from one instant per send.
- **No new environment variables.**

### Settled during implementation

- **The cancel invite gets its own subject.** The ticket wrote one subject for
  both kinds (`Calendar: assessment #<id> — <name>`); a CANCEL arriving under a
  subject identical to the create is the kind of mail that gets archived
  unread, and acting on the wrong one costs a crew a drive. Cancels now read
  `Cancelled: assessment #<id> — <name>`. Asserted as "a cancellation does not
  arrive under the same subject as the booking".
- **The boundary rule is the cancelled boundary, not the status names.** The
  ticket says "into `cancelled` sends `'cancel'`, out of `cancelled` back to
  `booked` sends `'request'`" while framing the rule as "crosses the cancelled
  boundary". Implemented as the boundary: any non-cancelled → `cancelled` sends
  a CANCEL, `cancelled` → any non-cancelled sends a REQUEST. A
  `cancelled → completed` edit means the visit happened, so the event belongs
  on the calendar. `booked → completed` / `booked → no_show` cross nothing and
  send nothing, exactly as specced, and both are asserted.
- **The self-join snapshot also selects `phone`.** The pinned statement lists
  seven columns and omits it, but `IcsEvent` takes a phone and the DESCRIPTION
  prints it — so the pinned SQL was one column short of buildable. Added rather
  than dropping the field from the invite.
- **`inviteEventFromPayload(id, payload, serviceLabel)`** takes the id first and
  the label explicitly, matching `planForPayload`'s existing argument order
  rather than the ticket's informal `(payload, id)`. `serviceLabel` cannot come
  off the payload — it holds the service *key*, and `SERVICE_LABELS` lives in
  `db.ts`, out of reach of a `tsx` script (the same reason this module already
  injects it).
- **`inviteEventFromAppointment` takes a `Pick<Appointment, …>`, not a full
  row.** `update.ts` holds a seven-column self-join snapshot, and demanding the
  whole row there would mean a second SELECT — the check-then-act shape that
  route's docstring forbids.
- **The admin entry's two post-commit sends run concurrently.** Serially they
  would stack two full `POST_COMMIT_BUDGET_MS` windows onto a request that has
  already run an insert, which is how a platform 504 replaces a saved entry's
  redirect. One `Promise.all`, the same reasoning `sendBookingNotifications`
  states for its own.
- **`ATTENDEE` carries the RSVP parameters**
  (`CUTYPE`/`ROLE`/`PARTSTAT=NEEDS-ACTION`/`RSVP=TRUE`) rather than the bare
  `ATTENDEE:mailto:` the Mechanism section spells. They are what makes a client
  offer the yes/no/maybe buttons instead of a file to download; the address —
  which is what the ticket was pinning — is unchanged and asserted. AC5's
  post-deploy render check remains the honest pin either way.
- **Scope 10's second half is a no-op.** The ROADMAP never states the
  admin-mail invariant — only BK-08's ticket does, as its own historical
  record, which is not rewritten. The narrowed wording therefore lives in
  `booking-admin-notify.ts`'s header (where the old one was) and in the
  rewritten assertion. What the ROADMAP *did* get is the P6 status line and a
  Known-traps entry for the two verification defects the red pass exposed.
- **A muted route CAN say more than the plan assumed.** `sendCalendarInvite`
  logs the booking it is muting, so a captured `console.error` in
  `verify-booking-admin-db.ts` distinguishes "the route reached the send and
  the mute stopped it" from "the route was never wired" — which plan-review S5
  expected only the post-deploy check to do. It still says nothing about the
  message's contents, so the lib-level arms stay where they are. This is what
  makes AC3's "re-submits and completed/no_show edits send nothing" and AC2's
  "regardless of the checkbox" behavioural rather than source-pinned.
