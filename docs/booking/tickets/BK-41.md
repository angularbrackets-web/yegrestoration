# BK-41 — HEIC: findings and options

**Status:** report only, 2026-08-16. **Nothing built, by instruction** — the
options touch the Blob write path or the serving path, and the client wants to
see the trade before anything moves.
**Phase:** P10 · **Tier:** — · **Depends on:** nothing · **Blocks:** nothing.
**Deploy:** none yet.

## Findings

### (a) Accepting `.heic`/`.heif` — ALREADY BUILT, nothing to do

Verified in the code, on both upload surfaces:

| Layer | State |
| --- | --- |
| `ALLOWED_UPLOAD_TYPES` | includes `image/heic`, `image/heif` |
| `UPLOAD_EXTENSIONS` / `EXTENSION_TO_TYPE` | map `heic` → `image/heic`, `heif` → `image/heif` |
| `parseUploadPathname` | therefore accepts `<uuid>.heic` |
| `BookingForm.svelte:78`, `AppointmentUpload.svelte:54` | `accept` carries the MIME types **and** `.heic,.heif,.mov` |
| `resolveContentType` | falls back to the filename extension when the browser reports `type: ''`, which it routinely does for HEIC |

That extension fallback is deliberate and already commented: a types-only
accept list "hides every iPhone photo behind 'no files available'". **Nothing in
the upload path needs changing.**

### (b) Viewing — this is the actual gap, and it is measured

I generated a real HEVC-coded HEIC with `sips` and tried to decode it in
Chromium 151:

```
createImageBitmap → InvalidStateError: The source image could not be decoded.
<img> onerror      → failed to decode
```

Both paths fail on a well-formed file. **Chrome, Edge and Firefox cannot render
HEIC; Safari (macOS and iOS) can.**

The admin file link 302s to a signed CDN URL (`api/admin/files/[id].ts:64`) and
the CDN serves the blob with the `contentType` recorded at upload. So on a
Windows or Chrome desktop the office gets a download or a broken tab, never a
photo. On a Mac or an iPad, it just works.

**Unverified, and it changes the severity:** whether Vercel Blob sends
`Content-Disposition: attachment` on these objects. If it does, every HEIC is a
download rather than a broken tab even on Safari — annoying but workable. I
could not test this without production Blob credentials.

## The thing that inverts the obvious fix

**Our own `accept` list is the most likely reason we receive HEIC at all.**

iOS Safari transcodes HEIC → JPEG for a file input *unless the accept list says
HEIC is welcome* — and ours says so explicitly. There is a well-documented
Safari 17+ report of the stronger form: with `image/heic` in `accept`, files
arrive renamed to `tempImage….heic` with `type: "image/heic"`; with it removed,
"the file object would be printed out as its original extension."

Two honest caveats, because this decides the recommendation:

- **This is not an Apple guarantee.** The thread is user-reported with no Apple
  response, and the behaviour is widely described as version- and
  context-dependent. It must be tested on a real iPhone before it is relied on.
- The same thread notes the dilemma: other browsers *need* `image/heic` in
  `accept` before they will let a user pick a `.heic` file at all.

## Options, cheapest first

### Option 0 — narrow the client `accept` list. Recommended to test first.

Drop `image/heic` / `image/heif` from the **`accept` attribute only**, keeping
the `.heic,.heif` extension entries so a desktop user can still select one, and
keeping the MIME types in `ALLOWED_UPLOAD_TYPES` so a genuine HEIC that does
arrive is still accepted server-side.

- **Cost:** one line per island. No migration, no Blob change, no serving
  change, no new dependency.
- **Effect if it works:** iOS transcodes at the source and we receive JPEG.
  The problem stops existing rather than being compensated for, and the office's
  browser stops mattering.
- **Risk:** if the extension entries alone still trigger Safari's conversion, it
  changes nothing and we have lost nothing. If a desktop user's picker starts
  refusing `.heic`, that is a regression — which is why the extension entries
  stay.
- **Unknown until tested on a real iPhone.** Two minutes, and it decides
  everything below.

### Option 1 — convert on upload (the Blob write path)

**The awkward fact: the browser uploads directly to Blob and the bytes never
pass through our functions**, which is the whole reason 100 MB videos work. So
"convert on upload" really means one of:

- **In the browser, before `upload()`** — `heic2any`/`libheif` WASM, roughly
  1–2 MB added to the bundle and slow on the phones that produce HEIC. It would
  land on the **public booking island**, whose LCP the project has already spent
  a ticket on. Poor trade.
- **Route images through a function** — a second upload path, contradicting
  BK-34a's explicit "there is no multipart proxy in this feature", and capped by
  the 4.5 MB function body limit.
- **A post-upload job** — new infrastructure for a handful of files.

**Verdict: the most expensive option and the one that touches the most
load-bearing code.**

### Option 2 — convert in the serving path

The admin proxy would stop redirecting and start streaming converted bytes.

`booking-files.ts`'s header rejects exactly this by name: the redirect exists
"because uploads run to 100 MB per file and a function response body has
platform limits a redirect never touches". It could be narrowed to *images
only*, which are a few MB — but that means the proxy behaves differently per
content type, and the security property that makes it reviewable (one pathname,
one signed token, no bytes through the function) gets a second mode.

**Verdict: cheaper than Option 1, but it spends a documented architectural
decision to fix a browser-support problem.**

### Option 3 — change nothing in code

Tell the office to open HEIC links in Safari, which renders them natively; on
Windows, the free HEIF Image Extensions make a downloaded `.heic` open in Photos.

- **Cost: zero.** **Effect: depends entirely on what the office actually uses.**
- Worth knowing before spending anything: **if the office reviews photos on an
  iPhone or iPad, there is no problem to solve.**

## Recommendation

1. **Test Option 0 on a real iPhone** — book a test appointment, attach a photo
   from the Photo Library, and look at `appointment_files.content_type`. If it
   says `image/jpeg`, iOS is already transcoding and (b) only ever bites on
   files sent from a Mac. If it says `image/heic`, try the narrowed accept list
   and look again.
2. **Answer the operational question**: what does the office read photos on?
   That single fact may retire this ticket.
3. Only if Option 0 fails **and** the office is on Windows/Chrome does Option 2
   become worth its cost. Option 1 is not recommended in any branch.

## Two things to do regardless of the decision

- **BK-23's thumbnail gallery must degrade to a filename tile for HEIC**, not a
  broken-image icon. Already written into that ticket.
- **The admin file row should say when a file will not preview**, so the office
  knows it is a format issue rather than a broken upload. `content_type` is on
  the row already; this is a label, not a mechanism.
