## What is wrong

Five findings. §7 named one of them, and named it smaller than it is.

**This was not theoretical. On 2026-08-31 the dev branch held 34 stranded rows
from at least two interrupted runs, a full suite ran over them, exited 0, printed
`✓ admin write-path checks passed`, and left all 34 in place** — while its own
leftover check reported `0 seeded row(s) survived cleanup`. That run is R1.

### 1. `cleanup()` cannot see most of the rows it strands

`scripts/verify-booking-admin-db.ts:392-395`:

```sql
DELETE FROM appointments
WHERE id = ANY(${createdIds}::int[]) OR admin_notes LIKE ${`${MARKER}%`}
```

Two arms. On the **`finally`** sweep (`:4376`) `createdIds` is populated, so a
normally-terminating run cleans up fine. On the **pre-run** sweep (`:435`)
`createdIds` is empty — so only the `admin_notes` arm is live, and it sees only
rows seeded with `admin_notes: MARKER`.

A run killed by SIGKILL, by a broken pipe (`| head`), or by a harness timeout
never reaches the `finally`. Its rows survive. The next run's pre-run sweep is
then structurally unable to remove any of them that lack MARKER.

**The pre-run sweep exists for precisely this job and cannot do it.** Its own
comment at `:432-434` says so:

> *"Leftovers from an interrupted earlier run would make the first insert report
> a taken slot, which reads as a failure of this run rather than of that one."*

Fourth instance of the stale-comment-becomes-justification shape this project
records, after `update.ts:266`, `booking-email.ts:629` and `[id].astro:87` — and
the first where the comment was never true rather than becoming untrue.

### 2. The leftover check reads the same predicate as the delete, so it cannot fail

The `finally` block asks whether anything survived (`:4381-4396`) using the
**same two arms** it just deleted by, then `failures++` if the count is non-zero.
A row `cleanup()` cannot see is a row this check cannot count. It reports
`0 seeded row(s) survived` while the strandings sit in the table.

**This is the eighth member of this repo's "assertion that cannot fail" family**,
and it is the exact rule the sixth instance produced: *an assertion must never
call the function — or read the constant — it is asserting about.* The check and
the delete share the predicate, so both sides move together.

### 3. Nine fixed session-id literals collide on a unique index

§7 names one, `cs_test_cronprobe0001` at `:2069`. Verified by grep, it is one of
**nine** fixed `stripe_session_id` literals, on rows seeded through paths that
write **no** `admin_notes` and are therefore in finding 1's blind spot:

| Literal | Written at | Seed path | Carries MARKER? |
| --- | --- | --- | --- |
| `cs_test_cronprobe0001` | `:2069` | expiry `seed` | MARKER goes to **`name`** (`:2028`), not `admin_notes` (`:2031`) |
| `cs_test_webhook00001` | `:2886` | `seedAwaitingPayment` | no |
| `cs_test_webhook00002` | `:2918` | `seedAwaitingPayment` | no |
| `cs_test_webhook00003` | `:2954` | `seedAwaitingPayment` | no |
| `cs_test_stale000000001` | `:3033` | direct INSERT | no |
| `cs_test_happy0001` | `:2469` | — | no |
| `cs_test_twice0001` | `:2544`, `:2552` | — | no |
| `cs_test_clash0001` | `:2583` | — | no |
| `cs_test_late00001` | `:2621` | — | no |
| `cs_test_bk44_stale` / `_live` | `:4108`, `:4126` | `seedAt` | yes — swept |
| `` cs_test_bk33_${refundProbe} `` | `:3224` | already per-run | yes — swept |

The collision is against **`appointments_stripe_session_idx`**,
`UNIQUE (stripe_session_id) WHERE stripe_session_id IS NOT NULL`
(`scripts/migrations/010-payments.ts:127-131`). That is the `23505` the ROADMAP
records, and the reason it kills the run rather than failing a check.

`cs_test_cronprobe0001` is doubly invisible: unswept **and** its seed writes the
marker into the wrong column.

### 4. A crash and a failure are the same exit code, and a crash prints no summary

`:4423-4427`, the only terminal output:

```ts
if (failures > 0) {
  console.error(`\n✗ ${failures} check${failures === 1 ? '' : 's'} failed\n`);
  process.exit(1);
}
console.log('\n✓ admin write-path checks passed\n');
```

There is no `catch` on the top-level `try` (`:437`…`:4375`). On a mid-run
exception the `finally` runs, the error rethrows out of top-level await, and the
process exits **1 with neither summary line printed**.

So `exit 1` means *either* "checks failed" *or* "crashed", and
`grep -c "✗"` returns **0** for a crash. That is the BK-33 measurement failure
exactly. There is also no count of checks *run*, so a crash at 5% and a crash at
95% are indistinguishable from each other and from a clean pass by anything a
harness can read.

**This is why the artifact for this ticket is an exit code plus a summary line
carrying a check count, and never a marker count.**

### 5. `:2114` counts a global sweep, so it reddens on the clock alone

```ts
check(counts.paymentsExpired === 2, `both overdue payments expired, got ${counts.paymentsExpired}`);
```

`counts.paymentsExpired` is the cron's **branch-wide** tally. The assertion is
therefore *"the dev branch contains exactly the two overdue rows this fixture
made"* — a claim about ambient state, not about the sweep.

Any stranded `seedAwaitingPayment` row sets `payment_due_at = now + 6h` (`:275`);
six hours later it is overdue and the next run reports 3. **Nothing changes but
the clock.** And the failure cures itself, because the run that reports it also
*expires* the strays and a `payment_expired` row cannot be swept twice — so it
presents as a flake, and "transient, ignore it" is available every time and
wrong every time.

`requestsExpired` two lines up (`:2109`) is already a floor, with the reasoning
written out. `:2114` is the one that was not converted.

## The fix

Five parts, one file, ~45 lines. **Parts 1–3 and 5 change only what the script
seeds and what it reports. Part 4 is the single assertion-level edit.**

**1 · Per-run probe identity.** `const RUN = Date.now().toString(36)` near
`:158`; every literal in finding 3's table becomes `cs_test_<name>_${RUN}`. The
read at `:3066` already reads the variable, so its assertion still pins.
Collision gone even with wreckage present. ~10 lines.

**2 · Make the marker reachable.** Add `admin_notes: MARKER` to
`seedAwaitingPayment` (`:271`), the expiry `seed` (`:2031` becomes
`${extra.notes ? MARKER + '\n' + extra.notes : MARKER}` — `:2141`'s assertion
uses `.includes`, so it still holds), and the Elapsed / Order / Reapprove /
Goodwill probes (`:1839`, `:2773`, `:3032`, `:3080`). ~8 lines.

**3 · Abort on unswept wreckage, and a `--reset` that can clear it.** After the
pre-run sweep, count the probe rows **by name** and refuse to run if any remain,
naming each one — the abort pattern already proven in
`scripts/verify-booking-commit.ts:352-359`. This is what makes findings 1 and 2
*loud* rather than merely fixed. ~10 lines.

Counting **by name** rather than by the marker is the load-bearing part: a
predicate that reads what `cleanup()` deletes by is finding 2 all over again.
`PROBE_NAMES` is deliberately a separate list, and the query also catches
`name LIKE MARKER%` (the expiry seed's rows) and any `cs_test_%` session.

`--reset` exists because **the legacy wreckage carries no marker and no id any
live process remembers, so nothing in the repo could clear it** — the recovery
was a hand-written DELETE pasted from a comment, which is not a reviewable
artifact and not something a future session can be told to run safely. The
script that stranded the rows is the right thing to own removing them, it already
holds the dev-branch guard (`:84-98`), and it prints what it removed. It exits
immediately afterwards rather than continuing into a run, so a reset can never be
mistaken for a pass.

**4 · Scope `:2114` to the rows the fixture made.** Snapshot the sweep's
predicate over rows **not** in `createdIds` immediately before invoking the cron,
then assert `paymentsExpired === 2 + foreignOverdue`.

**This edits an assertion, and it makes it stricter, not looser.** It replaces an
unscoped global equality with an equality against a measured baseline; it does
not degrade to `>= 2`. Per CLAUDE.md's fixture rule the fixture moves and the
assertion holds — here the assertion was itself the defect, so it is stated
rather than relaxed. The per-row negative pins (`:2107`, `:2111`) already carry
the "did not over-sweep" claim and are untouched. ~6 lines.

**5 · Make a crash announce itself.** `checksRun` incremented in `check()`
(`:190`); a `catch` around the top-level block printing
`✗ CRASHED after N checks (M already failed)` and exiting **2**; both terminal
lines gain the count. **Exit 0 = passed, 1 = checks failed, 2 = crashed**, and
every terminal state prints exactly one summary line. ~12 lines.

- It does not add or remove a single check beyond part 4's scoping.
- It does not fix the sibling scripts. `verify-availability-db.ts:102-121` has

## Why Light is uncomfortable here, and what is being done about it

§7 designates W0 **Light**, and by CLAUDE.md's own definition it fits: no public
write path, no PII, no concurrency, nothing irreversible. Nothing in this ticket
reaches production.

But this script is what *certifies* the tickets that do, and Light means gates
only — so the item whose whole purpose is making other gates trustworthy would be
self-certified by the person who wrote it. That is the shape this repo has paid
for repeatedly.

**Therefore: shipped at Light tier per §7, with one fresh-agent implementation
review anyway**, receiving only this ticket, the diff, and the gate output. The
review's first question is part 4 — the one edit that changes what the script
asserts. Cost is one agent; the alternative is that every red row logged after
this ticket rests on an unreviewed rewrite of the thing measuring them.

## Verification it owes

Every measurement below is **`(exit code, summary line)`**. A row is green only
on exit 0 *and* `✓ admin write-path checks passed (N checks)` with N no lower
than the previous run's. **A marker count is not an accepted measurement in this
ticket**, and neither is "it printed no ✗".

Before each red-first attempt the probe rows are cleared by hand — the suite
under test is the thing being proven non-idempotent, so it cannot be trusted to
prepare its own ground:

```sql
DELETE FROM appointments
 WHERE name IN ('MarkPaid Probe','Elapsed Probe','Order Probe',
                'Reapprove Probe','Goodwill Probe','BK33 Probe','BK44 Probe')
    OR admin_notes LIKE 'BK-08 verification%'
    OR stripe_session_id LIKE 'cs_test_%';
```

**Each failure mode is dirtied separately.** Two consecutive runs from one
dirtying is *not* the artifact: the first run consumes the wreckage — it expires
the strays, and an expired row cannot be swept twice — so the second run is green
for the wrong reason. That is the ROADMAP's own recorded flake, and reproducing
it as an artifact would be this ticket committing the defect it exists to remove.

## Implementation review — 2026-08-31

Fresh agent, given only this ticket, the diff and the gate output. **No
blockers. Five should-fix, six nits. All five should-fix accepted and fixed;
nothing refused, nothing disputed.**

The reviewer independently verified the ticket's two load-bearing claims rather
than taking them: that only one assertion changed semantics and that it became
stricter, and that the new abort predicate is genuinely disjoint from what
`cleanup()` deletes by (so it is not finding 2 recreated).

| # | Finding | Resolution |
| --- | --- | --- |
| S1 | `--reset` exited **0** — the same code as a full pass, for a run that executes zero checks. The ticket's own claim that "a reset can never be mistaken for a pass" was **false as written** for anything reading the exit code | Exits **3** |
| S2 | **`throw null` / `throw undefined` / bare `Promise.reject()` left `crashed` falsy, so the catch swallowed it and the script exited 0 GREEN** — where the unfixed script exited 1. Strictly worse than the defect being fixed | Separate `didCrash` flag; every branch tests the flag, never the value. Red-observed as R7 |
| S3 | An exception **inside the `finally`** escaped both the catch and the terminal block — exit 1, no summary, and the recorded crash destroyed on the way out. The leftover query runs immediately after a crash, i.e. exactly when the schema may be mid-mutation | `finally` body wrapped; a throw there is promoted to the crash path if nothing is recorded yet |
| S4 | `--reset`'s blast radius was wider than its report: it deletes on `cs_test_%`, which also matches a real dev-branch booking taken through Stripe **test-mode** Checkout, while printing only a count | Prints every deleted row by id/name/status, matching the abort. Dev-branch guard confirmed to cover the path |
| S5 | A **failed** pre-run cleanup was swallowed into zeros with no marker and the run proceeded; post-fix wreckage carries MARKER and may carry no probe name, so it was invisible to both the failed delete and the abort | `preSweepFailed` flag, plus an `admin_notes` arm on the strays query — safe here because it runs *after* the delete, so it detects a failed delete rather than co-moving with it |

Nits taken: the code comments said 22 stranded rows where the ticket said 34
(**34 is correct** — the first count was mine and it was wrong, taken with a
query that searched `admin_notes` while the expiry seed writes its marker into
`name`; the script's own abort found the other twelve, which is the same blind
spot this ticket is about, committed by its author while writing it); two
`failures++` sites that did not increment `checksRun`, so `N failed of M run`
could report a failure outside the M; and SIGINT/SIGTERM exiting 130 with no
summary, which left the one terminal state that **strands rows** as the only
silent one.

Nit taken with a design change rather than a note: `expire-payments.ts` sweeps
`LIMIT 25`, so past ~23 foreign overdue rows the new equality is unsatisfiable
and would redden for the batch cap rather than for the sweep. The arm now
**reports itself inert** and says so, following `verify-availability-db.ts`'s
pattern — inert is a state the reader has to be told about, because silently
skipping is how an assertion stops existing.

Nit not taken: the reviewer noted the clock-skew window between the Postgres
`now()` baseline and the cron's Node-side `new Date()`. Real, and orders of
magnitude tighter than the global equality it replaces. Left, and recorded here.

## Assumptions log

1. **The R-series restarts at R1 for this ticket.** Red-row labels are per-ticket
   in this repo (BK-10 runs to R43, BK-33 uses R24 and R30–R33); they are not a
   global sequence.
2. **`RUN` uses wall-clock, not a UUID.** `Date.now().toString(36)` is enough for
   a single-writer dev branch and keeps the ids greppable. Two runs starting in
   the same millisecond would collide; that requires deliberate parallelism,
   which the shared slot pool already forbids.
3. **Exit code 2 for a crash is new vocabulary in this repo.** No existing
   harness reads exit codes numerically — they read truthiness — so nothing
   breaks; 2 is chosen so a future harness *can* tell the cases apart.
