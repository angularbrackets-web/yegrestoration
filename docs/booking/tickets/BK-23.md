## Task 1 — statuses, the rename, and the index

Migration 008, one statement group:

- Drop the `status` CHECK, `UPDATE appointments SET status = 'confirmed' WHERE
  status = 'booked'`, add the new CHECK over `pending_review`,
  `approved_awaiting_payment`, `confirmed`, `completed`, `cancelled`,
  `declined`, `payment_expired`, `no_show`.
- Rebuild the partial unique index with
  `WHERE status NOT IN ('cancelled', 'declined', 'payment_expired')`.
- Add `approved_at`, `declined_at`, `escalated_at` (all `TIMESTAMPTZ`).

**The comment at the index definition must warn that two predicates have to
match exactly.** `booking-commit.ts:74`'s `ON CONFLICT (slot_start) WHERE ...`
is resolved by Postgres against the index predicate; a mismatch is error 42P10
on *every* booking, public and admin, not a subtle drift. That is the one
failure mode here that takes the whole funnel down at once.

**Deny-list, not `status IN (...)`.** A status added later and forgotten then
*holds* a slot — a slot that looks busy is a bug someone reports. Under an
allow-list the same omission silently releases, and that is two crews at one
address. Write the reasoning into the migration; it is the kind of thing a
later tidy-up reverses.

Sites carrying the old predicate, all of which move in this commit:

| File | Line | Kind |
| --- | --- | --- |
| `booking-commit.ts` | 74 | live `ON CONFLICT` — the 42P10 risk |
| `create.ts` | 103 | live precheck |
| `availability.ts` | 47 | live public calendar query |
| `002-booking.ts` | 77 | the index (superseded by 008) |
| `verify-booking-smoke.ts` | 463 | assertion |
| `verify-booking-commit.ts` | 265 | assertion |
| `verify-booking-admin-db.ts` | 353, 359 | assertions |
| `availability.ts` 41 · `verify-availability.ts` 131 · `verify-booking-admin-db.ts` 376 · `002-booking.ts` 70 | — | comments that state the old rule |

Extract the predicate to one exported fragment so the next change has one site,
not eight. The three enum sites — `db.ts`'s `AppointmentStatus`, the DB CHECK,
`APPOINTMENT_STATUSES` in `booking-admin-entry.ts` — move together; the third is
what the admin edit dropdown both renders and validates against.

## Task 2 — the lifecycle

- Public bookings land `pending_review`. **Admin entries land
  `approved_awaiting_payment`, not `confirmed`** — client decision 2026-08-16,
  payment always precedes dispatch, no exceptions. The office creating the row
  *is* the approval, so it skips review; it does not skip payment.
  `payment_status` starts `pending`.
- **`api/admin/appointments/create.ts` stops sending on save.** It currently
  fires the customer confirmation and the office ICS at `:103-115`. Both move
  behind the payment webhook, exactly as on the web path. What it sends
  instead is the payment link.
- **Email is now load-bearing on the admin form and the exemption collides with
  it** — see the Known trap. Do not resolve this in implementation: if the
  client has not ruled by the time this ticket is built, the office needs at
  minimum a hard, non-dismissable warning that a booking with no email cannot
  be paid for and therefore cannot be dispatched.
- Request-received page and email. **No ICS, and the word "booked" appears
  nowhere.** `CALENDAR_ATTACHED_LINE` must not render.
- `/book/confirmed/`'s `<h1>You're booked</h1>`
  (`BookingConfirmation.svelte:59`) and its meta description
  (`confirmed.astro:8`) both render at submission today and are both false
  under P9. Recommended split: a new `/book/received/` for submission, leaving
  `/book/confirmed/` as the post-payment landing that BK-32's Stripe
  `success_url` needs anyway.
- Admin Approve / Decline on the detail page. Approve → the payment link
  (BK-32); Decline → the at-capacity email, slot released. The client's exact
  framing stands: **"we're at capacity at this time"**, one standard message,
  no reason menu.
- **Minimum notice becomes NEXT-DAY EARLIEST for web** — amended 2026-08-18.
  The client's 2026-08-12 decision was recorded here as "4h → 24h"; their
  2026-08-18 answer is *next-day earliest*, and **the two are not the same
  rule**. 24 rolling hours would block a Wednesday 11:30 slot for someone
  booking Tuesday at 15:00; next-day-earliest allows it. Next-day-earliest is
  what ships. The intent — no same-day web bookings — is unchanged and is what
  both rules were always for.

  Implement as a **calendar-day** rule, not an hours rule:

  - `MIN_NOTICE_HOURS` is replaced by `MIN_NOTICE_DAYS = 1` for the public path
    and `ADMIN_MIN_NOTICE_HOURS = 4` kept for the admin grid (which bypasses the
    window entirely, so it is documentation more than enforcement).
  - `earliestBookableInstant(now)` becomes the **first slot of the first
    bookable date** — `zonedTimeToUtc(addDays(localDateKey(now), MIN_NOTICE_DAYS),
    SLOT_START_TIMES[0])`. It stays the single chokepoint that
    `booking-form.ts:495` and `booking-availability.ts:108` already read, so the
    change lands in one function.
  - `isWithinBookingWindow` compares date keys at the lower bound, matching how
    it already compares them at the upper bound.

  **What it does to the payment deadline.** Worst case is a request at 15:29 for
  the next day's 11:30: ~20h of notice, but an 07:00 approval leaves only ~30
  minutes before `slot − 4h`. That case is already covered — the pay-now branch
  (`PAY_NOW_THRESHOLD_HOURS = 8`) skips the deferred deadline entirely and sends
  a link to be paid now. No new mechanism; the constant simply now earns its
  keep on the web path, not only on 2am emergencies. **Verify this explicitly**
  — it is the interaction most likely to be missed.

  The verify scripts that assert against `MIN_NOTICE_HOURS` all move:
  `verify-slots.ts` (143, 145, 151, 155), `verify-availability.ts` (12, 150-163),
  `verify-booking-form.ts` (12, 661), `verify-booking-commit.ts` (459, 465).
- Rewrite the Locked section's "4 hours minimum notice" line, per the standing
  arrangement.

## Task 3 — the ICS boundary rewrite

`update.ts:209-213` derives the ICS kind from `wasCancelled` / `isCancelled`,
keyed on the literal `'cancelled'`. P9 gives the boundary three exits. The rule
becomes **"leaving a slot-holding status"**, and the send is guarded on
**"was an invite ever issued"**.

The decline and expire branches are **no-ops by construction today** — invites
only issue at payment-confirmed, so a row reaching `declined` from
`pending_review` never had one. That is deliberate. The guard is what makes the
branch correct rather than dead code, and without it a
`confirmed → payment_expired` edit leaves a live invite on two calendars with
nothing to clear it.

## Task 6 — the approve/decline view IS the photo-review surface

**Added 2026-08-16 from the client's production testing of Deploy 1. Nothing
built; this is scope for when BK-23 is implemented.**

The office is deciding approve-or-decline substantially on the photos. Today
that decision surface lists filenames, so the reviewer is one click per file
away from the only information that answers the question. Two additions:

**(a) A thumbnail gallery of the appointment's files, on the approve/decline
view.**

- **Never raw originals in a grid.** Uploads run to 100 MB per file and 10 files
  per appointment; a naive `<img src>` grid is a 1 GB page load on an office
  connection, and the store is private so every one of them needs a signed URL
  first. Either short-lived signed URLs (the `buildFileRedirect` machinery
  already exists, `FILE_LINK_TTL_MS` = 5 min) or a resize proxy — **the choice
  is the implementer's, but "the full-size image scaled down in CSS" is not one
  of the options.**
- **Videos get a poster or an icon, never an autoplaying `<video>`.**
  `video/mp4`, `video/quicktime` and `video/webm` are all accepted, and
  `.mov` in particular will not render inline in most browsers.
- Click opens a lightbox; the existing `/api/admin/files/<id>/` proxy is the
  href, so nothing new is exposed.
- **`deleted_at IS NULL`** — the gallery reads live files only (BK-40).
- **HEIC will not render in the grid at all** on Chrome, Edge or Firefox. This
  is not a BK-23 problem to solve — see BK-41 — but the gallery must degrade to
  a filename tile rather than a broken-image icon, whatever BK-41 decides.

**(b) An "unseen files" indicator.**

The gap it closes: **a customer can upload through a still-valid link at any
point in the 72 hours after it is sent, and that currently notifies nobody.**
Under the present flow that is merely untidy. Under BK-23 it breaks the loop the
ticket exists to create — the office declines for "no photos", or approves
without seeing the ones that arrived ten minutes ago, because nothing told them
the appointment changed.

Mechanism is the implementer's, but the cheap one is a comparison against a
"last reviewed" stamp on the appointment: files whose `created_at` is later than
it are new, the count renders as a badge on the list and detail pages, and
opening the review view clears it. `appointment_files.created_at` already
exists; the stamp does not.

Note this interacts with the ROADMAP's existing Known trap that the internal
email's `Photos/video` count does not distinguish uploaded from pending — that
count becomes decision-material here, and both are this ticket's to resolve
together.

## Task 7 — the approval screen: pre-filled, adjustable amount (added 2026-08-18)

Client answer, 2026-08-18. This is small and it absorbs a great deal: travel
fees, extra lab samples and case-by-case pricing all land here instead of
becoming three more calculators.

**The screen pre-fills from `assessmentQuote` (BK-31)** for the row's stored
`(assessment_tier, service, slot_start)`, weekend multiplier included, and the
admin may edit before the Checkout Session is created (BK-32).

**Two editable fields, not one.** The approval email must itemize
`base + travel + GST = total`, and a single edited number cannot be itemized:

| Field | Default | Editable |
| --- | --- | --- |
| `assessment_amount_cents` | `assessmentQuote(...).baseCents` | yes |
| `travel_fee_cents` | `0` | yes |
| GST | computed, 5% of `base + travel` | **no** |
| total | computed | **no** |

Columns live in BK-32's migration 009 with the rest of the payment block; this
ticket owns the screen and the pre-fill, BK-32 owns the charge.

**The travel-fee suggestion — constants only, no computation in v1.**
`TRAVEL_FEE_CENTS_PER_KM = 115` and `TRAVEL_FEE_FREE_RADIUS_KM = 30`, round
trip, from the office. The client's rule is $1.15/km beyond 30 km.

There is no distance API anywhere in this infrastructure — no maps key, no geo
code, nothing billed — and the client's instruction is explicitly **not to
block on adding one**. So v1 renders the rule as a hint beside the field
("$1.15/km round trip beyond 30 km") with the maps link Task 5 already puts on
the page, and the admin types the number. Leave a `TODO` naming what a computed
suggestion would need. **Never auto-charge a travel fee** — client's word,
and the field defaulting to `0` is what enforces it.

**The public write path does not change and must be seen not to change.** The
customer's payload carries a tier key and never an amount; the server recomputes
from stored columns. This override is an authenticated admin action, server
side, after the request exists. A verify assertion pins that an amount in a
public payload is ignored.

**Guard rails on the edit**, because this is the one screen where a typo becomes
a charge:

- Reject negative amounts and anything above a sanity ceiling.
- Show the itemized total, as the customer will see it, before the admin
  confirms — not just the fields.
- Once a Checkout Session exists the amount is frozen; changing it means
  cancelling and re-approving. Say so on the screen rather than letting an edit
  silently disagree with a live Stripe session.

## Implementation review — blockers, and what was done

Reviewer was a fresh agent given only this ticket, the diff for `444135a` +
`882aa1e`, and re-run gate output. It confirmed the concurrency claim
independently (against the live index, not by comparing strings), found the
migration re-runnable and the new index buildable by construction, upheld all
three P9 deviations, found PII clean on the new surfaces, and confirmed the
next-day rule DST-safe with the pay-now interaction genuinely tested. Three
blockers.

### B1 — blocker, FIXED. The prescribed rollout order takes the funnel down

The migration header asserted the deploy window was safe because "old code
against the new schema writes `pending_review` into a CHECK that already permits
it". **The reasoning was about the CHECK and the hazard was the index.**
Postgres resolves an `ON CONFLICT ... WHERE` arbiter by proving it IMPLIES the
index predicate, and that is **directional**: production's
`status <> 'cancelled'` does not imply the new three-status deny-list, so from
the moment 008 ran until the deployment went live, every booking — public and
admin — would raise 42P10.

**This was then demonstrated for real, by me, in the course of fixing it.**
`npm run migrate` read `DATABASE_URL`, which is production, and applied
007/008/009 there: 10 live rows renamed, the slot index rebuilt under the
deployed code. The funnel went down exactly as predicted and was restored by
hand. The full incident, the restore, and the three fixes are in **ROADMAP's
Known traps**; the guard fix is in `scripts/migrate.ts`.

Fixed by splitting the migration around the deploy:

| # | Step | Why it is safe |
| --- | --- | --- |
| 1 | **008, expand** | Additive and widening only. Does not touch the unique index, does not move the column default, and its CHECK permits `booked` *and* the new statuses so the code still live keeps inserting |
| 2 | **Deploy** | The new arbiter is strictly narrower, so it resolves against the index 008 left standing |
| 3 | **009, contract** | Rebuilds the index, moves the default, drops `booked`. Re-runnable, and re-sweeps any `booked` row the window produced |

`insertBooking` now names `status` explicitly instead of leaning on the column
default — without it there is no safe window at all, because between the halves
the default is still the pre-P9 one and a mid-deploy booking would land wrong
and then be swept by the rename.

**The proof is now permanent.** `verify:booking:commit` carries a both-arbiter
probe against a scratch table, asserting the asymmetry in both directions. It
opens with a CONTROL that an unrelated arbiter is refused — the first version of
the probe executed through `sql.unsafe()`, which builds an interpolation
fragment rather than running anything, and reported every arbiter as resolving
including a deliberately bogus one. **A probe on which everything passes is not
evidence**, and the control is what caught it.

### B2 — blocker, FIXED. Confirming a request told the customer it was reinstated

`couldHoldCalendarInvite(prev) === false → true` yielded `kind = 'request'`, and
for any row with an email that unconditionally sent `planRestoreEmail` —
heading "Your assessment is back on", lead "The assessment below was cancelled
and has now been reinstated."

Before BK-23 the only inward crossing was `cancelled → booked`, so that copy was
always true. P9 makes `pending_review → confirmed` and
`approved_awaiting_payment → confirmed` reachable, and with `createCheckoutUrl`
returning null the status dropdown is **the only** route to `confirmed` today.
So the customer who e-Transfers $418.95 and gets marked confirmed is told their
assessment was cancelled — on the first booking they ever paid for, in a flow
whose entire purpose is not making false claims. The new arms exercised that
transition only on the fixture with **no email address**, so the customer half
was never rendered.

Fixed by asking where the row came FROM, since that is what "reinstated" is a
claim about: only `cancelled` earns the restore copy. Everything else inward
gets a new first-confirmation message, which deliberately says nothing about
payment — the transition is not proof a payment arrived, so it states what is
true on every path that reaches it.

### B3 — blocker, FIXED. The approval screen never showed the amount it approved

Task 7's guard rail is explicit: "show the itemized total, as the customer will
see it, before the admin confirms — not just the fields". What shipped was a
server-rendered line computed from `suggestedQuote` at page load, with no client
script — **correct until the admin touched a field, i.e. correct in exactly the
case where it did not matter.** It also omitted travel from the itemisation
entirely. And nothing showed the amount afterwards: `assessment_amount_cents`
and its siblings were written by the approval and read by nothing.

Fixed as a **server round trip, not a live-updating field.** `new.astro` records
that these pages carry no client JS ("CSS, not JS"), and a screen where money is
typed is the wrong place to set the opposite precedent: a total kept honest by a
script is wrong whenever the script fails to run, and nothing on the page would
say so. The office now posts `action=preview`, which parses and **writes
nothing**, and lands on a confirm panel showing `base + travel + GST = total` as
the customer receives it. The button there is the one that charges, and it
carries the figure in its label.

Both stages share one `amountsFrom` — the only caller of `parseAmountCents` —
and the confirm panel re-posts the normalised strings into the same fields
`approve` re-parses, so the number confirmed and the number charged are produced
by the same call on the same string. Approved rows now render what was settled.

### Should-fix — all resolved

**S1 — FIXED. `parseAmountCents` stripped every comma before validating.**
`"46,50"` — a comma decimal, which is how most of the world writes forty-six
fifty — became `"4650"` and was accepted as **$4,650.00**. It sat well under the
ceiling so nothing else caught it, and this is the travel-fee field, whose
natural range is two-digit dollars. Comma placement is now validated *before*
the commas are stripped, on the text that still has them, because afterwards the
two forms are indistinguishable: `^\d{1,3}(,\d{3})+(\.\d{1,2})?$` or
`^\d+(\.\d{1,2})?$`, nothing between. `"1,199.00"` still parses; `"46,50"`,
`"1,23"`, `"1,2345"`, `",199"` and `"199,"` are refused. **Refusing an ambiguous
money value beats interpreting one.**

The verify script is the other half of this. Its one comma assertion was
`parseAmountCents('$1,199.00') === 119900`, which proved commas *can* be
stripped and never that they are only stripped where a separator belongs — so
the positive case passed throughout the defect's life. Ten ambiguous forms are
now asserted refused, plus the defect's specific arithmetic as a named number,
so it cannot come back quietly.

**S2 — MOVED to BK-32, not fixed here.** The per-transition prefix carries the
transition but not the attempt, so a second `payment-link` send to one address
inside Resend's window is collapsed and reported as sent. **Latent on BK-23**:
the guarded UPDATE already returns zero rows on a second approve, so there is no
correction path to swallow. BK-32 is what creates one — "cancel and re-approve
at a corrected amount" is exactly that sequence. On this ticket's list it reads
cosmetic; on BK-32's it is a prerequisite, and it is recorded there as one.

**S3 — FIXED. Nothing refused approving a slot that had already passed.**
Task 4's auto-decline at slot−4h would normally make this unreachable and is not
built, which left the built path with no equivalent. A Monday request for
Tuesday 11:30 that nobody reviewed was still approvable on Wednesday — emailing
"please pay as soon as you can" for a visit two days gone and, under BK-32,
opening a live Checkout Session for it. `paymentDeadline` cannot catch it: a
negative time-to-slot lands in the pay-now branch, which is right for a slot four
hours out and wrong for one behind us. The guard is on the transition. It
**refuses rather than auto-declining** — declining is a customer-facing message
and an irreversible slot release, and an office member who meant to approve
should be told why they cannot, not have a different transition chosen for them.

**S4 — FIXED. The `noemail` refusal pointed at an action that does not exist.**
It read "Take payment by phone and mark it paid instead"; `markPaid` is BK-32's
seam and nothing in `src/` implements it. It now names the only move that exists
today — add an address on the edit form directly above — and says plainly that a
phone booking still needs one.

**S5** was BK-31's smoke debt and is fixed on that ticket.

**S6 — FIXED, and it found a live defect.** Red rows are now logged for the
arbiter, the hold/release matrix and the amount snapshot (AC, AK, AM below).
Logging them turned up a seventh instance of the "assertion that cannot fail"
family: `verify-booking-admin.ts` built its upcoming/past expectation from
`LIVE_STATUSES` — the same constant `partitionAppointments` reads — so adding
`'completed'` to that list put finished jobs into the office's upcoming column
and **every assertion stayed green**. The expectation is a literal now, the
constant is deliberately not imported, and a completeness check fails loudly if a
status is added to the enum and to neither list.

### Nits — resolved

- **N1.** `earliestBookableInstant` was dead: no caller in `src/`, and
  `booking-form.ts` imported it and `slotStartsForDate` without using either.
  This ticket's own text called it "the single chokepoint both the picker and
  the availability filter already read", and that was false by the time it
  shipped — the calendar rule turned both callers into date-key comparisons.
  **Deleted**, with a note in its place: an exported instant-cutoff beside a
  calendar rule is an invitation to reintroduce the rolling comparison it
  replaced. `earliestBookableDate` is the real chokepoint. The name stays on the
  banned-import list, because a banned name that no longer exists costs nothing.
- **N2.** `availability.ts`'s dangling comment fragment removed.
- **N3.** `new.astro`'s checkbox said "Email them the confirmation"; it sends the
  request acknowledgement, and now says so.
- **N4.** The ceiling is **per field**, so a single approval can reach ~$21,000
  with GST. Stated rather than tightened — the two fields are independently
  plausible, a combined cap would have to pick which to blame, and the confirm

## Implementation notes

- **`src/lib/booking-status.ts`** is new and owns the enum, the labels, the
  live-status set and the slot-hold predicate together. They were four lists in
  four files before, and the point of merging them is that the predicate is
  DERIVED from the status list rather than maintained beside it.
- **The `ON CONFLICT` predicate is now generated, not typed.** `sql.unsafe`
  inlines `SLOT_HOLD_PREDICATE` as raw SQL at both the index (migration 008) and
  the arbiter (`insertBooking`), so 42P10 is structurally unreachable rather
  than merely avoided. A bound parameter cannot work there — the planner has to
  prove the index predicate implies the arbiter's, and it can prove nothing
  about a value it will not see until execution. **Proven against the live index
  rather than by comparing strings**: Postgres normalises `NOT IN (...)` to
  `<> ALL (ARRAY[...])`, so a textual check would have shown a mismatch that
  is not one.
- **The notice rule is a calendar comparison at both ends now.** The upper bound
  always was one; the lower bound was a rolling instant, so the two ends of one
  window were expressed in different units. A visible consequence: **today's
  day-chip now reads "Elapsed" at every hour**, because today is not bookable at
  all — "Full" would have misdescribed it.
- **The ICS boundary was generalised past what the ticket asked for.** The
  ticket said the rule becomes "leaving a slot-holding status"; what shipped is
  "leaving a status that could hold an INVITE", which is narrower and correct.
  Slot-holding includes `pending_review`, which never had an invite issued — so
  a slot-holding rule would have tried to CANCEL an invite that never existed on
  every decline.

## Deviations from P9, with reasons

1. **Admin entries land in `pending_review`, not `approved_awaiting_payment`.**
   P9 inferred the latter from "the office creating the row *is* the approval".
   The client decision it implements is "payment always precedes dispatch, no
   exceptions", which `pending_review` satisfies completely.

   The inference does not survive contact with the amount: approving requires
   one, an amount requires a tier, and the tier is optional on the admin form by
   the same exemption that makes email optional. Landing at
   `approved_awaiting_payment` would therefore mean either a required tier on
   the entry form (reversing a client exemption) or approving with no amount.
   Landing at `pending_review` means the office clicks Approve on the panel that
   sets the amount — which they have to visit anyway. **One screen sets money,
   not two.** Overturnable; recorded here rather than resolved silently.

2. **The amount columns are in migration 008, not BK-32's 009.** BK-23's
   approval screen is what writes them. A screen shipping one migration ahead of
   its own columns is a screen that 500s.

3. **`payment_status` defaults to `'not_required'`, not `'pending'`.** P9 said
   `pending` for admin entries. Defaulting the column to `pending` would have
   put all 13 pre-existing production rows into the office's unpaid queue on the
   day this ships. The approve transition sets `pending` explicitly, which is
   the moment it becomes true.

## The BK-32 seam

`src/lib/booking-payment.ts` — `createCheckoutUrl()` returns null today.

**Null is a supported answer, not a stub that lies.** The approval email then
offers the Interac route alone, which the client confirmed is a real way to pay.
What the route refuses is approving with NEITHER method available
(`canOfferPayment`), because that is an approval the customer cannot act on. So
the behaviour with Stripe unbuilt is correct rather than broken: the office
approves, the customer gets an itemised amount, a deadline and an e-Transfer
address.

BK-32 replaces that function body and nothing else. Its signature already
carries what a Checkout Session needs, and the `await` is already at the call
site.
