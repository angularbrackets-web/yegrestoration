# BK-47 — The appointment screen buries the decision and still speaks pre-P9

**Status:** draft 2026-08-20
**Phase:** P9 (post-deploy) · **Tier:** Light — layout, ordering and copy. No
write path changes, no money, no mail. **Deploy:** 3. **Migration:** none.

Found 2026-08-20 in the same end-to-end read of `/admin/appointments/[id]` that
produced BK-46. These four are workflow and vocabulary; none of them is wrong
about money. Split from BK-46 deliberately so a copy pass does not have to run
at Reviewed tier behind a money-correctness fix.

## The four

### 1. The decision is the second-to-last thing on the page

On a `pending_review` row the panels render in this order:

| # | Panel | What it is |
| --- | --- | --- |
| 1 | Visit | reference |
| 2 | Customer | reference |
| 3 | Notifications | reference |
| 4 | Files | reference |
| 5 | Get photos | an action, but a minor one |
| 6 | **Review this request** | **the decision** |
| 7 | Update | the editor |

**The user confirmed 2026-08-20 that the office arrives from the Appointments
list and opens one booking to act on it.** So the single thing the screen is
open for is five panels down, and the office scrolls past four reference cards
and an upload widget to reach it. The same is true of the Payment panel on an
`approved_awaiting_payment` row.

This is the other half of BK-44's complaint. BK-44 fixes *which control is the
decision*; this fixes *where it is*.

### 2. Two amount forms are live at once during the confirm step

Posting `action=preview` renders "Confirm the amount" — and leaves the full
"Review this request" form standing directly beneath it, fields populated, with
its own **"Review the amount →"** button. Two panels, both amber-bordered, both
about the same amount, and the page does not say which one is the pending step.

The lower form is redundant while confirming: the top panel already carries a
**"Change the amounts"** link, and that link returns to exactly the view where
the lower form is the only one on screen. Suppressing the input form while
`confirming` is truthful and costs nothing.

### 3. "Booked" is still the header's word for an unpaid request

A `pending_review` row's header reads **BOOKED · Aug 19, 2026, 11:07 p.m.** and
**SOURCE · Booked online**. The label means `created_at`.

`booking-status.ts` killed that word under P9 on purpose:

> *"`booked` is GONE, renamed to `confirmed` by migration 008. Under prepay,
> 'booked' was the word for the thing that had not happened yet: a request looks
> booked to the customer and is unpaid to us. Keeping the old value alongside
> the new ones would have invited exactly the confusion the flow exists to
> remove."*

The enum was renamed; **this sentence was not**, because it is a field label
rather than a constant. That is verbatim the trap CLAUDE.md records from BK-36:
*"grep the claim across `src/`, not the constants that state it."* The rename
had no constant to follow here.

Low severity — the audience is the office, not the customer, and no decision
turns on it. It is in scope because it is the same word the whole deploy exists
to stop using, sitting on the deploy's own admin screen.

### 4. "Reminder — Not sent" advertises a feature that does not exist

The Notifications panel renders a Reminder row on every appointment, reading
**Not sent** whenever `reminder_sent_at` is null — which is every row, because
reminders are BK-06, Twilio-gated, and scheduled for deploy 4.

"Not sent" reads as a delivery that failed or was forgotten. Nothing was
supposed to have been sent. The row should say what is true, or not render
until the feature exists.

## Out of scope, deliberately

- **Anything about the amounts themselves** — BK-46 owns all four money
  findings, including the header total. If this ticket touches the header at
  all it is the `BOOKED` label and nothing else, and it must not conflict with
  BK-46's rewrite of the same block. **Build BK-46 first.**
- **The Status dropdown and panel legibility** — BK-44.
- **The "Get photos" panel rendering on completed rows.** Checked; it is
  deliberate and useful (photos arrive after the visit as often as before it).
  Not a finding, recorded here so the next reader does not re-raise it.

## Risk areas for the reviewer

- Panel order is the only structural change, and it must not move a *reference*
  panel below the fold that the office needs while acting — Customer's phone
  number is read during the same call as the decision. Moving the action panel
  up is safer than moving reference panels down.
- Finding 2 changes what renders on a `confirm=1` URL. That URL is reachable
  by hand and by back-button; the suppressed form must not become the only
  route to correcting an amount.
- Finding 3 is a label rename on a shared header block that BK-46 also edits.
  Sequencing, not correctness.

## Verification it owes

- A red row proving the action panel precedes the reference panels for each
  actionable status.
- A red row proving the input form does not render while `confirming`.
- A copy assertion for the retired vocabulary, pinned to the **claim shape**
  rather than to a constant name — `verify-cutover.ts`'s `BOOKED_CLAIM_SHAPES`
  is the pattern, and this is the fifth surface it should have covered.

## Assumptions log

- **2026-08-20, user:** the office works list-first, opening one booking at a
  time to act on it. This is what ranks finding 1 first and argues for moving
  the action panel up rather than adding a sticky action bar.
