# BK-01 — Availability computation + `GET /api/booking/availability/`

**Status:** draft
**Phase:** P2 · **Tier:** Standard · **Depends on:** P1

Tier is Standard rather than Heavy despite being a public endpoint: it is
read-only, writes nothing, and exposes only free/busy counts — no PII, no
customer data, no irreversible effect.

## Goal

Give the date/time picker (BK-03) a single source of truth for what can be
booked, computed server-side from the same rules the commit endpoint (BK-02)
will validate against.

## Scope

1. `src/lib/booking-availability.ts` — a **pure** function that takes an
   explicit clock plus already-fetched booked slots and blackout days, and
   returns the availability for the booking window. No DB, no `new Date()`
   default inside the computation, no environment access. This is what makes it
   testable without a database and importable from a Svelte island.
2. `src/pages/api/booking/availability.ts` — a thin endpoint: read the two
   tables for the window, hand them to the pure function, serialise, set cache
   headers.
3. `scripts/verify-availability.ts` — property checks over the pure function
   with an injected clock, in the shape of the existing `verify-slots.ts`.
4. Add `verify:availability` to package.json scripts.

## Out of scope

- Any UI. The picker is BK-03.
- Creating a booking, or holding/reserving a slot. BK-02.
- Admin-visible availability (admin can book outside the public window).
- Blackout-date management UI. BK-08.

## Design notes

- **Availability is advisory, not a reservation.** Two visitors can both be shown
  the same free slot. The partial unique index in BK-02 is the only real guard,
  and BK-02 must translate its conflict into a friendly "just taken" response.
  Do not add locking here.
- Reuse `bookableDateRange`, `slotStartsForDate`, `isClosedWeekday`, and
  `isWithinBookingWindow` from `booking-time.ts`. Do not re-derive the grid.
- One query for booked slots (`status <> 'cancelled'` and `slot_start` inside the
  window) and one for blackout days. Not one per day.
- Response must not be cached by the CDN — a slot booked a second ago has to
  disappear. `Cache-Control: no-store`.
- Endpoint path needs its trailing slash, and a `BOOKING_AVAILABILITY_ENDPOINT`
  constant alongside the other two in `booking-config.ts`.

## Acceptance criteria

1. Returns every date in the booking window, each with its bookable slots, so the
   picker can render and disable days without a second call.
2. A slot is excluded when any of these hold: the weekday is closed (Friday), the
   day has a `blackout_dates` row, a non-cancelled appointment already occupies
   that `slot_start`, or the slot falls outside the 4-hour/14-day window.
3. A cancelled appointment's slot is offered again.
4. Slot instants are correct across both DST transitions — the local wall clock
   stays 11:30–15:30 on either side of the change.
5. Times are returned as both a UTC ISO instant and a pre-formatted
   America/Edmonton label, so the client never re-derives the timezone.
6. Blackout *reasons* are never in the response. Blocked days are simply empty.
7. Response carries `Cache-Control: no-store`.
8. A failed DB query answers **500 with an error body** and logs the cause. It
   never degrades to an empty or partial calendar.
9. A day whose every slot is taken still appears, with an empty slot list.
10. The pure function is deterministic for a given clock and input set.

## Verification

- `npm run typecheck` and `npm run build` clean.
- `npm run verify:availability` — asserts, against a fixed injected clock:
  closed Fridays, blackout exclusion, booked-slot exclusion, cancelled-slot
  re-offer, the 4-hour boundary on both sides, the 14-day horizon on both sides,
  and both 2026 DST transitions.
- Manual: `curl` the endpoint on the dev server and eyeball one real day.

## Risks

- Getting "now" from the server while the visitor's device clock differs — the
  picker must render what the server sent rather than filtering again locally,
  or the two will disagree at the 4-hour boundary. Flag this for BK-03.
- The window is computed at request time, so a form left open past midnight can
  submit a stale slot. BK-02 revalidates; the picker should refetch on submit.

## Assumptions log

- **Full-window response, not just free days.** The picker needs to grey out
  closed and full days, so returning every date with a possibly-empty slot list
  is cheaper than a second call. ~14 dates × 5 slots — trivial payload.
- **No rate limiting on this endpoint.** It is read-only and hits two indexed
  queries. Revisit if it is ever abused; `rate-limit.ts` is available.
- **DB failure is a 500, not an empty calendar.** A silent empty response is
  indistinguishable from "fully booked", which would quietly turn away every
  visitor while looking healthy. Fail loudly; the picker shows an error state.
- **No `reason` field for excluded slots.** Telling the public "blacked out" vs
  "already booked" leaks the schedule. Absent means unavailable, full stop.
