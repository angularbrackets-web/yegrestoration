Reviewed because it mints read credentials for the private Blob store on
request, from a route that serves customer PII (damage photos of people's
homes). Risk areas, in the order a reviewer should weight them:

1. **Signed-token scope.** Every issued token must be scoped to **one exact
   pathname**, `get`-only, with a short expiry. The SDK's `issueSignedToken`
   defaults `pathname` to a whole-store `"*"` wildcard when omitted — an
   omitted argument is a token for every customer's photos, so the scope must
   be asserted, not assumed.
2. **No client-controlled pathname.** The route takes a numeric file id and
   reads the pathname from the `appointment_files` row. The request must have
   no way to influence which pathname gets signed — no pathname, no filename,
   no query fallback. (The upload side already treats client pathnames as
   hostile; the read side must not reintroduce them.)
3. **Auth coverage.** The route lives under `/api/admin/`, protected by
   prefix middleware like every BK-07/08 surface. The redirect it answers
   with is a *capability*: anyone holding the URL can fetch that one blob
   until expiry. Short TTL bounds that; see Assumptions.
4. **Claimed files only.** Unclaimed draft uploads (`appointment_id IS
   NULL`) belong to no booking, may be mid-upload or awaiting the orphan
   cron, and render nowhere in admin — the route must 404 them rather than
   serve them.

## Goal

BK-07 renders each appointment's file names, sizes, and states — and no way
to open any of them, because the store is private and enforces it (Known
trap: a direct blob URL answers 403). A crew heading to a flooded basement
can see that photos exist and cannot look at them. Give admin a working link
per file.

## Mechanism — pinned against the installed SDK, not recalled

`@vercel/blob` **2.6.1** (read from `node_modules`, BK-05's Resend
precedent):

- `issueSignedToken({ token, pathname, operations, validUntil })` calls the
  Blob control API (`POST /signed-token`) using the store's read-write token
  and returns `{ delegationToken, clientSigningToken, validUntil }`.
  Per the installed types: `pathname` **defaults to `"*"` when omitted**
  (risk area 1), `operations` defaults to read-only `['get']`, `validUntil`
  defaults to now + 1 h.
- `presignUrl({ clientSigningToken, delegationToken }, { operation: 'get',
  pathname, access: 'private', validUntil })` returns `{ presignedUrl }` — a
  blob-host URL the CDN verifies without any bearer token.
- So the route **302-redirects to the presigned URL** and the bytes flow
  CDN → browser directly. This is why a proxy that *streams* is the wrong
  shape here: uploads run to 100 MB/file (locked), and a function response
  has platform body-size limits the redirect never touches. The 302 also
  means the function does no data transfer.

`issueSignedToken` is a network call to the control API on every click.
That is fine at this volume (≤10 files per appointment, one office) and
buys per-file, per-minute credentials; caching tokens would widen the blast
radius of a leaked URL for no operational gain.

Two more installed-SDK facts that shape the design (plan review):

- **The SDK retries failed requests 10 times with backoff** (`requestApi`
  wraps calls in `async-retry`; network errors and 5xx responses all
  retry). A down control API therefore keeps `issueSignedToken` pending
  past the platform function limit — a 504, not the route's 502. The
  `issue` call carries `abortSignal: AbortSignal.timeout(BLOB_ISSUE_TIMEOUT_MS)`
  (a new `booking-config.ts` constant, ~4000 ms) so an outage bails as a
  rejection → `'unavailable'` → 502. Fast-bail failures (bad token, 4xx)
  never hit this.
- **`presignUrl` is local** — HMAC via `crypto.subtle`, no network, host
  derived from the storeId inside the delegation token — so it needs no
  base URL and the row's `url` column (NULL until the webhook fires) is
  irrelevant. It also rejects on pathname-vs-scope mismatch, reinforcing
  risk area 1.

## Scope

1. **`src/lib/booking-files.ts`** — the decision logic, pure over injected
   deps so a script can drive it (BK-05's seam pattern):
   `buildFileRedirect(row, deps: { issue, presign, now }) →
   { kind: 'redirect'; url: string } | { kind: 'unavailable' }`.
   - Calls `issue` with **exactly** `row.pathname`, `operations: ['get']`,
     and `validUntil = now + FILE_LINK_TTL_MS`; then `presign` with
     `operation: 'get'`, the same pathname, `access: 'private'`, same
     `validUntil`. Returns the presigned URL.
   - Never throws: any `issue`/`presign` rejection **or synchronous
     throw** maps to `'unavailable'` (the route turns that into a 502 with
     a plain message). The abort-signal timeout (see Mechanism) is what
     makes "Blob API down → 502" true rather than a platform 504.
   - Also exports **`claimedFilePathname(sql, id)`** — the claimed-only
     SQL as a shared symbol (`SELECT pathname FROM appointment_files WHERE
     id = … AND appointment_id IS NOT NULL`), consumed by both the route
     and the dev-branch verify script, so breaking the production query
     turns the script red (plan-review blocker: a script-side copy of the
     query cannot go red).
   - `FILE_LINK_TTL_MS = 5 * 60_000` and `BLOB_ISSUE_TIMEOUT_MS = 4000`
     join `booking-config.ts`.
2. **`GET /api/admin/files/[id]/`** — `prerender = false`. Integer-validate
   `id` (reuse the BK-08 id parser); look up via `claimedFilePathname` — no
   row → 404 (risk area 4; the claimed-only rule is the shared SQL, not an
   `if`; `upload_state` is deliberately not fetched — a claimed-but-pending
   row is served and the CDN answers the truth about its bytes). Wire
   `buildFileRedirect` with the real SDK functions, **passing the store
   token read via `readEnv('BLOB_READ_WRITE_TOKEN')` explicitly as the
   SDK's `token` option — never left to the SDK's own `process.env`
   lookup**, which is empty under `astro dev` (the documented third-party-
   SDK trap; the seam's argument capture pins this). Unset → 502, logged —
   same posture as the notify adapter's missing key. `'redirect'` → 302
   `Location: presignedUrl` with **`Cache-Control: no-store`** stated
   positively (a shared cache storing the redirect would extend the
   capability's audience); `'unavailable'` → 502.
3. **`src/pages/admin/appointments/[id].astro`** — each file row's name
   becomes a link to `/api/admin/files/${file.id}/` (slashed, per the
   scan), `target="_blank" rel="noopener noreferrer"` (the admin page URL
   names the appointment id and must not travel as a Referer to the blob
   host); the "viewing is BK-09" note
   goes away; `upload_state = 'pending'` rows render unlinked with their
   state label instead (their bytes may not exist yet).
4. **`src/lib/db.ts`** — `AppointmentFile.size_bytes` corrects to
   `string | number | null` per the Known trap this ticket owns (BIGINT
   arrives as a string; BK-07's `formatFileSize` already coerces, and the
   trap entry gets closed out).
5. **`scripts/verify-booking-files.ts`** + `npm run verify:booking:files` —
   `buildFileRedirect` through injected seams (see Verification).
6. **`scripts/verify-booking-admin-db.ts`** — extended: drives
   `claimedFilePathname` (the shared symbol, not a copy) against dev-branch
   fixtures — unclaimed row invisible, claimed row returned — and
   dynamically imports the route's `GET` to drive the three 404 cases
   (non-numeric id, unknown id, unclaimed id) plus the unset-token 502 for
   a claimed row, which exercises the route's wiring without a live
   control-API call. The extension **owns its own `appointment_files`
   fixture cleanup**: the script's existing cleanup covers appointments
   and blackouts only, the FK CASCADE reaches only claimed rows, and the
   orphan cron never runs against the dev branch.

## Out of scope

- **Uploading, replacing, or deleting files from admin.** Read-only.
- **Thumbnails, gallery views, zip-all downloads.** Links suffice for one
  office.
- **Serving files to customers.** Nothing outside `/api/admin/` ever gets a
  signed URL.
- **The orphan-upload cron and its `del()` path** — untouched.

## Design notes

- **Redirect, not stream.** Named in Mechanism; the alternative fails
  exactly when the files matter most (a 100 MB walkthrough video) and
  doubles data transfer besides.
- **The pure core owns the scope invariant.** `buildFileRedirect` is the
  only caller of `issue`/`presign`, and the verify script asserts the
  arguments — pathname equality, `['get']`, the TTL arithmetic — so
  "scoped token" is a red-observable property, not a code-review note.
  The route contributes only SQL and wiring.
- **`upload_state` gates the link, not the route.** A pending row does
  **not** 404 at the route — claimed pending rows are legitimate (the
  Known trap: localhost never completes them), so the route serves any
  *claimed* row whose id it is given and never reads `upload_state`. The
  page-level unlinking is presentation only. Serving a claimed-but-pending
  row is harmless: the presigned GET simply 404s at the CDN if the bytes
  never arrived.
- **507s and half-states are not retried.** One office clicking a link can
  click it again; retry logic in a redirect route is complexity with no
  constituency.

## Acceptance criteria

1. `buildFileRedirect` passes the row's exact pathname, `['get']`,
   `now + FILE_LINK_TTL_MS`, the explicit `token`, and an abort signal to
   `issue`; passes `operation: 'get'`, `access: 'private'`, the same
   pathname and expiry to `presign`; returns the presigned URL untouched;
   maps any rejection **or synchronous throw** of either dep to
   `'unavailable'` without throwing.
2. The route 404s: non-numeric id, unknown id, and any file whose
   `appointment_id` is NULL (pending state alone never 404s). It 302s a
   claimed file to the presigned URL with `Cache-Control: no-store`, and
   502s (never 500s, never a platform 504) when the Blob API fails, times
   out against `BLOB_ISSUE_TIMEOUT_MS`, or the token is unset.
3. No request input other than the numeric id influences the signed
   pathname.
4. The detail page links claimed+uploaded files, renders pending rows
   unlinked, and contains no direct blob URL or pathname (BK-07's AC6
   still holds over the changed section).
5. A direct, unsigned blob URL still answers 403 (the store posture is
   unchanged — re-checked, not assumed).
6. `size_bytes` typing matches driver behavior; `formatFileSize` output
   unchanged.
7. `npm run typecheck` and `npm run build` pass.

## Assumptions log

Settled without the user; each is a reviewer's or the user's to overturn.

- **A 5-minute, single-pathname, get-only URL in the admin's browser is an
  acceptable capability.** The admin is one trusted office; the URL expires
  before it can rot in a chat log. Re-clicking mints a fresh one.
- **`issueSignedToken` per click** rather than cached — see Mechanism.
- **Pending-but-claimed rows are servable by the route** (the CDN answers
  the truth about whether bytes exist); only the page withholds the link.
- **No new environment variables** — `BLOB_READ_WRITE_TOKEN` already
  exists in production (P1) and `FILE_LINK_TTL_MS` is a code constant.
- **The `size_bytes` correction is this ticket's** — the Known trap named
  BK-09 its owner; the trap entry is closed out on implementation. Done: the
  ROADMAP entry is struck through and records both halves of the pin.

Settled during implementation, each a reviewer's to overturn:

- **`token` is a fourth dep, not a fourth argument.** Scope 1 sketches
  `deps: { issue, presign, now }`, but AC1 requires the explicit token be
  asserted *through the seam* — so `FileRedirectDeps` is
  `{ issue, presign, token, now }`. Passing it any other way would leave the
  one property the astro-dev trap threatens unobservable.
- **`now` is a `Date`, not a clock function.** Matches every other injected
  clock here (`partitionAppointments`, `stampNotifications`,
  `formatAdminTimestamp`) and is inherently read once, so the delegation and
  the URL cannot land on two different instants.
- **The path got a constant.** `ADMIN_FILE_ENDPOINT` + `adminFilePath(id)` in
  `booking-admin.ts` rather than a literal in the page, matching
  `adminAppointmentPath`. This is what puts the new path under the existing
  slash scan for free (red U), which is the reason the ROADMAP praises that
  file holding the constants.
- **`verify-booking-admin.ts` gained three lines, not just the page.** The
  ticket said its slash-scan list already covers the changed detail page — true
  — but the new endpoint is the only admin path that *mints a credential*, so
  "still needs a session" is pinned by name (red V). Risk area 3.
- **Order in the route: lookup → 404, then token → 502.** The three 404 arms
  therefore hold regardless of whether the store token happens to be
  configured, which is what lets the dev-branch script drive them without
  touching the Blob API. The unset-token 502 is driven for a *claimed* row so a
  404 arm cannot be what produced it.
- **`parseAppointmentId` is reused verbatim** for file ids, per Scope 2. Both
  are int4 `SERIAL`s and both need the same leading-zero rule; its doc comment
  now understates its reach, which is left alone rather than renamed mid-ticket.
- **Nothing drives the live 302.** Both scripts stop short of a real control-API
  call by design — `verify:booking:files` uses seams, and
  `verify:booking:admin:db`'s contract is the dev database. The round trip is
  the AC5 probe above (which proved the signature is honoured) plus the
  post-deploy check.

### Three assertions the red pass caught being weak, and what was done

Recorded because each was written, believed, and found not to hold — the
red-first rule earning its keep rather than confirming it.

1. **The URL-passthrough assert was inert.** Break I (`encodeURI`) first ran
   **green**: the fixture presigned URL was tidy enough that re-encoding it was
   a no-op. Fixed in the *script*, not the code — `PRESIGNED` is now shaped like
   a real one, with `%20` in the path and `%2F`/`%2B`/`%3D` in a signature
   parameter. Break I then went red. (A second mutation, `new
   URL(x).toString()`, is still green and correctly so: WHATWG normalization
   does not alter an already-normalized URL, so it is not a defect to catch.)
2. **The leading-zero 404 was contingent, not decisive.** Under break P it
   stayed green, because a loosened parser turns `0000000012` into id 12 and
   the dev branch happens to have no claimed file with that id — the assert was
   passing on the branch's contents rather than on the parser. It now runs
   against **this run's own claimed row** (`getFile('0' + claimedRow.id)`),
   where a loosened parser yields a 302 for a second spelling of one file.
3. **The unset-token 502 cannot pin the route's guard.** Break R2 (deleting
   `if (!token)`) left `verify:booking:admin:db` **fully green**: with `token`
   undefined the SDK falls through to its own `BLOB_READ_WRITE_TOKEN` lookup,
   finds nothing, throws, and `buildFileRedirect` maps that to the same 502. The
   behaviour is right by two independent routes, so behaviour alone cannot
   observe the guard. The guard still matters — without it, `astro dev` would
   502 every file link *while the token is correctly configured*, because the
   SDK's store is exactly the one Vite never populates. So a source-level
   assertion was added to `verify:booking:files` and R2 then went red. The
   behavioural 502 assertion is kept: it pins AC2, which is about the answer.
