# BK-33 — Refund mechanics

**Status:** draft 2026-08-16 · **policy values answered 2026-08-18** (client
question #4). Mechanism unchanged.
**Phase:** P9 · **Tier:** Reviewed (money, irreversible) · **Depends on:**
BK-32 (needs a payment intent) · **Blocks:** nothing.
**Deploy:** 3. **Migration:** folds into 008 if BK-32 has not shipped, else its
own.

**Mechanism only, and it stays policy-free by design** — the office can always
refund by hand, so nothing here ever waited on the policy. As of 2026-08-18 the
policy is answered anyway, which changes the constants below and nothing else.

## Scope

- `stripe.refunds.create({ payment_intent, amount?, reason })`, idempotency key
  `refund-<appointment_id>-<attempt>`.
- **Company-cancel refund is one action.** When the office moves a paid row to
  `cancelled`, a *Refund in full* checkbox appears, defaulted **ON** when a
  company-side reason is selected. This is the path that must be impossible to
  forget: a customer who paid for a visit we cancelled and then had to phone to
  chase their money is the worst outcome this feature has.
- The `amount` parameter is supported even if the policy turns out to be
  all-or-nothing. Partial refunds cost nothing to support now and a migration
  later.
- Columns: `stripe_refund_id TEXT`, `refunded_amount_cents INTEGER`,
  `refunded_at TIMESTAMPTZ`; `payment_status` gains `refunded` /
  `partially_refunded` (already in BK-32's CHECK).
- Webhook handles `charge.refunded` and `refund.updated` — **a refund issued
  from the Stripe dashboard by the office must reach our row too.** The office
  will use the dashboard; assuming otherwise is how the two records diverge.

## Policy constants — answered 2026-08-18

**Client answer, verbatim in effect:** *full refund if cancelled 24+ hours
before the appointment; no refund within 24 hours.* Exceptions are case-by-case
and handled **manually in the Stripe dashboard** — no code.

In `booking-config.ts`:

```ts
REFUND_COMPANY_CANCEL        = 'full'   // certain, and always was
REFUND_CUSTOMER_CANCEL_HOURS = 24       // client, 2026-08-18
REFUND_CUSTOMER_CANCEL_AFTER = 'none'   // client, 2026-08-18
```

`REFUND_NO_SHOW` **is deliberately not a constant.** The client's answer did not
name no-shows separately, and a no-show is by construction inside the 24-hour
window — so it is already covered by `REFUND_CUSTOMER_CANCEL_AFTER`. Adding a
third constant would invent a policy nobody stated. BK-36 words it as the 24-hour
rule rather than as forfeiture.

The `null`-renders-as-"call us" machinery the draft specified is **no longer
needed for these values** and should not be built for them. Keep the shape in
mind only if a future value is genuinely unknown.

## Out of scope

- Enforcing the policy automatically. The constants describe what the office
  owes; **every refund still starts with a human** and the 24-hour rule is not
  wired to a timer. There is no self-service cancel to hang one off.
- Automatic refunds on customer cancellation — there is no self-service cancel
  (locked, phone-in), so every refund starts with a human.
- The cron/webhook race refund case, which BK-32 deliberately resolves as
  "flag, do not auto-refund".

## Risk areas for the reviewer

Money movement, double refunds under webhook replay, dashboard-issued refunds
reconciling correctly, and the company-cancel default not being silently
flipped off.
