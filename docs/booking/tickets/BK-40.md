# BK-40 — File provenance and soft delete

**Status:** implemented 2026-08-16 — gates green (13 verify scripts, typecheck,
build, smoke), 14 red rows, migration 006 applied to the dev branch. **Awaiting
implementation review** (Reviewed tier).
**Phase:** P10 · **Tier:** Reviewed — private file store, admin write path, an
action the office will describe as "delete", and a change to the shipped
appointment-token format · **Depends on:** BK-34a (shipped) · **Blocks:** nothing.
**Deploy:** 1.5. **Migration:** **006** — see the renumbering note.

Two gaps the client hit as soon as real photos started arriving:

1. **The office cannot tell a customer's photo from one an agent uploaded.**
   Under BK-34a both paths ran the *same token* through the *same route*, so
   nothing distinguished them at any layer.
2. **A wrong or accidental upload was permanent.** It stayed on the
   appointment, counted against the 10-file cap, and had no UI to undo it.

## Scope

- **Migration 006** — `appointment_files.source`, `deleted_at`, `deleted_note`,
  plus a partial index on the live rows every read path now filters by.
- **A signed origin claim.** The admin page mints TWO tokens: the customer's
  link keeps version `a1` and origin `link`; the page's own uploader gets a new
  `a2` carrying `office`.
- **Soft delete** — a POST endpoint, a per-row Remove button with an optional
  reason, and a "Removed" section that keeps the record visible.
- **Every consumer excludes deleted rows**: the file proxy, the upload caps,
  the list page's count, the detail page's live list.

## The origin has to be inside the signature, and here is why

`issueAppointmentUploadToken` takes the HMAC over the payload and **prepends the
version tag afterwards — the tag is not signed.** So if `a1` and `a2` had
shared a payload shape, rewriting one leading byte of a customer's link
(`a1.` → `a2.`) would produce a token that still verified, and every photo that
customer sent would be filed as the office's own.

**Provenance the caller can choose is worse than no provenance, because the
office would believe it.** The same three barriers BK-34a put between draft and
appointment tokens therefore go between `a1` and `a2`:

| Barrier | `a1` (link) | `a2` (office) |
| --- | --- | --- |
| version tag | `a1` | `a2` |
| arity | 5 parts | 6 parts |
| signed payload | `<id>.<draft>.<issued>` | `<id>.<draft>.<issued>.office` |

`a1` is **byte-identical to what BK-34a shipped**. Links already sitting in
customers' messages have up to 72 hours left on them, and changing `a1`'s shape
would have killed every one.

## Two things the obvious implementation would have got wrong

**1. The audit line must NOT be appended to `admin_notes`.** The request said to
use "the existing audit-line pattern", which is BK-35's — and BK-35 appends one
*fixed* sentence *once*, with `MAX_STORED_ADMIN_NOTES` sized for exactly that
(`MAX_ADMIN_NOTES + UNTICKED_NOTE.length + 2`). Deletions are unbounded.
Appending here would push the stored notes past the bound that the detail page's
textarea and `parseAppointmentUpdate` both enforce, and the consequence is
already written down at that constant: **every later status change is rejected
with "That edit was not valid", naming no field**, and the appointment cannot be
moved through the pipeline until somebody hand-deletes text the system wrote.
The audit lives in `deleted_note` — a TEXT column of its own, queryable, and
rendered on the row it describes.

**2. The endpoint is `/api/admin/appointments/file-delete/`, not
`/api/admin/files/delete/`.** `src/pages/api/admin/files/[id].ts` is dynamic, so
the second path is the same URL shape as `/api/admin/files/7/`. Static-beats-
dynamic would *probably* have resolved it — "probably" being the word that cost
BK-34a a production outage with every gate green. The generated route table
settles it, and the red pass made it concrete: with the constant moved under
`/api/admin/files/`, **no route pattern is generated for it at all**, so the
form would POST at the dynamic file proxy, which exports only `GET`.

## Assumptions log

1. **`source` is nullable and nothing is backfilled.** NULL means "not
   recorded", which is the truth for every pre-006 row, and it renders as
   exactly that. A backfilled guess is indistinguishable from a fact the moment
   it lands. Same reasoning as `terms_acked_at` (005).
2. **No `'unknown'` in the CHECK.** An enum member meaning "no value" beside a
   nullable column is two spellings of one state that can disagree — the trap
   005's own comment describes for a boolean beside a timestamp.
3. **The Blob object is NOT deleted.** The office asked for this button because
   of *accidental* uploads, so it must not be unrecoverable. The row is what
   hides the file; the bytes cost far less than an irreversible click. If it
   ever matters, the cleanup cron sweeps long-deleted rows — not this button.
4. **Deleted rows stay on screen, muted and unlinked.** "The customer says they
   sent four photos" is answerable from this list and nowhere else. Unlinked
   because `claimedFilePathname` refuses a deleted id, so a link would 404 by
   design.
5. **`source` is not in the `ON CONFLICT DO UPDATE` list.** A retry of the same
   pathname keeps the origin the row was born with; letting a later token
   rewrite it would make provenance depend on who retried last.
6. **No `confirm()` dialog on Remove.** The action is soft and reversible in the
   database, and a blocking dialog on every removal costs the office more than
   the occasional mis-click.
7. **The reason is truncated, not rejected.** It is the audit trail on a
   deletion that has already been decided; refusing the whole action over a long
   footnote would lose the deletion. Nothing downstream re-applies the bound, so
   unlike the notes cap this truncation cannot return as a rejected edit.

### Red-observed

| # | Break | Assertion that went red |
| --- | --- | --- |
| s | mint side: the office payload drops the origin | the office's own token claims origin "office" |
| t | verify side: the office payload is rebuilt without the origin | a link signature re-shaped as an office token does not verify |
| **s+t** | **the real vulnerability — the origin never enters the signature** | **a link signature re-shaped as an office token does not verify** |
| u | arity and version no longer have to agree | a LINK token re-tagged a2 is rejected |
| v | the origin segment is not checked against `'office'` | an office token carrying origin "link"/"admin"/""/"OFFICE" is rejected |
| w | arity widened to `length < 5` | a token padded in the MIDDLE with its real signature last is rejected on arity |
| z | the file proxy stops excluding deleted rows | a REMOVED file is invisible to the proxy; the route 404s it |
| aa | migration 006 drops the `source` CHECK | migration 006 refuses a source outside web/link/office |
| ab | the public funnel stops recording its provenance | a public-funnel upload records source 'web' |
| ac | the delete endpoint moves under `/api/admin/files/` | it must match a generated Vercel route; it stays out of that namespace |
| ad | the endpoint constant loses its trailing slash | it must match a generated Vercel route |

**Row (w) is the one worth reading, and it is the second time in this file.**
The first spelling — `${office.token}.extra` — went GREEN with arity widened to
`length < 5`, because seven parts makes `isOffice` false and the `a2` tag then
fails the version check. It was testing the version tag while claiming to test
arity, which is exactly what BK-34a's own barrier-2 comment warns about two
screens above it. What isolates arity: `sigHex` is read from the LAST part, so
padding the **middle** and keeping the real signature in final position passes
every downstream check. Both assertions are kept; the weaker one is now labelled
for what it actually exercises.

**Row (ac) is the one that justifies the endpoint's address.** It does not merely
fail — it shows that the alternative path generates *no route at all*.

## Follow-up recorded, not fixed

Deleted rows keep their bytes, so a store that accumulates many deletions grows
without bound. **Severity: low** — deletions are exceptional by nature and the
per-appointment caps still bound live files. **Owner: none.** The natural home
is the existing `cleanup-uploads` cron, which would sweep blobs for rows deleted
more than N days ago; it is not this ticket's job and it must not be a default.
