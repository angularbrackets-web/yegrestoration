## What a scoping pass found that the plan's table does NOT contain

1. **⚠ THE SHARPEST ONE — `appointmentMoney` returns `{kind:'none'}` for ANY
   tier-less row** (`booking-admin.ts:482-483`). Today that is harmless, because
   a tier-less row cannot be approved. **The moment item 3 lands, it is a live
   defect:** an office member who types `$250` on a tier-less booking gets a
   charged customer and **no screen anywhere showing the amount** — `settled`
   (`[id].astro:653`) reads the same `money`. That reopens exactly what BK-46 was

   anywhere that shows what it was"*). **The tier gate must move out of
   `appointmentMoney` and into the display.** That reddens

   behaviour.
2. **`CheckoutRequest.tier` is non-nullable** (`booking-payment.ts:198`) and
   `review.ts:489` passes `row.assessment_tier` into it. **Deleting the `notier`
   guard is a typecheck error, not a behaviour change.** Good news: the tier is
   used only for Stripe `metadata.tier` (`booking-payment.ts:380`) and **nothing
   reads it back** — no `metadata.tier` reader exists in `src/`. Widen to
   `AssessmentTier | null` and omit the metadata key.
3. **`review=tier` is a dead banner key.** `amountsFrom` returns `{error:'tier'}`
   which is redirected verbatim, but `REVIEW_MESSAGES` has **`notier`, not
   `tier`** (`[id].astro:272-345`). Unreachable today; **reachable the moment
   item 4 renders the Preview button** for a tier-less row. Fix or delete the
   guard, do not leave both.
4. **`notier`'s banner text becomes a false instruction** — *"Choose an
   assessment first — the amount comes from it"*. If the key survives, it lies.
5. **The Decline-only arm states the rule in its own prose**
   (`[id].astro:1932-1938`): *"No tier means no amount to charge, so approval is

6. **Two comments state the retired rule**: `booking-payload.ts:268-271` and

7. **`assessmentSummary`** (`booking-email.ts:1159-1169`) recomputes the phantom

   `verify-booking-email.ts:2050-2053`, which becomes the **common** case for a

## The money-gate fix (decision 15's own ⚠ item), exact

`[id].astro:806-859`. `money.kind !== 'none'` is **exactly equivalent** to
"tier present" (`booking-admin.ts:482-483`), so the plan's *"the condition
inverts cleanly"* is literally true — **and that is why keeping the money gate
INSIDE a new tier gate is a tautology that would ship the phantom `$399` ladder
onto the office's own screen** via `appointmentMoney`'s `estimate` arm →
`assessmentQuote` → `TIER_DEFAULT_CENTS`.

Hoist the name in the frontmatter so the non-null assertion is **removed**, not
relocated:

```ts
const assessmentTierName =
  appointment && appointment.assessment_tier
    ? ASSESSMENT_TIER_NAMES[appointment.assessment_tier]
    : null;
```

then gate the whole `<div>` on `assessmentTierName`, render the name
unconditionally inside it, and gate the money sub-block on
`money.kind === 'settled' && money.totalCents > 0`.

⚑ **Dropping the `estimate` arm is a DECISION, not a mechanical edit** — it is
the phantom ladder, so dropping it is right under decision 12, but say so in the
Assumptions log or own it jointly with BK-53. **Do not ship the estimate arm
quietly.**
