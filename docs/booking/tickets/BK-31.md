## The deleted clause

The ROADMAP's earlier BK-31 row said the ticket was *"non-binding by design:
the form must say the choice can change on the day"*. **That is deleted, not
softened** (client, 2026-08-16). The tier is what gets charged, so it binds.
`FEE_TERMS_OUTRO`'s "Tell the tech on the day which of these you want" dies with
it — BK-36 owns the replacement sentence.

## Scope

1. **Radio group** in the terms box on step 3 of `BookingForm.svelte`, and on
   the homepage booking section, matching wherever `FEE_TERMS_ITEMS` renders.
   Required, with **no default selection** — a pre-selected $399 is a customer
   charged a tier they never looked at, and a pre-selected anything else is
   worse.

   Placement: below `FEE_TERMS_CREDIT`, above the ack checkbox. The ack label
   says "the terms above", which is a claim about page order that
   `verify-cutover.ts` should pin.

2. **`assessment_tier`** — `TEXT CHECK (assessment_tier IN ('standard',
   'report', 'sketch'))`, nullable. NULL is correct and permanent for admin
   entries and for every row predating the migration, on exactly the reasoning
   `terms_acked_at` records in `005-assessment-terms.ts`. Nothing is
   backfilled; there is no NOT NULL to add later.

3. **The pricing table — amended 2026-08-18, and its shape changed.** A new
   pure module `src/lib/booking-pricing.ts` (env-free, importable by the Svelte
   island, the API routes and a `tsx` verify script alike — the same constraint
   `booking-config.ts` carries and the reason this is not in `db.ts`).

   Keyed **`(tier, service)`**, not by tier alone and not by service alone:

   | Tier | Default | `mold` override |
   | --- | --- | --- |
   | `standard` | `39900` | `38500` |
   | `report` | `69900` | `64500` |
   | `sketch` | `119900` | `118500` |

   All in **cents, ex-GST**. A default row per tier, plus one override map with
   a single `mold` entry; every other service falls through to the default, so
   an un-overridden service is not a branch. Client's reason, verbatim: *"we
   have to be a bit more competitive with mold estimation"*, and *"for now"* —
   so a price move must stay a one-line edit.

   **The 1.5x after-hours multiplier** applies when the selected slot falls on
   a **Saturday or Sunday in America/Edmonton** (client: *"Yes weekend is
   extra"*). Saturday and Sunday are ordinary bookable days here —
   `CLOSED_WEEKDAYS = [5]` closes Fridays only — so this is a live path.
   Integer arithmetic, never a float multiply: `round(cents * 3 / 2)`.

   Read the weekday off the slot with `localDateKey` + `weekdayOfDateKey` from
   `booking-time.ts`. **Not** `Date.getDay()`, which is the server's zone and
   would surcharge the wrong bookings twice a year.

   One exported function is the only way anyone gets a number:

   ```ts
   assessmentQuote({ tier, service, slotStart, travelFeeCents? })
     -> { baseCents, afterHours, travelCents, subtotalCents, gstCents, totalCents }
   ```

   `GST_RATE_PERCENT = 5`, applied to `base + travel`, rounded once at the end.

   **The form posts a tier key, never an amount.** This is the whole defence
   against a tampered payload paying $1 for the sketch tier, and it is why the
   table is cents-integer rather than a float or a display string. That the
   *form now displays* a price changes nothing about it: display is not trust,
   and the server recomputes from `(stored tier, stored service, stored slot)`
   at approval. A verify assertion pins that a posted amount is ignored.

   The existing `FEE_TERMS_ITEMS` strings stay the customer-facing copy; the
   default-row numbers and those figures must agree, asserted by a verify
   script rather than by eye. **The mould overrides are deliberately not in
   `FEE_TERMS_ITEMS`** — the terms box states the standard prices, and the
   live price display is what tells a mould customer their actual number. BK-36
   owns the sentence that makes that honest.

3a. **Live price display on the form (new, 2026-08-18).** The customer must see
   the amount they will be asked to pay **before** they send the request —
   including the weekend multiplier, and including the mould override. It
   updates as the tier, the service or the slot changes, all three of which the
   island already holds.

   When the slot is a weekend, the display must say *why* it is higher rather
   than silently showing a bigger number. Copy is BK-36's; the control is this
   ticket's.

   **Stat holidays are out of scope for v1** (client, 2026-08-18 — they will
   blackout the date or take it by phone). A stat-holiday Monday shows the
   weekday price. Recorded here so the gap reads as a decision, not a bug.

4. **Validation** through the existing `entry` seam in `booking-payload.ts`:
   required when `'public'`, optional when `'admin'` — the same shape as the
   `terms_acked_at` gate at `:249`, riding the same discriminator, for the same
   client exemption.

5. **Renders**: internal email, customer email, admin detail page, and the
   admin edit form (the office must be able to change a tier when a customer
   upgrades on site).

6. **Upgrade path.** Changing the tier on a `confirmed` row **does not
   re-charge**. The delta is collected on site or added to the invoice — out of
   scope here, and the admin edit control must say so beside itself rather than
   implying a charge follows. Under P9 that control edits a value that has
   already been paid against; silence there is how somebody gets billed twice.

## Out of scope

- Charging anything. That is BK-32.
- The terms rewrite. That is BK-36, and the two must reach the browser in the
  same deploy — a picker beside "tell the tech on the day" is a self-
  contradicting page.
- **The travel fee.** It is not computed here and not shown to the customer:
  it is an admin-side suggestion at approval (BK-23), because it depends on an
  address we have not verified and a distance nothing in this infrastructure
  can measure yet.
- **Stat-holiday pricing.** Deferred, above.
- **Admin overrides of the amount.** BK-23 owns the approval-screen controls;
  this ticket owns only the table they pre-fill from.

## Risk areas for the reviewer

- Price integrity: no amount may originate in a request.
- The admin exemption must remain structural (hard-coded `entry: 'admin'`), not
  conventional.
- Tier copy and tier prices are two lists that must not drift, and the mould
  override is a third number the copy deliberately does not carry.
- Weekday must be computed in America/Edmonton, not the server's zone. Getting
  this wrong surcharges Friday-night-UTC bookings and misses real weekends.
- Integer cents throughout: a 1.5x float multiply that lands on `.5` of a cent
  is a Stripe amount that disagrees with the email.
- A `confirmed`-row tier edit must not look like it triggers a charge.

## Acceptance criteria

1. A public booking with no tier selected is rejected with a field error; the
   island routes it to the right step.
2. A public booking with a tier not in the closed set is rejected.
3. An admin entry with no tier saves, and stores NULL.
4. A payload carrying an *amount* has it ignored — the stored tier and the
   server-side price are the only sources of truth.
5. The tier appears in both emails and on the admin detail page.
6. The default-row prices and the figures in `FEE_TERMS_ITEMS` agree, asserted
   by a verify script rather than by eye.
7. `assessmentQuote` returns the mould override for `service: 'mold'` and the
   default for every other service key in `SERVICE_LABELS`.
8. A Saturday or Sunday slot returns `afterHours: true` and exactly
   `round(base * 3 / 2)`; a Monday-to-Thursday slot returns `afterHours: false`
   and the bare base. Asserted across a DST boundary in both directions, using
   Edmonton wall-clock dates rather than the server's zone.
9. GST is 5% of `base + travel`, rounded once; `totalCents` equals
   `subtotalCents + gstCents` exactly, with no float drift at any tier.
10. The form's displayed price matches `assessmentQuote` for the selected
    `(tier, service, slot)` — asserted against the same function, not a
    retyped expectation.
11. A weekend slot's displayed price is visibly explained as a weekend rate,
    not merely larger.

## Implementation review — findings and what was done

Reviewer was a fresh agent given only this ticket, the diff for `e476798` and
re-run gate output. Verdict: **gate evidence NOT adequate**, on two independent
grounds — a gate was red at HEAD and attributable to this ticket, and three ACs
had no assertion at all, so under red-first they were unverified rather than
passing.

### B1 — blocker, FIXED. `verify:booking:smoke` was red from the day this shipped

The smoke fixture builds its body from `emptyFormValues()` plus explicit
overrides, and the `assessmentTier` override was never added beside `termsAck`.
This ticket made the tier required on the public door, so **every smoke commit
422'd from the moment it landed** and the ticket's gate table recorded "gates
green" over a script that was failing and unlisted.

This is the third instance of the family already in ROADMAP's Known traps
(`verify:booking:admin:db` red from BK-35 to BK-40): **a ticket that changes
what a public door REQUIRES has to grep for fixtures that post to it**, and
neither typecheck nor build nor any pure script can find them.

It is not a stale fixture. `verify:booking:smoke` is the only gate that
exercises the **generated Vercel route table** plus a real HTTP commit against
a real database — the thing CLAUDE.md's leading trap exists about. For the
whole of BK-31 and BK-23's implementation, no public booking had been proven to
work end to end on this branch, and everything downstream of the commit in that
script was unexercised.

Fixed: the fixture posts `assessmentTier: 'report'` — deliberately **not**
`'standard'`, which is the first tier in the list and the value a careless
default would produce, so a wrong tier cannot pass for a missing one — and a new
arm asserts the tier reached the column through the real route.

### B2 — blocker, FIXED. AC10 and AC11 were asserted by nothing

No script referenced `assessmentQuote`, `tierQuotes`, `AFTER_HOURS_NOTE` or any
tier constant outside `verify-booking-pricing.ts`, which never touches the
island. The reviewer **deleted the entire radio fieldset and the quote block**
and typecheck plus four verify scripts stayed green.

The consequence is not cosmetic. The server requires the tier, so a public
booking with the control missing 422s with `field: assessment_tier`,
`FIELD_STEPS` routes the visitor to step 3, and step 3 contains nothing that can
set it. **The funnel is 100% dead with every gate passing** — a strictly worse
version of the terms-box regression `verify-cutover.ts` already existed to
prevent, and the pin was never extended to the control this ticket added.

Fixed in `verify-cutover.ts`, beside the terms-box pin it belongs with:
presence of the tier constants, the binding to `values.assessmentTier`, the
ordering inside the terms box and above `FEE_TERMS_ACK_LABEL`, and that every
rendered amount comes from a quote field through `formatCents` with no price
arithmetic anywhere in the island.

**Deliberately NOT an assertion that recomputes the price with
`assessmentQuote`.** AC10 as written ("asserted against the same function") asks
for exactly the shape ROADMAP's Known traps record six instances of: an
expectation built by the function under test moves with it and cannot go red.
What is pinned instead is that the island's figures *come from* that function
and from nowhere else, which is the property a wrong number would break.

### B3 — blocker, NOT FIXED. Release gate, owner BK-36

`FEE_TERMS_OUTRO[0]` still reads *"Nothing is charged when you book. Tell the
tech on the day which of these you want."* It renders three lines above the
binding radio group, and in the customer confirmation email immediately above
the `You chose: …` line.

**Refused here, in writing, with the reason:** the replacement sentence is
client-facing copy and BK-36 owns it. Writing it inside a BK-31 review fix would
be inventing customer-facing terms without the client, which is the one category
CLAUDE.md sends to the user rather than settling in-ticket.

**But the reviewer's severity is accepted and is stronger than this ticket's own
"Known gap" section recorded.** Concrete case — Saturday, service `mold`, tier
`sketch`: the customer keeps an email whose terms paragraph says the choice is
made on the day and whose list says $1,199, immediately followed by
"$1,777.50 + GST ($1,866.38 total) — weekend rate, 1.5x". That is a written
record contradicting itself about whether the choice binds *and* about the
amount, in a flow whose entire purpose is taking money up front.

**Deploy 2 must not ship without BK-36.** Recorded as a release gate in P9's
build order, not merely as a ticket dependency.

### S1 — FIXED. The weekend surcharge was applied before anything explained it

The radio prices render under `{#if tierQuotes}` (service + slot); the note
rendered under `{#if quote}` (which also needs a tier). So on a Saturday, before
the visitor clicked anything, the three radios read $598.50 / $1,048.50 /
$1,798.50 beneath a terms box reading $399 / $699 / $1,199, with no weekend note
on the page. AC11 requires the weekend price to be explained *at the moment of
comparison*, which is the whole point of showing three numbers.

Fixed by gating the note on the same `tierQuotes` the prices come from and
rendering it above the radio list, so the explanation and the higher number
appear together by construction rather than by two conditions agreeing.

### S2 — FIXED. The tier's appearance in the emails was unasserted

Only fixture fields had been added; nothing checked that either body contained
the tier name, the figure, or the `Not chosen` fallback. `assessmentSummary`
could have named the wrong tier, dropped the weekend suffix, or vanished from
both templates with every gate green — on the line a customer points at in a
dispute. Now asserted for the weekday standard case, the weekend-mould case
(where the override and the 1.5x compose), and the NULL-tier phone booking.

### S3 — FIXED. The price-drift pin did not catch price drift

`formatCents(tierDefaultCents(tier)).startsWith(expected[tier])` — and
`"$399.90".startsWith("$399")` is `true`. Editing `standard` to `39990` passed
the one assertion whose entire job is price drift, charging $399.90 against copy
saying $399. **The cents are the part a typo lands in.** Now exact equality
against `${expected[tier]}.00`, plus a length check so a fourth terms bullet
cannot leave one tier's figure pinned by nothing (the pin zips copy to tiers by
position).

- The "Deliberately not done" note says the picker is absent from "`/book/`'s or
  `ContactSection`'s terms boxes". `/book/` has no terms box of its own;
  `FEE_TERMS_ITEMS` renders in `ContactSection.astro` and the island only. The
  decision was right, the record was off. Corrected here.

## Implementation notes

- **`src/lib/booking-pricing.ts`** is new and is the only place a price exists.
  Pure and env-free so the Svelte island, the API routes and `tsx` scripts can
  all import it — the same constraint `booking-config.ts` carries.
- **`assessmentQuote()` is the single entry point.** The form renders it, the
  admin detail page renders it, both emails render it, and BK-32's Stripe line
  items will read the columns it pre-filled. Rounding happens exactly twice (the
  multiplier, then GST) and `totalCents` is `subtotal + gst` by construction, so
  the itemization a customer reads always sums to what they are charged.
- **The mould key is `mold`, not `mould`.** The data says `mold` (matching
  `SERVICE_LABELS`); the copy says "mould". A mismatch does not throw — it
  silently charges the standard price — so `verify-booking-pricing.ts` iterates
  `SERVICE_LABELS` rather than a hand-listed set, and a service added to `db.ts`
  is covered the day it lands.
- **The form shows a price for every tier, not just the selected one.** The
  point of the list is comparison, and a visitor booking a Saturday mould job
  should see three real numbers rather than three standard ones and a surprise
  at the bottom.
- **Weekend surcharges are explained where they appear.** `AFTER_HOURS_NOTE`
  renders above the total whenever the multiplier applied. A 1.5x figure a
  visitor discovers by comparing it against the terms box reads as an error or
  as sharp practice.
- **The admin tier control says what it does not do.** Under P9 the row it edits
  may already have been paid against, so the control carries "Changing this does
  not charge anything" beside itself rather than leaving the office to infer it.

## Known gap, handed to BK-36

The terms box states the **standard** figures ($399/$699/$1,199) while the
radios and the total show the price that actually applies. A mould customer sees
$399 in one place and $385 in the other with nothing saying which is real, and a
weekend customer sees a 1.5x figure the box does not mention. **Nothing about
this looks like a bug**, which is why it is written down here rather than left
to be noticed. BK-36 owns the disclosure sentence.

## Deliberately not done

- **The picker is not on `ContactSection`'s terms box.** It renders
  `FEE_TERMS_ITEMS` for information and contains no form, so a radio group there
  would be a control that does nothing. The ticket's scope line said "wherever
  `FEE_TERMS_ITEMS` renders"; that reading would have shipped a dead control.
  (Corrected at review: an earlier version of this note also named `/book/`,
  which has no terms box of its own — `FEE_TERMS_ITEMS` renders in
  `ContactSection.astro` and the island, and nowhere else.)
- **No amount column.** BK-32 adds one, snapshotted at approval. Until then the
  admin page recomputes, and it should switch to the snapshot when that lands —
  the office needs to see what the customer was quoted, not what the table says
  today.
