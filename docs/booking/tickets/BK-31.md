# BK-31 — Assessment tier selection at booking

**Status:** draft 2026-08-16 (promoted from "proposed" to **prerequisite**).
**Phase:** P9 · **Tier:** Reviewed (public write path; the value becomes a
charge) · **Depends on:** BK-27 (shipped), BK-29 (shipped) · **Blocks:** BK-32.
**Deploy:** 2, first ticket after the idempotency fix. **Migration:** 006.

Prepay cannot ship without this. The payment link charges an amount, and the
amount is whatever the customer chose here.

## The deleted clause

The ROADMAP's earlier BK-31 row said the ticket was *"non-binding by design:
the form must say the choice can change on the day"*. **That is deleted, not
softened** (client, 2026-08-16). The tier is what gets charged, so it binds.
`FEE_TERMS_OUTRO`'s "Tell the tech on the day which of these you want" dies with
it — BK-36 owns the replacement sentence.

## Scope

1. **Radio group** in the terms box on step 3 of `BookingForm.svelte`, and on
   the homepage booking section, matching wherever `FEE_TERMS_ITEMS` renders.
   Required, with **no default selection** — a pre-selected $399 is a customer
   charged a tier they never looked at, and a pre-selected anything else is
   worse.

   Placement: below `FEE_TERMS_CREDIT`, above the ack checkbox. The ack label
   says "the terms above", which is a claim about page order that
   `verify-cutover.ts` should pin.

2. **`assessment_tier`** — `TEXT CHECK (assessment_tier IN ('standard',
   'report', 'sketch'))`, nullable. NULL is correct and permanent for admin
   entries and for every row predating the migration, on exactly the reasoning
   `terms_acked_at` records in `005-assessment-terms.ts`. Nothing is
   backfilled; there is no NOT NULL to add later.

3. **Prices live server-side only.** `ASSESSMENT_TIERS` in `booking-config.ts`,
   keyed by tier, in **cents, ex-GST**: `standard: 39900`, `report: 69900`,
   `sketch: 119900`.

   **The form posts a tier key, never an amount.** This is the whole defence
   against a tampered payload paying $1 for the sketch tier, and it is the
   reason the constant is cents-integer rather than a float or a display
   string. The existing `FEE_TERMS_ITEMS` strings stay the customer-facing
   copy; the numbers must agree, and a verify assertion should say so rather
   than trusting two hand-maintained lists.

4. **Validation** through the existing `entry` seam in `booking-payload.ts`:
   required when `'public'`, optional when `'admin'` — the same shape as the
   `terms_acked_at` gate at `:249`, riding the same discriminator, for the same
   client exemption.

5. **Renders**: internal email, customer email, admin detail page, and the
   admin edit form (the office must be able to change a tier when a customer
   upgrades on site).

6. **Upgrade path.** Changing the tier on a `confirmed` row **does not
   re-charge**. The delta is collected on site or added to the invoice — out of
   scope here, and the admin edit control must say so beside itself rather than
   implying a charge follows. Under P9 that control edits a value that has
   already been paid against; silence there is how somebody gets billed twice.

## Out of scope

- Charging anything. That is BK-32.
- The terms rewrite. That is BK-36, and the two must reach the browser in the
  same deploy — a picker beside "tell the tech on the day" is a self-
  contradicting page.

## Risk areas for the reviewer

- Price integrity: no amount may originate in a request.
- The admin exemption must remain structural (hard-coded `entry: 'admin'`), not
  conventional.
- Tier copy and tier prices are two lists that must not drift.
- A `confirmed`-row tier edit must not look like it triggers a charge.

## Acceptance criteria

1. A public booking with no tier selected is rejected with a field error; the
   island routes it to the right step.
2. A public booking with a tier not in the closed set is rejected.
3. An admin entry with no tier saves, and stores NULL.
4. A payload carrying an *amount* has it ignored — the stored tier and the
   server-side price are the only sources of truth.
5. The tier appears in both emails and on the admin detail page.
6. The prices in `ASSESSMENT_TIERS` and the figures in `FEE_TERMS_ITEMS` agree,
   asserted by a verify script rather than by eye.
