# BK-03 — Booking form island

**Status:** committed 2026-08-08 — plan-reviewed (NEEDS REVISION, 14 findings),
implemented, implementation-reviewed (SHIP WITH FIXES, 9 should-fixes + nits).
All findings applied, none disputed. Gates green, red-first 14/14, browser pass
re-run after the fixes. **Done.**
**Phase:** P2 · **Tier:** Standard · **Depends on:** BK-01, BK-02, BK-12

Standard: a public form, but every rule it enforces is already enforced
server-side by BK-01 and BK-02. It writes nothing itself; it holds insurance
identifiers and CASL consent only long enough to POST them. Plan review plus
implementation review, lighter prompts.

## Goal

The visitor-facing half of the booking system: pick a time, give us the job
details, optionally attach photos, consent, submit. Everything BK-01 and BK-02
built is currently reachable only by `curl`.

## Scope

1. `src/lib/booking-form.ts` — the pure half of the island. File acceptance,
   payload assembly, step validation, submit-guard state, and server-response
   mapping, with no DOM and no network, so `scripts/verify-booking-form.ts` can
   check it the way `verify-booking-payload.ts` checks the validator.
2. `src/components/BookingForm.svelte` — the island. Three steps, availability
   picker, insurance toggle, uploads, consent.
3. `src/pages/book.astro` — the host page.
4. A `noindex` prop on `src/layouts/Layout.astro`, plus the `/book` sitemap
   exclusion. See Assumptions.
5. `scripts/verify-booking-form.ts` + `npm run verify:booking:form` — pure.
6. `scripts/verify-booking-smoke.ts` + `npm run verify:booking:smoke` — the
   live-endpoint pass against `astro dev` and the Neon dev branch.

## Out of scope

- **The confirmation experience and the conversion event — BK-04.** BK-03 ends
  at a minimal inline "you're booked" panel carrying the id and the slot label.
  It is deliberately plain; BK-04 replaces it.
- Replacing the contact form, nav links, and the `ContactForm.svelte` 308 bug —
  BK-10. `/book/` is reachable by URL only until then.
- Confirmation email/SMS — BK-05/BK-06. Nothing is sent when this form submits.
- Rescheduling or cancelling. Settled with the client on 2026-08-08: cancelling
  is a phone call at launch, so the form carries the phone number and no cancel
  affordance.
- **Removing an attached file** — see "No remove button" below. Not an
  oversight; it cannot be built honestly at this layer.
- The 13 pre-existing `svelte-check` a11y warnings (ROADMAP Known traps, owner
  BK-10). This ticket must not *add* any — see AC17.

## Design notes

### Steps

Three, not five. Each extra step is a drop-off point, and the natural fear of a
long form is what a restoration customer in a flooded basement has least
patience for.

1. **When** — date strip + slot buttons, from `GET /api/booking/availability/`.
2. **Where and what** — name, phone, email, service, address, city, postal
   code, description, then the insurance toggle and its three conditional
   fields in the same step. Payment route is a decision about *this job*, not a
   separate chapter.
3. **Photos and confirm** — optional uploads, SMS consent, a summary of the
   chosen slot, submit.

Steps are client-side only. There is no server-side wizard state: the whole
payload posts once, at the end, to `POST /api/booking/create/`.

### The field contract, enumerated

Read off `booking-payload.ts` rather than inferred, so client and server
validation cannot drift. Step 1 owns `slot_start`; step 3 owns `sms_consent`
and `draft_token`; everything else is step 2.

| Field | Required | Rule | Max |
| --- | --- | --- | --- |
| `name` | yes | non-blank | 120 |
| `phone` | yes | 10 digits, or 11 starting with 1 | 40 |
| `email` | no | loose `x@y.z` if present | 200 |
| `service` | yes | one of the 10 `SERVICE_LABELS` keys | 60 |
| `address` | yes | non-blank | 300 |
| `city` | no | server defaults to `Edmonton` | 120 |
| `postal_code` | no | — | 20 |
| `description` | no | — | 4000 |
| `payment_route` | yes | `insurance` \| `private` | — |
| `insurer_name` | **only if insurance** | non-blank on that route | 160 |
| `policy_number` | no | insurance route only | 80 |
| `claim_number` | no | insurance route only | 80 |
| `slot_start` | yes | the exact `start` string availability returned | — |
| `sms_consent` | no | boolean or omitted — **never `null`** | — |
| `draft_token` | no | string or **key absent** — never `null` | — |

Every `maxlength` attribute is driven from `MAX_FIELD_LENGTHS`, not typed by
hand. `null` is called out because `booking-payload.ts:180-187` 422s on it: the
assembler must *omit* the key, not send an empty one.

### Trailing slashes — the trap that bites clients, not servers

Every fetch goes through the constants in `booking-config.ts`
(`BOOKING_AVAILABILITY_ENDPOINT`, `BOOKING_CREATE_ENDPOINT`,
`BOOKING_DRAFT_ENDPOINT`, `BOOKING_UPLOAD_ENDPOINT`). No string literal for a
path appears in the island. `trailingSlash: 'always'` makes the unslashed form
308-redirect, and a 308 on a POST is *not* obviously broken — the browser
re-issues the POST to the new location, so it may appear to work while costing
a round trip, and `ContactForm.svelte` has been quietly eating one for months
(BK-10). `handleUploadUrl` gets the same treatment: the SDK resolves it with
`new URL(url, location.href)` (`client.js:441`), so it is a path like any other.

### Failure states are the actual deliverable

The happy path is the easy half. Three endpoints can fail and BK-01 explicitly
handed their presentation to this ticket.

**Availability (`GET`).** On any DB failure `availability.ts:74` returns 500
with `{ error }` and **no `dates` key** — deliberately, because an empty
calendar is indistinguishable from "fully booked" and would turn every visitor
away while looking healthy (`availability.ts:70-72`, BK-01 §"DB failure"). The
island must therefore treat *both* a non-200 and a 200 whose body has no
`dates` array as a load failure, and render a visible message with the phone
number. Reading `data.dates.map` off that body throws during render and leaves
a blank card — which discards precisely the distinction BK-01 paid for.

**Draft mint (`POST /api/booking/draft/`).** Returns 429 when the IP has
minted 20 drafts in the hour (`draft.ts:43-48`) and 500 when
`BOOKING_DRAFT_SECRET` is missing (`draft.ts:51-56`). Both must surface at the
file-picker as "photos can't be attached right now — you can still book, or
call us". A booking without photos is still a booking; failing the draft must
never block the appointment.

**Uploads — the server's messages never reach the browser.** `upload-token.ts`
raises careful text ("That file type is not supported", "You can attach up to
10 files", "Upload session expired — please reload the form", "Each file must
be under 100.0 MB"). None of it is reachable: on any non-2xx the SDK discards
the response body and throws a fixed string,
`new BlobError("Failed to  retrieve the client token")` — including the double
space (`node_modules/@vercel/blob/dist/client.js:398-401`). So **the browser's
own pre-checks are the only source of a readable upload message**, which
sharpens the "mirror, not replace" rule below from a nicety into the mechanism.
A rejected `upload()` renders a generic per-file failure with a retry, never
the SDK's string.

### Uploads

Read from the installed SDK (`node_modules/@vercel/blob/dist/client.d.ts`),
not from memory:

```ts
upload(pathname, file, {
  access: 'public' | 'private',   // required
  handleUploadUrl: string,        // required
  clientPayload?: string,
  contentType?: string,
  multipart?: boolean,
  onUploadProgress?: (e) => void,
  abortSignal?: AbortSignal,
})
```

- **`access: 'private'`.** These are photographs of the inside of someone's
  damaged home. `'public'` would mint a permanently public URL for each one,
  and the ROADMAP already records the store as private with BK-09 owing an
  authenticated proxy for admin viewing.
- **Our route cannot enforce this, but the store does.** `onBeforeGenerateToken`
  returns only `allowedContentTypes | maximumSizeInBytes | validUntil |
  addRandomSuffix | allowOverwrite | cacheControlMaxAge | ifMatch |
  tokenPayload | callbackUrl` (`client.d.ts:346-349`); `access` travels as the
  `x-vercel-blob-access` header on the PUT and is never sent to the handleUpload
  route at all (`client.js:381-387`). The plan concluded from this that customer
  privacy rested on one client-side argument. **That was too pessimistic**, and
  the red-first pass proved it: uploading with `access: 'public'` fails outright
  with `Cannot use public access on a private store. The store is configured
  with private access.` The guarantee is store-level, so a hostile client cannot
  publish its own uploads either. Verified positively as well — an
  unauthenticated GET of a returned blob URL answers **403**.
- **`clientPayload`** carries `{ draftToken, size: file.size, originalName }` —
  exactly what `parseClientPayload` accepts (`upload-token.ts:30-31`).
- **`pathname`** comes from `buildUploadPathname(draftId, contentType)`. On
  **retry, the pathname is reused, not regenerated**: `upload-token.ts:100`
  excludes the current pathname from the quota count specifically so a retry
  does not double-charge, and `buildUploadPathname` mints a fresh UUID every
  call (`booking-uploads.ts:39`) — regenerating defeats the exclusion and burns
  a second slot against the draft's cap of 10.
- **`multipart: true` above 10 MB.** A 100 MB phone video on hotel wifi is the
  case this system is *for*, and a single PUT that dies at 90% restarts at zero.

### No remove button

A file's `appointment_files` row is written at *token-mint* time
(`upload-token.ts:113-122`), and BK-02's CTE claims every unclaimed row for the
draft regardless of `upload_state` (`booking-commit.ts:66-73`). So a remove
button would be a lie twice over: the booking still claims the file, and the row
still counts against the server's 10-file and 300 MB caps
(`upload-token.ts:106-111`). Honest removal needs a delete endpoint scoped to a
verified draft — a server surface, with its own authorization, which is not
this ticket. BK-03 therefore ships **no remove affordance**, and the file list
says uploads are final for this booking. Recorded here so the next reader sees
a decision rather than a gap.

### The localhost callback trap

`onUploadCompleted` never fires against localhost, so in dev every
`appointment_files` row stays `upload_state = 'pending'` and `url` stays NULL.
BK-02's CTE therefore claims files regardless of `upload_state`, and this
island must agree: **a file counts as attached when `upload()` resolves, never
when the server says `'uploaded'`.** The island never reads `upload_state` and
never polls for it. Getting this wrong makes dev look broken and makes
production drop photos whose callback was slow.

### Draft tokens are minted lazily

`POST /api/booking/draft/` is called on the *first file selection*, not on
mount. `DRAFT_RATE_LIMIT_PER_HOUR` is 20 per IP, and minting on mount would let
20 page views from one office's NAT exhaust the funnel for everyone behind it,
while also issuing a signed token to every bounce. One draft per form session;
subsequent files reuse it. A booking with no photos omits `draft_token`
entirely, which BK-02 accepts as a zero-file booking.

### Client-side limits mirror the server, they do not replace it

`MAX_FILES_PER_BOOKING` (10), `MAX_FILE_BYTES` (100 MB) and `MAX_TOTAL_BYTES`
(300 MB) are checked before upload. Per the failure-states note, this check is
not merely a nicety — it is the only place a specific limit message can be
produced at all. The token mint re-checks all three; that re-check is the
enforcement, this one is the explanation.

### iPhone content types

`ALLOWED_UPLOAD_TYPES` includes `image/heic`, `image/heif` and
`video/quicktime` because that is what iPhones produce. But browsers sometimes
report `file.type` as the empty string for HEIC, and `buildUploadPathname`
throws on an unknown type. So the island resolves a content type as
`file.type` → falling back to the filename extension via `UPLOAD_EXTENSIONS`
reversed → rejecting with a readable message. Without the fallback the most
common phone in Edmonton silently cannot attach a photo.

### Server responses have codes for a reason

| Status | Meaning | Behaviour |
| --- | --- | --- |
| 201 | Booked | Success panel with `id` and `slotLabel`; cross-check `filesAttached` against the browser's own count and log a mismatch |
| 422 + `fields[]` | Per-field validation | Map to fields, jump to the earliest step holding an error, focus it |
| 422 **without** `fields`, or an unmapped field | Malformed JSON (`create.ts:59`), or `_` / `sms_consent` / `draft_token` / a `FORBIDDEN_KEYS` entry — none of which has an input | Form-level message, submit re-enabled. Never `undefined.map`, never a silent dead form |
| 409 `slot_unavailable` | Never offerable / no longer offered | Refetch availability, return to step 1, keep every other answer |
| 409 `slot_taken` | Lost the race | Same as above, different message |
| 400 | Draft token bad or expired | Drop the local draft, tell the user to re-attach photos |
| 429 | Rate limited | "Please try again shortly", offer the phone number |
| 500 | Ours | "Please call us instead" with the number |

A 409 must never dump the form. The visitor typed an address and a description;
losing that because someone else booked 13:30 is how a booking becomes a phone
call to a competitor.

### Submission is single-flight, and that guard is testable

The submit button is disabled while a request is in flight and until hydration
(`ContactForm.svelte`'s precedent — a pre-hydration submit does a native GET
and silently drops everything). BK-02 declined idempotency explicitly on the
grounds that "BK-03's disabled submit button covers the case"
(`BK-02.md:287-295`), so this button is load-bearing.

Load-bearing means tested. The guard lives in `booking-form.ts` as an explicit
state transition (`beginSubmit()` returns whether the caller may proceed), not
as a bare `disabled` attribute — a DOM attribute cannot be asserted by a pure
script, and "the button was greyed out" is not evidence.

### Consent

Unchecked by default and never pre-checked: under CASL the presence of
`sms_consent_at` *is* the consent, and a pre-checked box is not consent. Copy
states who is texting, what for, and how to stop. Booking is possible without
it — it gates reminders, not the appointment.

### The island never re-derives time

`AvailableSlot` carries `start` (ISO UTC), `time` (`HH:MM` local) and `label`
(`Tue, Aug 4 · 1:30 PM`), all computed server-side in America/Edmonton. The
island renders `label`/`time` as given and posts `start` back verbatim. A
browser in another timezone — a landlord booking from Vancouver — must see
Edmonton times, and `toLocaleString` in the island would quietly show them
theirs.

## Acceptance criteria

1. `/book/` renders the form and loads availability from
   `BOOKING_AVAILABILITY_ENDPOINT`; a day with no slots is visibly unavailable
   rather than absent-and-unexplained.
2. A failed availability load — non-200, **or** a 200 whose body has no `dates`
   array — renders a visible error with the phone number, and never an empty
   calendar or a blank card.
3. Every network path in the island uses a `booking-config.ts` constant.
4. Step validation blocks advancing with a missing or malformed required field,
   per the enumerated contract, and messages appear per field.
5. The insurance toggle shows insurer/policy/claim only on the insurance route,
   and switching back to private drops them from the outgoing payload.
6. A booking with no photos omits `draft_token` as a key and succeeds.
7. Selecting a file mints exactly one draft for the session, however many files
   follow.
8. A draft-mint 429 or 500 leaves the form bookable, with a message saying
   photos are unavailable — it never blocks submission.
9. A file over 100 MB, an 11th file, or a total over 300 MB is refused in the
   browser with a specific message, before any upload starts.
10. An unsupported type is refused; a HEIC file whose `file.type` is empty is
    *accepted* via the extension fallback.
11. A rejected `upload()` shows a generic per-file failure with a retry, and
    never surfaces the SDK's `"Failed to  retrieve the client token"`. A retry
    reuses the same pathname.
12. A file shows as attached when `upload()` resolves, with no read of
    `upload_state` anywhere in the island.
13. 201 shows the id and slot label. 422 with fields maps and jumps to the right
    step; 422 without fields, or with an unmapped field, shows a form-level
    message and re-enables submit. Both 409 codes refetch availability and
    preserve all other answers. 400/429/500 show their distinct messages.
14. `beginSubmit()` returns false for a second call while one is in flight, and
    the island issues exactly one POST for a double-click.
15. No path in the island produces a 308.
16. No response body or client state is rendered that contains
    `policy_number` or `claim_number` outside their own inputs.
17. `svelte-check` reports **zero new warnings** — the island ships a11y-clean
    even though the gate would tolerate warnings.

## Risks

- **The smoke test touches the production Blob store.** There is no branch
  equivalent for Blob. Mitigation: one 160-byte file, deleted in the same run,
  and the orphan cron would collect it within 24 h regardless.
- **`access: 'private'` is unproven on this store.** If the store rejects it the
  upload fails outright, which the smoke test surfaces. Falling back to
  `'public'` would be a privacy decision, not a workaround, and belongs to the
  user rather than the implementer.
- A visitor who abandons after uploading leaves rows the cleanup cron collects
  in 24 h. Already designed for; noted so it is not rediscovered as a leak.

## Assumptions log

- **`/book/` ships `noindex` and out of the sitemap until BK-10.** The sitemap
  exclusion alone does not stop indexing: `Layout.astro:74-77` hard-codes
  `content="index, follow"` with no override, so the stated goal — not ranking
  before cutover — needed a `noindex` prop on the layout. Both come off in
  BK-10. The prop is a small addition to a shared layout and is defaulted to
  `false`, so no existing page changes.
- **`client:load`, not `client:visible`.** The form is the entire purpose of the
  page and sits above the fold; deferring hydration only lengthens the window in
  which the submit button is disabled.
- **The success panel is deliberately thin.** Anything more is BK-04's, and
  building it twice invites the two versions to disagree.
- **`multipart` threshold of 10 MB** is a judgement call, not a measured one.
- **Service list comes from `src/data/services.ts`** plus the literal `other`,
  matching `ContactForm.svelte`. Its nine ids are exactly `SERVICE_LABELS`
  minus `other`.
- **The smoke test is split** between a scripted endpoint pass (a real gate with
  real output) and an MCP-driven browser pass (transcript only). Claiming the
  browser half as an npm script would be claiming a gate nobody can re-run.

The risk section's escalation path was never needed.

## Decisions taken during implementation

Recorded here because they were not in the approved plan and a reviewer should
see them as decisions rather than discover them as diffs.

- **`booking-payload.ts` now exports `isPlausiblePhone` and
  `isPlausibleEmail`.** The island validates with the *same* predicate the
  endpoint runs. The alternative — a second copy of "what a valid phone number
  is" in the browser — is exactly the drift that module's own header warns
  about, and it would show up as a form rejecting what the server accepts.
- **`booking-uploads.ts` now exports `EXTENSION_TO_TYPE`.** The browser needs
  the reverse map for the empty-`file.type` HEIC fallback. It was already
  computed there; only the `export` keyword is new.
- **The draft POST sends `Content-Type: application/json` despite having no
  body.** Astro's origin check forbids a POST carrying *no* content-type unless
  `Origin` matches, and allows any non-form content-type regardless
  (`core/app/origin-check.js:16-21`). A browser always sends `Origin`, so this
  changes nothing in production — it removes a silent dependency on a header we
  do not control. Found by the smoke script getting a 403.
- **The smoke test proves isolation before it writes.** It inserts a blackout on
  the dev branch and asserts the running server can see it, aborting if not.
  Asserting afterwards would mean discovering a misconfiguration by having
  already created a real appointment on production.
