# BK-12 — Make the typecheck gate see .astro and .svelte

**Status:** committed 2026-08-08 — Light tier, no reviews by design. Gates
green, red-first pass 6/6. **Done.**
**Phase:** P2 · **Tier:** Light · **Depends on:** nothing · **Blocks:** BK-03

Light: build tooling and two library one-liners. No public surface, no data,
nothing irreversible. Gates only — no plan review, no implementation review.

## Goal

`npm run typecheck` currently runs `tsc --noEmit`, which never opens a `.astro`
or `.svelte` file. BK-03 delivers a Svelte island, so today's gate would report
green over the exact code it cannot read. Make the gate cover the file types the
project actually ships, and clear the `process.env.X ?? import.meta.env.X`
TypeError trap while the tooling is being touched.

## What was measured first

Both facts below were probed on this tree, not recalled. They set the scope.

1. **`astro check` reports 0 errors on the current tree** (75 files, 23 hints),
   and it *does* cover `scripts/**` — a planted `const zz: number = "nope"` in
   `scripts/zz-probe.ts` was reported. So dropping `tsc --noEmit` loses no
   coverage.
2. **`astro check` does not look inside `.svelte`.** A component containing
   `const n: number = 'definitely not a number'`, imported *and rendered* from a
   page, left `astro check` green — the checked-file count went 75 → 76 for two
   added files, so the `.svelte` one was never in the set. `svelte-check` caught
   the same probe immediately.

Fact 2 is why this ticket is not "install `@astrojs/check`". `astro check`
alone would install a gate with precisely the blind spot the gate exists to
remove.

## Scope

1. `@astrojs/check` and `svelte-check` as devDependencies.
2. `npm run typecheck` becomes `astro check && svelte-check --tsconfig
   ./tsconfig.json`. **One script, both checks** — not a second command a future
   session can forget exists. `&&` fails on either.
3. Fix the two `VideoReel.svelte` type errors that `svelte-check` finds. This is
   **gate enablement, not scope creep**: a gate cannot land red, so making the
   new gate green is this ticket's job. Two null guards, no behaviour change.
4. `src/lib/env.ts` — one `readEnv(name)` helper, replacing every
   `process.env.X ?? import.meta.env.X` in the tree. `grep` found **three**
   sites, not the two the ROADMAP trap names: `draft-token.ts`, `db.ts`, and
   `src/pages/api/cron/cleanup-uploads.ts:31` (`CRON_SECRET`). The trap is a
   pattern, not a file list, so the third one is in scope rather than deferred.
5. `scripts/verify-env.ts` + `npm run verify:env` — the regression assertions
   for item 4, run under plain Node where the trap actually bites.

## Out of scope

- The 13 a11y warnings `svelte-check` reports (`ContactForm.svelte` labels,
  `Navbar.svelte` roles, `VideoReel.svelte` static-element handlers). They are
  warnings, they do not fail the gate, and fixing them is markup surgery on
  three unrelated components. Logged to ROADMAP Known traps with an owner.
- The 23 `astro check` hints (`is:inline` on JSON-LD scripts, an unused import
  in `blog/[slug].astro`, a deprecated `z.string().email()`). Same reasoning.
- The **bare** `import.meta.env.X` reads in `middleware.ts`, `api/contact.ts`,
  `api/admin/reply.ts`, `api/admin/login.ts`, `Analytics.astro`, and
  `ContactForm.svelte`. They carry no `process.env` fallback, so they cannot hit
  this TypeError — they simply require a Vite runtime, which is all they ever
  run under. Migrating them to `readEnv` is a defensible tidy-up and is not this
  ticket's job.

## Design notes

- **Why the fallback cannot simply be deleted.** The obvious fix is
  `process.env.X` alone, and it is wrong. Vite loads `.env` files into
  `import.meta.env` and never into `process.env`, so under `astro dev` the
  process store is empty for exactly these keys. Both stores are genuinely
  needed; what is broken is the *access*, not the intent.
- **What actually throws.** `import.meta.env` is undefined outside Vite. `??`
  only short-circuits on the left operand being null/undefined, so when `X` is
  unset the right operand evaluates, and `undefined.X` throws
  `Cannot read properties of undefined (reading 'X')` — a TypeError that reads
  like a code bug, in place of the deliberate "not configured" error. It fires
  only in the unset case, which is why it survived: every environment that
  works never reaches the second operand.
- **`readEnv` treats the empty string as unset.** `vercel env pull` writes
  sensitive variables back as `""` (ROADMAP Known traps), and both `loadEnv`
  implementations in `scripts/` already skip empty values. Under `??` an
  `X=""` short-circuits and never consults `import.meta.env` at all. Matching
  `loadEnv` makes the three readers agree.
- **Behaviour at the call sites is unchanged.** `getDb()` still throws
  `DATABASE_URL is not configured`; `secret()` still throws
  `BOOKING_DRAFT_SECRET is not configured`. This ticket changes what happens on
  the way to those errors, not the errors themselves.
- **`verify:env` must run under plain Node.** Run through Vite it would pass
  against the broken code, because `import.meta.env` would exist. `tsx` is the
  reproduction, not an implementation detail.

## Acceptance criteria

1. `npm run typecheck` runs both checks and exits non-zero if either finds an
   error.
2. A type error planted in a `.astro` file fails the gate.
3. A type error planted in a `.svelte` file fails the gate.
4. A type error planted in `scripts/*.ts` fails the gate — the coverage
   `tsc --noEmit` provided today.
5. `astro check` and `svelte-check` both report zero errors on the tree as
   committed.
6. With `DATABASE_URL` unset under plain Node, `getDb()` throws
   `DATABASE_URL is not configured` — not a TypeError.
7. With `BOOKING_DRAFT_SECRET` unset under plain Node, minting a draft token
   throws `BOOKING_DRAFT_SECRET is not configured` — not a TypeError.
8. `X=""` reads as not configured, not as the value `""`.
9. A set value is returned unchanged.
10. `npm run build` still passes — `readEnv` survives Vite's `import.meta.env`
    handling.

## Assumptions log

- **`svelte-check` warnings do not fail the gate.** `--fail-on-warnings` is not
  passed, deliberately: 13 pre-existing a11y warnings would make the gate
  unlandable, and turning them into errors is a separate piece of work with a
  separate owner.
- **`astro check` runs first, so a failure there hides `svelte-check` output**
  until it is fixed. Accepted — the alternative is running both unconditionally
  and reporting a combined status, which is a shell script this repo does not
  otherwise have.
- **`@astrojs/check` is `^0.9.10`, `svelte-check` is `^4.7.5`** against Astro 7
  and Svelte 5. Both resolved without peer warnings and both were observed
  catching a planted error, which is the only compatibility claim being made.
- The empty-string rule (Design notes) is a deliberate small behaviour change,
  not a side effect.
