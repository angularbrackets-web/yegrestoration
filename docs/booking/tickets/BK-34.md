**Deploy:** 1 (with BK-35). **Migration:** none.

Photos for phone-in bookings currently arrive by email and never attach to the
appointment. The office ends up with the pictures in one inbox and the job in
another system, which is the problem the upload funnel was built to solve for
web bookings and never solved for phone ones.

## Why there is no migration

The obvious reading — "appointment uploads need a new pathname shape" — is
wrong, and following it would mean touching `parseUploadPathname`,
`buildUploadPathname` and the island's upload logic for no gain.

`appointment_files` already has **both** `appointment_id` and `draft_id`. The
web funnel writes rows with `draft_id` set and `appointment_id` NULL, then
claims them at commit. A phone booking runs the other way: the appointment
exists first, so there is nothing to claim. But nothing stops us writing a row
with **both** set from the start.

So an appointment upload link carries a `draftId` that the server minted and
signed *alongside* the appointment id. Files land under the existing
`bookings/<draftId>/` prefix, `parseUploadPathname` is untouched, and the row
is written with `appointment_id` already populated.

Two things fall out of that for free:

- **The cleanup cron is already correct.** It deletes rows where
  `appointment_id IS NULL` (`appointment_files_orphan_idx`). Ours are never
  NULL, so an appointment upload is never swept, and it needed no special case.
- **The admin file proxy is already correct.** `claimedFilePathname` serves
  only claimed rows (`api/admin/files/[id].ts:40`). Ours are claimed from birth.

## BK-34a — the mechanism (unblocked)

### Scope

1. **Appointment upload token** in `draft-token.ts`. A second token type, HMAC
   over `appointment.<appointmentId>.<draftId>.<issuedAt>`, TTL 72h — a
   customer texted at 4pm looks at it that evening or the next morning.

   **A distinct version tag (`a1`, vs the draft token's `v1`), and the
   appointment id inside the signed payload.** Two token types over one secret
   is exactly where a confused-deputy bug lives: without the tag, a value that
   verifies as one type could be replayed as the other. `verifyDraftToken` must
   reject an appointment token and vice versa, and that rejection is an
   assertion, not a comment.

2. **`POST /api/booking/appointment-upload-token/`** — the Blob client-token
   route for this path. Mirrors `/api/booking/upload-token/` and reuses every
   constraint it already enforces: content-type whitelist, `maximumSizeInBytes`
   pinned to the declared size, `addRandomSuffix: false`, `allowOverwrite:
   false`. Differences, all deliberate:

   - authorization is the appointment token, not the draft token;
   - the file-count and byte-total caps are counted against **`appointment_id`**
     rather than `draft_id`, so a customer who is texted a second link cannot
     start a fresh 10-file / 300 MB budget;
   - the inserted row sets `appointment_id` as well as `draft_id`;
   - **it is rate-limited.** `/api/booking/upload-token/` has none — a standing
     Known trap, tolerated there because a draft token lives 6h and is itself
     minted behind a throttle. This token lives **72h**, which is twelve times
     the exposure, so the same omission is not tolerable here. Bucket is
     per-appointment (`appt-upload:<id>`), not per-IP: the customer is on a
     phone behind CGNAT and the thing worth bounding is the link, not the
     network.

3. **Public page `/upload/?t=<token>`.** Outside `/admin`, so the middleware
   does not guard it (`middleware.ts` gates `/admin` and `/api/admin` only) —
   the token is the authorization.

   **The token is in the QUERY STRING, not a path segment**, and that is a
   deployment constraint rather than a preference. `trailingSlash: 'always'`
   makes the Vercel adapter emit a pre-filesystem 308 that strips the trailing
   slash from any path whose last segment contains a dot; every token ends in
   `.<64 hex>`, so `/upload/<token>/` — the shape this ticket originally shipped
   — 308'd to a form no route matched and fell through to `/404.html`, for 100%
   of links. See blocker B1 in the implementation review below.

   **It renders the appointment date and the customer's first name, and
   nothing else.** No address, no phone, no service description, and under no
   circumstances `policy_number` or `claim_number` — the locked PII rule reads
   on this surface exactly as it reads on an SMS body. Anyone holding the link
   holds the link; it must be worth nothing to a stranger.

   An invalid, unknown or expired token renders one neutral page ("this link
   has expired — call or text us") with **no** distinction between the cases,
   for the same reason the availability endpoint does not say *why* a slot is
   unavailable.

   Writes only. The page must never list or link the files already attached:
   an upload capability must not become a read capability for the damage
   photos of whoever held the link last.

4. **Admin fallback file input** on `/admin/appointments/[id]`. For agents who
   already have the photos in their inbox. Behind `/api/admin/`, so the
   middleware has already authenticated the caller. This is the arm that works
   on day one with no SMS at all, and it should be built first.

5. **"Copy upload link" button** on the same page — mints a token and shows the
   URL. Until BK-34b, the office pastes it into their own texting app, and the
   link itself is already live.

### Out of scope

- Sending the SMS — BK-34b.
- Any change to the public booking funnel's own upload path. The two share
  `parseUploadPathname` and the caps, and that sharing is the point; do not
  fork them.
- Surfacing uploads back to the customer.

### Risk areas for the reviewer

- **Token confusion between the two types.** The highest-value thing to attack
  here. Both are HMAC over one secret.
- **Capability scope.** The link authorizes writes under one appointment's
  prefix and must confer no read of anything.
- **PII on the public page.** See the render list above.
- **Cap accounting.** Counted per appointment, with the current pathname
  excluded so a retry of a failed upload does not consume a second slot — the
  same exclusion `upload-token.ts:100` already makes.
- **Rate limit fail-open.** `consumeRateLimit` allows on DB error by design.
  Correct for booking; confirm it is acceptable on a 72h-lived link.

### Acceptance criteria

1. A minted appointment token verifies and yields `{appointmentId, draftId}`;
   a draft token handed to the appointment verifier returns null, and an
   appointment token handed to `verifyDraftToken` returns null.
2. A token past 72h returns null.
3. A tampered appointment id in the token fails the signature.
4. Uploading through `/upload/?t=<token>` writes an `appointment_files` row with
   **both** `appointment_id` and `draft_id` set, and the file appears on the
   admin detail page.
5. The 10-file and 300 MB caps are enforced across *all* files on the
   appointment, not per link — a second link cannot reset the budget.
6. `/upload/?t=<bad-token>` renders the neutral expired page and no appointment
   details, for a malformed token, an unknown appointment and an aged-out one
   alike — **and a missing `?t=` entirely lands on the same page**, which the
   query-string form makes reachable in a way the path form did not.
7. The page's HTML contains no address, phone, policy or claim number.
8. The admin fallback input attaches a file to the appointment and the result
   is indistinguishable, on the detail page, from a customer upload.
9. The rate limit rejects the **31st** token request in a window for one
   appointment. (Was "the 11th" — stale, and caught in implementation review.
   `APPOINTMENT_UPLOAD_RATE_LIMIT_PER_HOUR` is 30 deliberately: it has to cover
   the 10-file cap with room for retries on the bad phone connection this whole
   feature exists for. The AC was wrong, not the constant.)

### A live defect the gates would not have caught

`verifyAppointmentUploadToken` **throws** when `BOOKING_DRAFT_SECRET` is unset;
it does not return null. The first version of `/upload/<token>/` called it
unwrapped, so a misconfigured deploy answered Astro's HTML 500 to a customer who
had just been texted a link — reading as "this company's site is broken" rather
than "this link is old, call us".

Typecheck, build and the token suite were all green across it. It surfaced from
a `curl` against the dev server, whose `.env.local` carried
`BOOKING_DRAFT_SECRET=""` from a `vercel env pull` — the exact blank-value shape
`env.ts` documents, so this was a live production configuration rather than a
hypothetical. `create.ts` already wraps its `verifyDraftToken` call for this
reason and says so; the page now does the same.

Also found by the same smoke test: `formatSlot` ends in `"p.m."`, so a sentence
that ended on `{slotLabel}` printed `3:30 p.m..`. Fixed twice — once from each
end of the sentence — before the dash landed.

## Implementation review — 2026-08-16 (BK-34a)

Fresh reviewer, input-isolated (ticket + diff + gate output only). Gates
independently re-run by the reviewing session before the agent was spawned: all
green. The blocker and the four should-fixes were each re-verified against the
repo by the coordinator.

### Blocker

**B1 — every upload link 404s in production.** `astro.config.mjs:13` sets
`trailingSlash: 'always'`, which makes `@astrojs/vercel` emit this
**pre-filesystem** rule into `.vercel/output/config.json`:

```json
{ "src": "^/((?:[^/]+/)*[^/]+\\.\\w+)/$", "headers": { "Location": "/$1" }, "status": 308 }
```

Its intent is "a path that looks like a file should not have a trailing slash".
An appointment token is `a1.<id>.<uuid>.<ms>.<64 hex>` — the final URL segment
ends in `.` + word characters, and `encodeURIComponent` does not escape `.`, so
`appointmentUploadUrl` (`booking-config.ts:207-209`) produces a path that
matches unconditionally. Simulated against the route table from the build
already in the tree:

```
/upload/a1.4271.<uuid>.1755367200000.<64hex>/
  → 308 Location: /upload/a1.4271.<uuid>.1755367200000.<64hex>
  → rule 2 (^/((?:[^/]+/)*[^/\.]+)$) does NOT re-add the slash — last segment has dots
  → handle: filesystem — nothing
  → ^/upload/([^/]+?)/$ does NOT match — it requires the trailing slash
  → ^/.*$ → /404.html, status 404
```

Failure scenario: the office copies the link and texts it; the customer taps it,
is redirected once, and lands on the site's 404 page. This is 100% of links —
the signature is always 64 hex characters. No other route in the app has a dot
in its final segment, which is why nothing has hit this before.

It also silently defeats **AC6**: `/upload/garbage/` (no dots) still renders the
neutral 200 page while anything token-shaped 404s, so malformed and well-formed
tokens become distinguishable by status code — the opposite of the stated
property.

Why the gates missed it: the live smoke tests in the table above were run against
`astro dev`, which does not apply the Vercel route table. `typecheck`, `build`
and the token suite cannot see this class of defect at all.

Fix — stop putting dots in the URL segment. In rising order of blast radius:
(a) have `appointmentUploadUrl` swap `.` → `~` (or base64url the token) and
reverse it in the page frontmatter before verifying; (b) split the token across
path segments with `[...token].astro`; (c) move the token to a query string on
`/upload/`. Whichever is chosen, **the check that it is fixed must be a
route-table assertion** (regex the generated `.vercel/output/config.json` against
a sample link) or a preview-deploy curl. A dev-server smoke test cannot see it,
which is exactly how it got here.

### Should-fix

- **S1 — the 300 MB byte cap is defeatable to ~1 GB.**
  `appointment-upload-token.ts:127-149` and `:161-164`. `size_bytes` is only ever
  the client-*declared* value: `onUploadCompleted` (`:188-193`) writes
  `upload_state` and `url` but **not** `size_bytes`, despite
  `scripts/migrations/002-booking.ts:97-98` claiming it is "overwritten with the
  true size when the upload-completed callback fires". Because
  `ON CONFLICT (pathname) DO UPDATE SET size_bytes = EXCLUDED.size_bytes` accepts
  a *lower* value and the `f.pathname <> ${pathname}` exclusion removes the row
  from its own totals, a holder can: declare 100 MB → upload 100 MB → re-mint the
  same pathname declaring 1 byte, rewriting the row. Ten rounds (30 requests,
  inside the 30/hr limit) leaves 1 GB in the store while the DB believes 10 bytes
  are attached. The **file-count** cap still holds at 10 rows. Inherited verbatim
  from `upload-token.ts:95-122`, so per `/CLAUDE.md` the twin belongs in the
  ROADMAP's Known traps rather than being fixed inline — but AC5 as written
  claims the byte cap is enforced, and it is not. Fix here:
  `SET size_bytes = GREATEST(appointment_files.size_bytes, EXCLUDED.size_bytes)`,
  or refuse a token for a pathname whose row is already `upload_state = 'uploaded'`.
- **S2 — pending rows on an appointment are never swept and can permanently
  exhaust the file cap.** The cap counts rows regardless of `upload_state`
  (`:141-146`), and the cleanup cron only deletes `WHERE appointment_id IS NULL`
  (`cron/cleanup-uploads.ts:48-53`) — which is precisely the property this ticket
  relies on to keep appointment uploads from being swept. So a holder who
  requests ten tokens for ten pathnames and uploads nothing leaves ten `pending`
  rows, and from then on *every* token request for that appointment — including
  the office's own inline uploader, which posts to the same endpoint — is
  rejected with "You can attach up to 10 files", permanently. There is no admin
  UI to delete an `appointment_files` row. On the draft route this shape
  self-heals via the orphan cron; here it cannot. Fix: exclude stale `pending`
  rows from the count, or extend the cron to sweep old `pending` rows regardless
  of `appointment_id` (carefully — it must not race the web funnel's claim step).
- **S3 — the "barrier 2" assertion on the appointment verifier does not test
  arity.** `scripts/verify-appointment-upload.ts:133-137` feeds
  `a1.<uuid>.<ms>.<sig>`; `parts[1]` is a UUID, so with the arity check gone it
  is still rejected by the leading-zero id regex at `draft-token.ts:200`, not by
  arity. This is the **same defect as red row (g)** — fixed on `verifyDraftToken`
  and left standing on the appointment side. Re-run red-first by the reviewer:
  loosening `draft-token.ts:192` from `!== 5` to `< 4` produced exactly one
  failure, and it was *not* the labelled assertion — the line calling itself
  "barrier 2 … rejected on arity" stayed green. The file header at `:9-18` claims
  the three barriers "are asserted individually"; for this one that is false.
  Fix: promote the already-present `${minted.token}.extra` case (a *valid*
  appointment token with data appended) out of the malformed loop and label it,
  mirroring `:129-132`. Then re-observe red.
- **S4 — AC9's number contradicts the implementation.** AC9 says the limit
  rejects the **11th** request; `booking-config.ts:174` sets
  `APPOINTMENT_UPLOAD_RATE_LIMIT_PER_HOUR = 30`, and the comment at `:166-173`
  argues for 30 deliberately. The code is right and the AC is stale; rewrite it
  to 31 before marking it met.

### Nits

- `draft-token.ts:204-205` — `issuedAt` is canonicalised through `Number()`
  before re-signing, so `01786…`, `+1786…`, `" 1786…"` and `"1786…\n"` all verify
  to identical claims. Harmless malleability (same claims, same TTL), but the
  comment at `:197-199` shows the author guarded exactly this for the *id* field
  and not this one. Inherited from `verifyDraftToken:101`.
- `draft-token.ts:202` — `Number.isSafeInteger` admits ids to 2^53 while
  `parseAppointmentId` (`booking-admin-entry.ts:353`) caps at int4; the comment
  says "exactly as `parseAppointmentId` requires", and it is not exactly.
  Unreachable today.
- `upload/[token].astro:132` — `href={`tel:+17804793285`}` is a template literal
  with no interpolation, hardcoding a number that exists as `SUPPORT_PHONE` two
  lines below. House style elsewhere, but the backticks are pointless.
- `admin/appointments/[id].astro:100` — `Astro.site ?? Astro.url.origin` makes a
  preview deployment hand out a link pointing at production.
- `appointment-upload-token.ts:107` — the rate limit is consumed after
  `parseUploadPathname` and the size checks, so malformed requests cost nothing
  against the bucket. Fine (they cost no SQL either), but the bucket does not
  count total request volume.
- `upload/[token].astro:59-77` — no appointment-status check, so a `cancelled`
  appointment still accepts uploads for the rest of the 72h. Probably desirable;
  currently undocumented.

### Attack log — token confusion

21 hand-built forgeries against the real verifiers with the production secret.
**All rejected**, except `issuedAt` re-encodings (nit above, no privilege
change). The load-bearing rejections: retagged draft tokens die on arity; a
5-part reshaped draft token dies on the **HMAC**, because the signature covers
`<uuid>.<ms>` and the verifier computes `<id>.<uuid>.<ms>`; id re-encodings
`05`, `+5`, `5e0`, `0x5`, `" 5"` die on the **id regex at `:200`** — without it,
`Number('05') → 5` re-derives the exact signed payload and the token verifies.

No signed-string ambiguity exists, and structurally so: both verifiers split on
`.` and hard-check arity *before* reconstructing, so no component reaching the
HMAC can contain a `.`. A draft payload always has exactly one dot, an
appointment payload exactly two; one string can never parse as both.

**"Any one barrier alone suffices" still holds** for all three — but with a
correction to the comment at `draft-token.ts:26-32`: there is in practice a
**fourth** barrier, the id regex at `:200`, and it is not decorative. It is the
only thing between `Number()`'s numeric normalisation and a re-derived valid
payload. Name it, so a future reader who trusts "three barriers" does not remove
the regex as redundant shape-checking.

### Verified correct

Capability scope is genuinely tight. The appointment id comes only from
`verifyAppointmentUploadToken` — never from URL, query or `clientPayload` — so
the rate-limit bucket `appt-upload:${appointmentId}` is not client-influenceable,
and it is consumed *before* the existence check, the INSERT and the mint.
`parseUploadPathname` takes the draft id from the signature only, and rejects
`..`, `//`, nested paths, non-UUID filenames and unknown extensions; since
`draftId` is a fresh `crypto.randomUUID()` per mint, one link's prefix is
unguessable from another's. Read from the installed SDK
(`@vercel/blob/dist/client.js:273-281`, v2.6.1): `handleUpload` pins the client
token to the single validated pathname, alongside `addRandomSuffix: false`,
`allowOverwrite: false`, a single-entry `allowedContentTypes`, and
`maximumSizeInBytes: declaredSize`.

**No read capability.** The page issues exactly one query — `SELECT name,
slot_start FROM appointments WHERE id = …` — and never touches
`appointment_files`. The island has no `fetch`, no `$effect`, no lifecycle hook;
its only network call is `upload()`. PII confirmed **in the built server chunk**,
