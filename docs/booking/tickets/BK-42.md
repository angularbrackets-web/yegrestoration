# BK-42 — The homepage booking CTA was invisible in production

**Status:** implemented 2026-08-17 — gates green, 4 red rows in the script plus
2 observed behavioural failures, verified in Chromium against the **real built
bundle**, not the dev server. Light tier, no reviews by design.
**Phase:** P10 · **Tier:** Light (presentation only — no write path, no schema,
no endpoint, no URL shape) · **Depends on:** nothing · **Blocks:** nothing.
**Deploy:** 1.5. **Migration:** none.

## What was wrong

The client reported the homepage booking button "flashes on refresh and then
disappears". It did. **`See available times` has been rendering at
`opacity: 0` on production** — present in the DOM, clickable in theory, invisible
in fact. The flash is the server-rendered HTML painting before the reveal script
runs and hides it.

Measured on production before anything was changed:

```
a.cta-primary "See available times"
  computed opacity: 0
  inline: "translate: none; rotate: none; scale: none;
           opacity: 0; transform: translate(0px, 16px);"   <- the tween's START values, after it finished
```

The seven siblings in the same stagger all reached `opacity: 1`. Only the
button did not.

## The mechanism, and the one property that singled the button out

`ContactSection.astro` reveals the card's children with a single
`gsap.from(formFields, { y: 16, opacity: 0, stagger: 0.06 })`. A `from()` tween
sets the start state, then **re-reads the element to learn what to animate back
to**. On an element with a CSS transition on that property, the read can land
mid-transition and record the *start* value as the destination — so the tween
runs `0 -> 0` and the element never appears.

`.cta-primary` carried `transition-all duration-200`. **It was the only one of
the eight children with a non-zero transition duration** — the other seven
compute to `0s` — which is exactly why exactly one element was stranded:

| child | transition-duration | final opacity |
| --- | --- | --- |
| `P`, `H3`, `P`, `UL`, `DIV`, `ASTRO-ISLAND`, `P` | `0s` | 1 |
| **`A.cta-primary`** | **`0.2s`** | **0** |

A `MutationObserver` on the button recorded the shape of it: twelve style writes
in one burst at t=373ms, a `translate3d` promotion at t=385ms as the tween began,
and a final write at t=1079ms putting `opacity: 0` back. The tween ran. It
animated to the wrong destination.

**This is not a BK-39 regression.** BK-39 changed the label and added the teaser;
the conflict predates it and would have hidden `Book Your Assessment` just as
readily. What BK-39 did do is ship a gate that could not catch it — see the
process note below.

## The fix, in two parts, both load-bearing

**1. `global.css` — `transition-property` is now the two properties `:hover` and
`:active` actually change, never `all`.** Removing `opacity` from the list is
what makes the fade work; proved causally by changing only this and re-measuring
(`opacity: 0` -> `opacity: 1`).

**2. `ContactSection.astro` — every reveal tween ends with `clearProps`.** Part 1
alone leaves the button **16px low forever**: `transform` is still transitioned,
for the hover scale, so the same corrupt read strands `y` at its start value of
16px. Rather than also de-transitioning `transform` — which would make every CTA
on the site snap instead of scale on hover — the tween now clears the inline
styles it wrote when it completes, and the element falls back to the stylesheet
whatever the tween recorded. Author inline styles survive: the form card's
`perspective: 1000px` is still there afterwards, checked.

Also folded in, one line, same eight lines of code: the three tweens were sharing
**one mutable ScrollTrigger config object**. Each now builds its own. They are
identical, so there was nothing to gain from sharing and a class of cross-talk to
lose.

## Assumptions log

1. **`transition-all` came out of `.cta-secondary` too, though nothing animates
   it today.** The hazard is a property of the class, not of its current
   position on one page; leaving one of the pair explicit and the other `all`
   would read as an oversight and invite the next person to "fix" it back.
2. **The fix is scoped to `ContactSection`, not applied to the other five GSAP
   sections.** I checked every `.cta-primary` on the homepage: seven of the
   eight are not GSAP targets at all and compute to `opacity: 1`. There is no
   second instance to fix, and touching four more sections to prevent a
   hypothetical is how a Light ticket becomes a risk. The general rule went to
   the ROADMAP's Known traps instead, which is where the next implementer will
   meet it.
3. **`prefers-reduced-motion` is still unhandled here and stays out of scope.**
   Pre-existing, unrelated to the defect, and it wants a decision about the whole
   site's motion rather than one section's.
4. **The teaser was never broken.** It renders `Next opening: Tue, Aug 18 ·
   11:30 a.m.` and caches it. It reads as missing because it sits directly above
   an invisible button. The *multi-slot* preview the client also expected is
   BK-28, deliberately not in Deploy 1.5.

### Red-observed

| # | Break | Assertion that went red |
| --- | --- | --- |
| s | `transition-all` put back on `.cta-primary`, rebuilt | the built rule must not transition `all` |
| t | `transition-property: opacity, transform, background-color` | the built rule must not transition `opacity` |
| u | one tween's `onComplete: settle()` deleted | every `gsap.from()` carries `onComplete: settle()` (3 tweens, 2 settled) |
| v | `clearProps` list narrowed to `translate,rotate,scale` | the clear list includes `opacity`; the clear list includes `transform` |
| w | *(behaviour)* the shipped defect itself | CTA at `opacity: 0` on production and reproduced locally at 1280×900 |
| x | *(behaviour)* fix 1 applied, `clearProps` not yet | CTA visible but stranded at `transform: translate(0px, 16px)` |

Rows s–v are the script; w and x are the browser. Note that `s` and `t` are
separate rows on purpose: `transition-property: all` does not contain the
literal string `opacity`, so the two assertions fail independently and neither
covers the other.

## What the script proves, and what it cannot

`verify-reveal.ts` cannot prove the button is visible — that needs a browser and
the repo has no driver, which is why the behavioural check is a recorded manual
gate rather than an automated one. What it does pin is the two structural
conditions the defect required, so they cannot return unnoticed.

It reads the **built** CSS rather than the source, deliberately. The hazard is
spelled `transition-all` in `global.css` and `transition-property:all` in the
artifact; only the second is what a browser gets. A source-only grep would keep
passing if Tailwind's expansion ever changed underneath it — the
"assertion that cannot fail" family the ROADMAP tracks. For the same reason the
script exits **non-zero** when there is no build output, instead of skipping:
a gate that reports green for a build nobody made is worse than no gate.

## Process note — how this shipped green

BK-39 logged "verified live end to end" and six red rows. All six were about
`booking-preview.ts`: which slot is soonest, how a stale cache entry is refused,
what happens on a malformed payload. Every one of them was true. **None of them
looked at whether the element was on the screen**, and the live check confirmed
the label string in the DOM — which was correct, on an invisible element.

The lesson is narrower than "check visually": it is that **a ticket whose subject
is a piece of UI needs at least one assertion about the rendered result, not only
about the data behind it.** A string is in the DOM long before a visitor can see
it. Recorded in the ROADMAP's Known traps.
