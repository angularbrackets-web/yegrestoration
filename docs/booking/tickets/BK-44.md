# BK-44 — The status dropdown can perform an approval

**Status:** committed 2026-08-20 on `deploy-2-prepay` — NOT deployed
**Phase:** P9 (post-deploy) · **Tier:** Reviewed — it is an admin write path that
sends customer mail and moves money's worth of state · **Deploy:** 3, or sooner
if the live-key swap is imminent (see "When this should ship")
**Migration:** none expected.

## The defect, in one paragraph

`review.ts`'s header states the design and states it correctly:

> *"Folding that into the editor would mean the editor's dropdown could also
> perform it, which is exactly what must not happen: an office member setting
> the status to `approved_awaiting_payment` by hand would approve a booking with
> no amount, no deadline and no email."*

**That is one dropdown selection away today.** `src/pages/admin/appointments/[id].astro`
renders **all eight** `APPOINTMENT_STATUSES` on every row, and
`src/pages/api/admin/appointments/update.ts` has **zero** transition guards. The
route that was split out to make the unsafe thing impossible sits beside a
control that still does it.

## Two consequences, the second worse

1. **`pending_review → approved_awaiting_payment` by hand** is the scenario the
   comment forbids verbatim. No amount is computed, no `payment_due_at` is set,
   no Checkout Session is created, and no email is sent. The slot is held, the
   customer hears nothing, and no clock is running — so BK-23 Task 4's stale
   sweep will not catch it either, because that sweep targets `pending_review`.
   The row is stranded in a slot-holding status with nothing to move it.
2. **`pending_review → confirmed` by hand** crosses the calendar-invite boundary
   (`couldHoldCalendarInvite`), so `update.ts` **sends the customer a
   confirmation email and an ICS invite with no payment taken.** That is
   directly against P9's locked decision: *"PAYMENT ALWAYS PRECEDES DISPATCH. NO
   EXCEPTIONS."* A crew is now expected at an address for a job nobody paid for,
   and the customer has a calendar entry saying so.

## Why it survived every gate

**Twenty-three verify scripts and none of them could see it, because each tests
a route and nothing tests whether two routes overlap.** `verify-booking-review.ts`
proves `review.ts` guards its transitions. `verify-booking-admin-db.ts` proves
`update.ts` writes what it is told. Both pass. The defect lives in the space
between them.

**`update.ts:266` is the other half of how it survived.** Its comment reads:

> *"with `createCheckoutUrl` returning null until BK-32, the status dropdown is
> currently the ONLY route to `confirmed`"*

True when written, false since BK-32 shipped **"Mark as paid — Interac"** as the
sanctioned manual confirm. A comment that was accurate at the time became the
justification for leaving a hole open, which is the same shape as this repo's
other stale-FINAL traps.

**Found 2026-08-19 by the user, minutes into the first real use of the review
screen**, by asking which of the two panels accepts a booking. That is the right
question, and having to ask it is the evidence: the ambiguity is a trap, not a
theoretical hole.

## THE DESIGN QUESTION THIS MUST ANSWER FIRST — and it is not the implementer's

**Should the office EVER be able to confirm a booking by hand, without a
payment?** Do not assume the answer is no.

- The **paid-another-way** case is already handled: BK-32's Interac action is
  the sanctioned route, and it records `payment_method` so the money is
  traceable.
- The **genuinely free** case is already handled too: `approveFree`
  (`review.ts:546`) sets `payment_method = 'none'` and skips Stripe.
- What is left is the **comp / warranty-callback / goodwill** case, and whether
  it exists at all is a business question. If it does, the answer is a
  deliberate, labelled, traceable control — **not** a status dropdown that looks
  identical to changing a pipeline stage.

**Client-facing, therefore not settleable in planning or by a fresh agent.**
Ask the user. Record the answer in the Assumptions log before building.

## Scope

- **Constrain the dropdown to transitions legal from the row's current status.**
- **Guard the same rule server-side in `update.ts`.** A template-only fix is a
  client-side check on a write path, and this codebase has paid for that
  distinction before. The server must refuse, not merely the UI.
- **Keep the two panels legible.** Half the defect is that the page never says
  which control is the decision. The user did not misread it; it does not say.
- **Fix `update.ts:266`'s stale comment**, and state what the sanctioned manual
  routes are now.
- **Leave `cancelled` reachable from everywhere it is today.** Cancelling is the
  office's escape hatch and must not get harder.

## Risk areas for the reviewer

- The transition map itself — an over-tight map that blocks a legitimate
  correction is a worse failure than the hole, because the office will work
  around it and the workaround will not be recorded anywhere.
- Whether the server guard and the dropdown can disagree. They must come from
  one source, the way `APPOINTMENT_STATUSES` is re-exported rather than
  redeclared (`booking-admin-entry.ts:49-61`).
- Whether `update.ts`'s invite-boundary mail is still correct once transitions
  are constrained.
- The pin must fail on the ROUTE, not on the template. Prove it by posting a
  forbidden transition directly to `update.ts`, not by checking the `<select>`.

## Verification it owes

- A red row per forbidden transition, driven through the endpoint.
- A red row proving the dropdown and the server guard read the same map.
- A red row proving `cancelled` is still reachable.

## Acceptance criteria

## Plan (2026-08-20)

### The rule, in one sentence

**The dropdown may write any status except the two the decision routes own as
an ENTRY — `approved_awaiting_payment` and `confirmed` — and it may write
`confirmed` only for a row that has already been paid.**

That is the whole map. It is not a status-pair table, and deliberately so: an
8×8 matrix is 64 cells nobody can hold in their head, and the failure the ticket
warns about — *"an over-tight map that blocks a legitimate correction"* — is a
matrix failure. Ownership of an entry plus one predicate is a rule a person can
check a proposed edit against.

### Why `paid_at` is the predicate, and not `prev_status`

**`status = 'confirmed'` ⟺ `paid_at IS NOT NULL` is already an invariant of
this system everywhere except the defect.** `markPaid()` is the single writer of
`confirmed` (`booking-payment.ts:530`, `:610`) and it stamps `paid_at` in the
same statement. `approveFree` is not an exception — its own docstring is
explicit that it *"takes the ordinary approval transition and is then confirmed
through the same function a card payment goes through"*, with
`method: 'none'`. So a free approval has a `paid_at` too.

This is what makes the carve-out safe rather than clever. Asking *"has this
booking been paid?"* is asking the column that the one confirmation path
writes; asking `prev_status = 'cancelled'` would only be asking where the row
happened to come from, which is a proxy, and a proxy that is wrong for exactly
the dangerous case — a `pending_review` row cancelled and then un-cancelled has
never been paid, and a `prev_status` rule would wave it through to `confirmed`.

**Once this ships the invariant holds by construction**, because the dropdown
was the only writer of `confirmed` that did not go through `markPaid`.

### What the carve-out buys, concretely

| Transition | Allowed? | Why |
| --- | --- | --- |
| `confirmed → completed` / `no_show` | ✅ | The ordinary after-the-visit record. |
| `completed`/`no_show` → `confirmed` | ✅ | `paid_at` is set. The correction `update.ts`'s docstring names verbatim. |
| `cancelled → confirmed`, paid row | ✅ | *"The interesting case is un-cancelling."* The invite reissues, the index re-arbitrates, a 23505 is still translated. Unchanged. |
| `cancelled → confirmed`, never-paid row | ❌ | The hole, wearing a different hat. `paid_at` is null. |
| `pending_review → confirmed` | ❌ | Defect consequence 2. Free crew dispatch. |
| `approved_awaiting_payment → confirmed` | ❌ | Bypasses `markPaid`, so no `paid_at`, no `payment_method`, no reference, and no double-payment detection. |
| `* → approved_awaiting_payment` | ❌ | Defect consequence 1. `review.ts` owns this entry. |
| `approved_awaiting_payment → pending_review` | ✅ | **Already relied on.** `approveFree`'s comment describes *"a booking previously approved at a real price, sent back to `pending_review`"* — the office does this today and the code handles it. |
| `* → cancelled` | ✅ from every status | The escape hatch. Scope requires it and nothing here touches it. |
| re-submitting the current status | ✅ | Not a transition. Required for a notes- or stage-only save, and for the `<select>` to render its own value. |

### The one case this closes with no replacement, and its recovery

**A row cancelled while `approved_awaiting_payment` cannot be put back to
`approved_awaiting_payment`.** Restoring it would need a live payment link, a
deadline and a customer who was told — three things a status write does not
produce, which is the ticket's whole thesis.

**The recovery is through the sanctioned controls and it already exists:** set
the row to `pending_review` with the dropdown, then use **"Review this
request"**, which mints a fresh session, a fresh deadline and a fresh email.
`approveFree`'s comment shows that exact path is already in use and already
handles the dead session id. This is the answer to the over-tightness risk: the
map does not block the correction, it routes it through the control that does it
properly.

### One source, generated — the `SLOT_HOLD_PREDICATE` pattern

New in `src/lib/booking-status.ts`, beside the other lifecycle predicates:

```ts
/**
 * WHO OWNS ENTRY INTO EACH STATUS — the office's editor, or a decision route.
 * ... (reasoning as above)
 */
export const STATUS_ENTRY_OWNER: Record<AppointmentStatus, 'editor' | 'decision'> = {
  pending_review:            'editor',
  approved_awaiting_payment: 'decision',   // review.ts approve / approveFree
  confirmed:                 'decision',   // markPaid — card, Interac and free alike
  completed:                 'editor',
  no_show:                   'editor',
  declined:                  'editor',
  payment_expired:           'editor',
  cancelled:                 'editor',
};

export const EDITOR_STATUS_TARGETS = APPOINTMENT_STATUSES.filter(
  (s) => STATUS_ENTRY_OWNER[s] === 'editor',
);

/** The dropdown's options AND the route's guard, from one call. */
export function editorStatusTargets(row: Pick<Appointment, 'status' | 'paid_at'>): readonly AppointmentStatus[];
export function editorMaySetStatus(row: Pick<Appointment, 'status' | 'paid_at'>, next: AppointmentStatus): boolean;
```

**`Record<AppointmentStatus, …>` rather than a hand-written array, and that is
the safety property.** A status added to the union later is a **typecheck
error** until somebody classifies it — the compiler forces the decision that
was never made for the eight that exist today. `STATUS_LABELS` already uses this
shape in the same file, so it is the local idiom rather than a new one.

This also settles the deny-list-versus-allow-list question that
`SLOT_RELEASING_STATUSES` answers the other way. There, a deny-list is right
because a forgotten status *holds* its slot and the failure is a nuisance. Here
the failure of a forgotten status would be a dispatch, so the direction would
have to flip — except that an exhaustive `Record` makes "forgotten" a build
failure, and the question stops needing an answer.

### The server guard lives in the WHERE clause

`update.ts` runs one statement with a self-join snapshot and takes no SELECT
first, because *"reading 'is the slot free' before the UPDATE is the
check-then-act race this system already closed once."* The guard must not
reintroduce that. So it goes where `review.ts` puts its guards — in the
predicate:

```sql
WHERE appointments.id = old.id
  AND (
        ${nextStatus}::text IS NULL                       -- no status edit at all
     OR ${nextStatus}::text = appointments.status         -- re-submit; not a transition
     OR ${nextStatus}::text = ANY(${EDITOR_STATUS_TARGETS}::text[])
     OR (${nextStatus}::text = 'confirmed' AND appointments.paid_at IS NOT NULL)
  )
```

**A bound array parameter is correct here and a generated string is not
needed**, which is the opposite of `SLOT_HOLD_PREDICATE` and will read as an
inconsistency unless the comment says why: that string is a string *only*
because an `ON CONFLICT` arbiter cannot be parameterised without 42P10. This is
an ordinary WHERE with no arbiter, so the parameter binds. (If the Neon driver
turns out not to marshal a JS array to `text[]` cleanly, fall back to the
generated-text form and say so in the ticket — behaviour is identical, the
reason is driver mechanics.)

**Zero rows now means two different things**, and today's code reads it as one
(`?saved=missing`). Disambiguate with a read *after* the failed write:

```ts
if (rows.length === 0) {
  // Nothing was written, so this read is not a check-then-act: there is no
  // window between a decision and an action, only a message to choose.
  const still = await sql`SELECT 1 FROM appointments WHERE id = ${id}`;
  if (still.length === 0) return redirect(`${ADMIN_APPOINTMENTS_PATH}?saved=missing`);
  return redirect(`${detail}?saved=refused`);
}
```

New `SAVED_MESSAGES.refused`, worded to point at the control that does the job
rather than merely refusing: approving is *"Review this request"*, confirming is
payment — the card link or *"Mark as paid — Interac"*.

### THE RELATIONSHIP PIN — the trap the last session named

The defect survived 23 scripts because *"every script tests one route in
isolation and none tests whether two routes overlap."* A sixth per-route script
would not have caught it either. So one of the pins asserts the overlap
directly, at source level, in the spirit of `verify-cutover.ts`:

> **No status is an entry for both the editor and a decision route.** Read
> `review.ts` and `booking-payment.ts`, collect every literal assigned by
> `SET status = '<x>'`, and assert that set is disjoint from
> `EDITOR_STATUS_TARGETS`.

It goes red if someone reclassifies `confirmed` as editor-owned, if a decision
route starts writing a status the editor owns, or if a future money-bearing
status is added to the wrong side. **That is an assertion about the relationship
between two routes, and this suite has never had one.**

## Plan review (2026-08-20, fresh agent)

Verdict: **must be revised before building.** Four blockers, seven should-fixes,
five nits. The shape of the plan — ownership of an entry plus one predicate,
generated from an exhaustive `Record`, guarded in the WHERE clause, refused at
the route — is right, and the reasoning about why a matrix would be worse is
right. What is wrong is the *predicate*, the *fact it rests on*, and two of the
pins.

### Blockers

**B1 — `status = 'confirmed'` ⟺ `paid_at IS NOT NULL` is NOT an existing
invariant, and the plan's whole safety argument is stated as fact on top of it.**
`scripts/migrations/008-review-lifecycle.ts:95` runs
`UPDATE appointments SET status = 'confirmed' WHERE status = 'booked'` against
live rows. `paid_at` does not exist until `scripts/migrations/010-payments.ts:126`
and is **never backfilled**. So every pre-P9 row — 008's own header says 13 rows,
10 of them `booked` — is `confirmed` with `paid_at IS NULL`. Migration 008 is
explicit that this is deliberate: those rows get `payment_status = 'not_required'`
precisely because they were confirmed under a flow that took no money.
The reverse half fails too: `booking-payment.ts:608-618` (paid-after-release)
stamps `paid_at` on a `cancelled` / `declined` / `payment_expired` row and
deliberately leaves `status` alone.
*Concrete failure:* a legacy `confirmed` row is set to `completed` after the
visit (allowed), the office then notices it was the wrong row and tries the
correction `update.ts`'s own docstring names verbatim — `completed → confirmed`.
`paid_at IS NULL`, so the guard refuses it. There is no recovery through
`review.ts` either: `approve` guards on `status = 'pending_review'`, and routing
a 2026-era historical job through the approval screen would mint a payment link
for it. That is exactly the over-tightness failure the ticket says is worse than
the hole.
*What I would do:* (a) correct the sentence — it is a *post-BK-32* invariant for
rows created under prepay, not an invariant of the table; (b) adopt B2's
predicate below, which makes movement *within* the invite-holding set legal
regardless of `paid_at` and therefore un-breaks `completed → confirmed` for
legacy rows; (c) accept the one residual refusal (a legacy row cancelled by hand
cannot be un-cancelled) as a second "closed with no replacement" case, record it
beside the `approved_awaiting_payment` one, and pin it so it is a chosen refusal
rather than a surprise. Do **not** use `payment_status = 'not_required'` as the
legacy carve-out: `review.ts`'s `rollBack` (`:545-546`) writes that value onto a
live `pending_review` row, so the carve-out would re-open
`pending_review → confirmed` — the exact hole this ticket exists to close.

**B2 — the guard covers one of the three doors into the invite-holding set, so
the ticket's own consequence 2 survives the fix.** `couldHoldCalendarInvite`
(`booking-status.ts:154`) is `confirmed || completed || no_show`. The plan
classifies `completed` and `no_show` as `'editor'` and puts no predicate on
them, so they stay reachable from every status.
*Concrete failure:* a `pending_review` row (never approved, never paid, no
amount) is set to `completed` — or `no_show` — from the dropdown. In
`sendBoundaryMail` (`update.ts:233-235`) `hadInvite = false`, `hasInvite = true`,
so `kind = 'request'`; `prev_status !== 'cancelled'`, so the customer is sent
`planFirstConfirmationEmail` — *"Your assessment is confirmed"* — **with an ICS
`REQUEST` invite, for a job nobody paid for**, and the office calendar gets one
too. That is defect consequence 2 verbatim, one status over. The same holds from
`approved_awaiting_payment`, `declined`, `payment_expired` and never-paid
`cancelled`.
*What I would do:* make the predicate about the invite boundary, derived from
`couldHoldCalendarInvite` rather than from the literal `'confirmed'` —
"crossing INTO the invite-holding set requires `paid_at IS NOT NULL`; moving
within it is free". In the WHERE that is one extra disjunct, not a matrix:

```sql
OR ( ${nextStatus}::text = ANY(${INVITE_HOLDING_STATUSES}::text[])
     AND ( appointments.paid_at IS NOT NULL
        OR appointments.status = ANY(${INVITE_HOLDING_STATUSES}::text[]) ) )
```

This also fixes B1's legacy `completed → confirmed`, keeps the paid un-cancel,
keeps `confirmed ↔ completed ↔ no_show`, and makes the guard and the mail rule
read the *same* predicate — which is the strongest form of the ticket's "one
source" requirement, and it is a predicate that already exists in this file.

**B3 — the relationship pin as specified goes RED against the correct
implementation.** The plan says: *"Read `review.ts` and `booking-payment.ts`,
collect every literal assigned by `SET status = '<x>'`, and assert that set is
disjoint from `EDITOR_STATUS_TARGETS`."* `review.ts:724` is

*What I would do:* scope the assertion to ENTRY writes rather than to files:
the statuses written by `review.ts`'s `approve` / `approveFree` and by
`markPaid`'s confirm UPDATE — i.e. `approved_awaiting_payment` and `confirmed` —
must be disjoint from the editor's targets. A file-wide `SET status =` sweep is
the wrong shape because "this route writes X" and "this route is X's entry" are
different claims, and only the second one is the property being pinned.

**B4 — red-first row 3's expected red is backwards, so it cannot be observed as

## Plan revision (2026-08-20, after plan review)

**Verdict accepted: the plan above was wrong and is superseded by this section
wherever the two disagree.** Both design blockers were verified against the
code independently before revising; both hold.

### B1 — the invariant I asserted as fact is false in both directions

`008-review-lifecycle.ts:95` renames `booked → confirmed` against live rows.
`paid_at` does not exist until `010-payments.ts:126` and **is never
backfilled**, so every pre-P9 row is `confirmed` with `paid_at IS NULL` — by
design, which is why 008 hands them `payment_status = 'not_required'`. And
`booking-payment.ts:608-618` stamps `paid_at` on `cancelled` / `declined` /
`payment_expired` rows without touching status, so the converse fails too.

The sentence *"`status = 'confirmed'` ⟺ `paid_at IS NOT NULL` is already an
invariant"* is struck. It was the plan's whole safety argument and it was not
checked before being written down — the same failure mode as the stale comments
this ticket exists to fix.

`payment_status = 'not_required'` is **not** available as a legacy carve-out:
`rollBack` (`review.ts:545`) writes that value onto live `pending_review` rows,
so keying on it would reopen the hole for exactly the rows most likely to be
mid-flight.

### B2 — the predicate belongs to the invite boundary, not to `confirmed`

**This is the blocker that would have shipped a fix that did not fix the
defect.** `couldHoldCalendarInvite` is `confirmed || completed || no_show`
(`booking-status.ts:154`), so guarding `confirmed` alone leaves two other doors
into the same set. Setting an unpaid `pending_review` row to `completed` gives
`hadInvite = false, hasInvite = true` in `sendBoundaryMail`, so `kind =
'request'`, `prev_status !== 'cancelled'`, and the customer receives
`planFirstConfirmationEmail` — *"Your assessment is confirmed"* — with an ICS
`REQUEST`, for a job nobody paid for. **That is the ticket's own consequence 2,
reached through `completed` instead of `confirmed`.** Same from
`approved_awaiting_payment`, `declined`, `payment_expired`, and never-paid
`cancelled`.

**THE REVISED RULE, and it is now one sentence about the boundary rather than
about a status:**

> The dropdown may not create `approved_awaiting_payment`, and it may move a
> row **into** the invite-holding set only if that row has been paid. Movement
> **within** the set is free, movement **out** is free, and everything outside
> the set is the office's to edit.

Movement within the set is free because no boundary is crossed and no mail is
owed — which is also what un-breaks B1 at no cost: **a legacy `confirmed` row
going to `completed` and back never consults `paid_at`, because it is already
inside.** The correction `update.ts`'s docstring names verbatim keeps working
for exactly the rows B1 is about.

**Residual, recorded rather than solved:** a legacy `confirmed` row that is
*cancelled* and then wants un-cancelling crosses back in with no `paid_at` and
is refused. Every such row is a past appointment (ROADMAP: 008 moved 8 past
rows; no future-dated rows remained), so un-cancelling one is not a workflow.
Recorded here so it is a known cost rather than a surprise. **N4's converse is
also accepted:** nothing clears `paid_at`, so a hand-refunded `cancelled` row
still satisfies the predicate. It carries a `needs_attention` banner and a
deliberate office action either way.

### The third door, found while verifying the review's out-of-scope note

`rollBack` guards on `stripe_session_id IS NULL`, and says why:

> *"a row with a live session must never be walked backwards, because the link
> would still be payable against a `pending_review` row that `markPaid` would
> refuse."*

**The dropdown can walk it backwards, because `pending_review` is editor-owned
and `update.ts` has no such guard.** The customer then pays a live link against
a `pending_review` row; `markPaid` guards on `approved_awaiting_payment` and
refuses, and its paid-after-released branch guards `status IN
('payment_expired', 'declined', 'cancelled')` — which does not include
`pending_review`, so the money may land with no `needs_attention` raised at all.

This is BK-44's exact shape — a decision route's guard with an unguarded twin
in the dropdown — reached in the other direction. **It is folded in rather than
deferred**, because a map that ships as "the legal transitions" must not bless
a money-loss path: `approved_awaiting_payment → pending_review` is refused
while `stripe_session_id IS NOT NULL`. One disjunct, derived from `rollBack`'s
existing rule rather than invented. The recovery is unchanged and already
correct — approve, or decline, or cancel.

### The guard, revised

```sql
WHERE appointments.id = old.id
  AND (
        ${nextStatus}::text IS NULL                          -- no status edit
     OR ${nextStatus}::text = appointments.status            -- re-submit, not a transition
  )
  OR (
        ${nextStatus}::text <> ALL(${DECISION_ENTRY_STATUSES}::text[])
    AND (
          ${nextStatus}::text <> ALL(${INVITE_HOLDING_STATUSES}::text[])   -- not crossing in
       OR appointments.status = ANY(${INVITE_HOLDING_STATUSES}::text[])    -- already inside
       OR appointments.paid_at IS NOT NULL                                 -- paid its way in
    )
    AND NOT (
          ${nextStatus}::text = 'pending_review'
      AND appointments.status = 'approved_awaiting_payment'
      AND appointments.stripe_session_id IS NOT NULL
    )
  )
```

Every status set is **derived, not retyped** (S5): `INVITE_HOLDING_STATUSES` is
generated from `couldHoldCalendarInvite` over `APPOINTMENT_STATUSES`, and
`DECISION_ENTRY_STATUSES` is the `'decision'` half of `STATUS_ENTRY_OWNER`. With
B2's framing, `confirmed` no longer appears as a literal anywhere in the SQL.

`STATUS_ENTRY_OWNER` keeps only `approved_awaiting_payment: 'decision'` — the
invite predicate now carries what `confirmed: 'decision'` used to.
